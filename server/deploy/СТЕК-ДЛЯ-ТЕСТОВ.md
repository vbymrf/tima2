# Стек для тестов сервера

Что нужно поднять, чтобы `go test ./...` прошёл **весь**, а не частично. Три
службы; какие именно и с какими доступами — здесь, где именно они лежат на
конкретной машине — в `doc_mig/ОКРУЖЕНИЕ.local.md` этой машины (вне git).

> **Зачем это отдельный документ.** Без служб прогон **выходит с нулём**:
> `internal/api/api_test.go:52` при недоступной базе делает `t.Skipf`, и 70 тестов
> из 118 не выполняются, а `go test` печатает `ok`. То есть отсутствие окружения
> выглядит как пройденная проверка. Ожидаемые числа прогона — в тире `server-full`
> (`.cursor/skills/adaptive-test-runner/project/PROFILE.md`).

## Три службы и зачем каждая

| Служба | Кому нужна | Сколько тестов ждёт |
|---|---|---|
| **PostgreSQL** | всему `internal/api` | 70 из 118 |
| **Redis** | шина событий и ограничитель частоты: `ws`, `sync`, `ratelimit` | 6 из этих 70 |
| **S3-совместимое** (MinIO) | медиа: загрузка, чанки, CAS | 2 из этих 70 |

Остальные 48 (`crypto`, `escrow`, `pii`, `calls`) идут без служб вовсе.

## Переменные

```
TIMA_TEST_DATABASE_URL   postgres://<user>:<pass>@<host>:<port>/<db>_test
TIMA_TEST_REDIS_URL      redis://[:<pass>@]<host>:6379
TIMA_TEST_S3_ENDPOINT    http://<host>:9000
```

Значения по умолчанию (когда переменная не задана) прописаны в тестах:
`api_test.go:52`, `ratelimit_test.go:22`, `ws_test.go:30`, `media_test.go:29`.

Доступы к MinIO **зашиты в тест**, менять их нечем: `tima-admin` /
`tima-dev-only`, бакет `media-test` (`media_test.go:34`). Бакет создаёт сам
`blob.New` — руками заводить не надо.

## Обязательное требование к имени базы

Имя обязано кончаться на `_test`. `ResetForTests` на базе без этого суффикса
**отказывается работать**, и это защита, а не формальность: `setup` труncate-ит
все таблицы, и указанный по ошибке dev-адрес стоил бы всей истории
(`internal/store/store.go:94`).

## Четыре ловушки, на которых теряется время

**1. Пароль Redis должен совпадать, а не «Redis должен быть доступен».** Redis без
пароля отвечает на URL с паролем так:

```
ERR Client sent AUTH, but no password is set
```

Тест ловит любую ошибку и пишет «Redis недоступен» — то есть **живая служба
читается как отсутствующая**, и шесть тестов молча пропускаются. Против
passwordless Redis нужен `redis://localhost:6379`, без пароля в URL.

**2. MinIO не поднимается service container-ом GitHub Actions.** Образу нужна
команда `server /data`, а service container задаёт только образ, `env` и
`options` — команду задать нечем. В CI он поднимается обычным `docker run`
(`.github/workflows/ci.yml`, задача `server`).

**3. `ok` от `go test` ничего не доказывает.** Пакет, где всё пропущено,
печатает `ok`. Считать надо построчно:

```bash
go test -count=1 -v ./... 2>&1 | tee /tmp/t.log
grep -cE '^=== RUN   Test' /tmp/t.log   # RUN
grep -cE '^--- PASS'       /tmp/t.log   # PASS
grep -cE '^--- FAIL'       /tmp/t.log   # FAIL
grep -cE '^--- SKIP'       /tmp/t.log   # SKIP  ← обязан быть 0
```

**4. Старый том Postgres роняет весь пакет — и выглядит это как «всё сломано».**
Замечено 2026-08-26 на машине сборки: 71 падение, все с одной строкой, ни один
сценарий не выполнился.

Тестовый том живёт дольше схемы. Если в нём остались таблицы от прежней версии
(тогда это были `communities` и `stories`) и они ссылаются внешним ключом на
`users` или `groups`, `TRUNCATE` отказывается работать:

```
ERROR: cannot truncate a table referenced in a foreign key constraint (SQLSTATE 0A000)
```

Отказ приходит в `setup`, то есть `t.Fatal` в **каждом** тесте пакета. Счёт
показывает семьдесят одно падение, а произошло одно: подготовка не удалась.

Это зеркало ловушки №3. Там пустота выглядит успехом, здесь — катастрофой, и оба
раза счёт врёт о том, что случилось. `check-server.ps1` теперь сам замечает
общую причину и называет её; лечится пересозданием тома:

```bash
docker compose -p tima-test -f server/deploy/docker-compose.test.yml down -v
```

Тестовый том данных не хранит — он для того и отдельный, `-v` здесь безопасен.

Само перечисление таблиц из `ResetForTests` с 2026-08-26 спрашивается у базы, а
не пишется руками, так что этот отказ больше не должен возникать. Ловушка
остаётся записанной, потому что старый том может дать и другие сюрпризы.

## Способ 1: Docker

Машина сборки. Два compose-проекта, тестовый слушает **55432**, доступ
`tima-test-only`.

```bash
docker compose -f server/deploy/docker-compose.test.yml up -d
docker compose -f server/deploy/docker-compose.dev.yml up -d
```

## Способ 2: без Docker, портативно

Машина, где Docker не используется. Ставится в один каталог, удаляется удалением
каталога, службы Windows не заводятся, права администратора не нужны.

**PostgreSQL** — zip с бинарями с `get.enterprisedb.com` (`…-windows-x64-binaries.zip`,
~330 МБ). Мажорную версию брать как на стенде (сейчас 16).

```
initdb  -D <данные> -U tima --pwfile=<файл> --auth-local=trust \
        --auth-host=scram-sha-256 --encoding=UTF8 --locale=C
createdb -h 127.0.0.1 -U tima tima_test
pg_ctl  -D <данные> -l <лог> -o "-p 5432" start
```

**MinIO** — один файл с `dl.min.io/server/minio/release/<платформа>/minio`:

```
MINIO_ROOT_USER=tima-admin MINIO_ROOT_PASSWORD=tima-dev-only \
    minio server <данные> --address 127.0.0.1:9000
```

**Redis** — на Windows официальной сборки нет; годится любая работающая служба или
порт 6379 из другого источника. Пароль тогда, скорее всего, не задан — см. ловушку 1.

Проверка живости, чтобы не гадать по логам:

```bash
pg_isready -h 127.0.0.1 -p 5432
redis-cli -h 127.0.0.1 ping
curl http://127.0.0.1:9000/minio/health/live
```

## Способ 3: CI

Ничего поднимать не надо — задача `server` в `.github/workflows/ci.yml` поднимает
всё сама на каждый push и **валит прогон при любом пропуске**. Это и есть основной
гейт; локальный прогон нужен для скорости, а не вместо него.
