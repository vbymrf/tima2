## 0. Зачем

Три требования, вокруг которых собран весь рефакторинг:

1. **Метаданные храним всегда и в открытом виде.**
2. **Персональные данные скрываем.**
3. **Ключи живут ограниченный срок, и срок — настройка, а не константа.**

Из них следует главная идея: **разделить сроки жизни трёх вещей, которые сейчас
склеены в одной строке таблицы.**

| Плоскость | Что | Срок | Видимость |
|---|---|---|---|
| Метаданные | кто-кому-когда-какого типа | вечно | открыто, но псевдонимно |
| Контент | текст, медиа | пока жив нужный ключ | шифртекст |
| Личность | телефон ↔ идентификатор, имя | пока живёт аккаунт | под ключом |

Связывает их крипто-шреддинг: истёк срок ключа — контент недоступен, метаданные целы.

## 1. Принятые решения

| № | Решение |
|---|---|
| 1 | Модель угроз для персональных данных — **утечка базы или бэкапа**, не компрометация сервера |
| 2 | Escrow — **только для ордеров**. Пользователю недоступен; потерял ключи — потерял переписку |
| 3 | Удаление пользователем — **пометка**, не стирание. Физически стираем только когда аккаунт удалён / чат в архиве **и** уничтожен escrow-ключ периода |
| 4 | Escrow-ключ — на пару **«чат × месяц»**, генерируется лениво при первом сообщении чата в эпохе |
| 5 | Срок ключа = длина эпохи + срок хранения по закону = **1 месяц + 6 месяцев = 7 месяцев** |
| 6 | Состояния аккаунта: **временный / постоянный / архивный**. Постоянный по неактивности не удаляется никогда |
| 7 | Аккаунт — **цепочка идентификаторов**. Текущий тот, чьи ключи доказуемы |
| 8 | Связка идентификаторов без подписи прежним ключом — собеседник видит **предупреждение о смене личности** |
| 9 | **Key-commitment делаем**, конверт версии 2 |
| 10 | Звонки: **в работу LiveKit не вмешиваемся**. Реализуем только групповые звонки |
| 11 | Ключ персональных данных — **отдельно от базы**, за одним интерфейсом. Отдельный сервер — позже |
| 12 | Содержимое сообщения — **массив узлов + разметка**, без якорей и смещений. Разметка приватного сообщения шифруется. Блоки в обоих контурах, профили возможностей обязательны ([ADR-0011](doc/adr/0011-message-content-model.md)) |

### Занятые номера ADR

| Номер | Решение |
|---|---|
| 0011 | Модель содержимого сообщения (принят) |
| 0012+ | Свободны: escrow-эпохи, key-commitment, цепочка идентификаторов, сроки хранения |

### Сроки (все — настройки)

| Обозначение | Смысл | Сейчас |
|---|---|---|
| У | Неактивность временного аккаунта → архив | 30 дней |
| СУ | Архив аккаунта → стирание | 30 дней |
| К | Окно воссоединения истории | 30 дней (К ≤ СУ) |
| Н | Архив чата → пометка удалённым | 180 дней |
| СЧ | Пометка чата → стирание | 180 дней |
| — | Длина эпохи escrow | 1 месяц |
| — | Срок жизни escrow-ключа | 7 месяцев |
| — | Срок хранения по закону | 6 месяцев |
| — | Окно восстановления связи в звонке | 30 секунд (в конфигурации LiveKit) |

## 2. Швы, которые режем сразу

Дёшевы сейчас, дороги потом. Не требуют ни второго сервера, ни шардирования.

1. **`key_id` рядом с каждым шифртекстом** — иначе первая же ротация упрётся в «каким ключом это зашифровано».
2. **Колонки региона и шарда в реестре escrow-ключей**, пусть с одним значением.
3. **`chat_id` как единственный ключ разбиения** — ни одна функция не должна требовать запроса по всем чатам сразу.
4. **Ключи только за интерфейсом или по адресу** — для escrow уже так (`ESCROW_URL`), для персональных данных сделать так же с первого дня.

## 3. Фазы

### Фаза 0 — развязать канон ✅ выполнено 2026-07-30

### Фаза 1 — личность и персональные данные

- [ ] `persons` как аккаунт; `users` становится «личностью в период»
- [ ] Цепочка идентификаторов: `person_id`, `valid_from/valid_to`, `link_proof`
- [ ] `phone_bidx` (HMAC с pepper) + `phone_enc` + `name_enc`; ключ и pepper вне базы и бэкапов
- [ ] Уникальность номера **только среди неархивных**
- [ ] Интерфейс шифрования персональных полей — единственная точка доступа к ключу
- [ ] Разрешение «идентификатор → человек» для клиентов

Пользователю не видно ничего. Фундамент под фазу 4.

### Фаза 2 — escrow-эпохи

- [ ] Реестр `escrow_keys` (регион, эпоха, шард, окна валидности, `destroy_at`)
- [ ] Ленивая генерация ключа при первом сообщении чата в эпохе
- [ ] **Независимые seed'ы**: никакого общего корня, иначе уничтожение — фикция
- [ ] Подписанный `/escrow/config` вместо `/escrow/pubkey`; клиент выбирает по чату и дате
- [ ] Уничтожение по расписанию + подписанная запись в аудит
- [ ] Ордер со scope: анклав отдаёт ключи сообщений, никогда — приватный ключ

Формат конверта не ломается: `escrow_key_version` становится идентификатором записи реестра.

### Фаза 3 — конверт версии 2

- [ ] `key_commitment = HKDF-SHA256(message_key, "tima/commit/v1")`
- [ ] Кладётся в подписываемые байты, AAD, обёрнутый ключ, escrow-блоб
- [ ] Сверка на всех четырёх путях; расхождение — отказ
- [ ] Отказ от неканонической подписи Ed25519 (low-S) на приёме
- [ ] Тест-векторы
- [ ] **Двухфазная выкатка**: сначала все принимают v1 и v2, потом начинают слать v2

Фазы 2 и 3 выпускать одной сборкой клиента — обе трогают запечатывание.

### Фаза 4 — удаление и сроки

- [ ] Состояния аккаунта и чата, `deleted_at`, `archived_at`, `purge_after`
- [ ] Сроки как политика в базе, а не константы в воркере
- [ ] GC с гейтом по `destroyed_at` эпохи
- [ ] Перерегистрация, воссоединение, QR-пункт «Присоединить прежний аккаунт»
- [ ] Экран выбора при занятом номере (перенос против «начать заново»)

Зависит от фаз 1 и 2.

### Фаза 5 — групповые звонки

- [ ] Участники звонка как сущность (сейчас `calls` — это `initiator_id` + `peer_id`)
- [ ] Права на вход и повторный вход в активный `call_id`
- [ ] Выдача токенов на участника
- [ ] **Обработчик вебхуков LiveKit** — сейчас отсутствует полностью
- [ ] `livekit.yaml`: включить TURN, задать умолчания комнаты
- [ ] UI-состояния звонка

Ни от чего не зависит, можно вести параллельно. Работы с качеством медиа нет.

### Фаза 5б — модель содержимого сообщения

Решение — [ADR-0011](doc/adr/0011-message-content-model.md). Ни от чего не зависит,
кроме фазы 3 (обе трогают формат): выпускать вместе с конвертом версии 2.

- [ ] `MessageBody`: поля `nodes` и `markup` новыми номерами, аддитивно
- [ ] Переходный релиз: отправитель кладёт и плоский `text`, и новую структуру
- [ ] Стабильные идентификаторы узлов в разметке (`n`), не позиция в массиве
- [ ] Публичный контур: `channel_posts.text` → `nodes TEXT[]` + `markup JSONB`
- [ ] Метаданные: основные — типизированные колонки (закрытый список), редкие поля по типам — ограниченный JSONB
- [ ] Редактор: один на оба контура
- [ ] Профили возможностей: пузырь сообщения и публикация
- [ ] Каскад стилей: фиксированный порядок + три режима читателя + защитный пол
- [ ] Кеш рендера с ключом по версии стилей, теме, ширине, масштабу шрифта
- [ ] Тест-векторы формата

Основная стоимость — не формат, а отрисовка блоков на всех платформах.
