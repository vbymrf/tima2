## 1. Регистрация (первое устройство, полный аккаунт)

```
1. Телефон подтверждён SMS + привязан email (обязателен)
2. Устройство генерирует одну `Kodium.generateKeyPair()` → `KodiumPrivateKey`
   (даёт и X25519-encryption, и Ed25519-signing из общего seed)
   — приватный ключ в Keystore (Android) / Secure Enclave (iOS)
3. Аттестация: Play Integrity / App Attest ([client-attestation.md](./client-attestation.md))
4. Регистрация device_id + публичных ключей на сервере (таблица devices)
5. Первое телефонное устройство помечается is_trust_anchor = TRUE
6. Генерация 10 резервных кодов (для восстановления входа) — показываются один раз
7. Ключ локальной БД: производный от пароля пользователя (PBKDF2, Kodium) — вводится раз в сессию
```

## 2. Привязка нового устройства

**Статус: реализовано** (`server/internal/api/device_link.go`,
`server/internal/store/device_link.go`, миграция `0027_device_link.sql`; клиент —
`DeviceLinkQr.kt`, `QrCodeImage.kt`, `DeviceLinkScan.kt` и экраны `App.kt`
`LinkNewDeviceScreen`/`HomeScreen` «Подключить устройство (QR)»). Протокол
адаптирован из прототипа `doc_add/timaNC/server/internal/phase1/device_link.go`
под здешнюю модель устройств (без деления по платформам, без отдельного
«завёрнутого секрета устройства» — тут не нужен, каждое устройство и так
получает свою независимую X25519+Ed25519 пару). Мультиустройство и до этого
уже работало — каждое устройство могло зарегистрироваться независимо по SMS;
QR — более быстрый путь ТУДА, где под рукой есть второе, уже авторизованное
устройство.

```
Новое устройство (без аккаунта)      Сервер              Авторизованное устройство
  1. генерирует encryption/signing      │                         │
  2. POST /link/start ─────────────────►│                         │
  │◄── session_id, qr_payload, ─────────│                         │
  │    claim_token (у себя)             │                         │
  3. показывает QR (qr_payload)         │                         │
  │                                     │   4. скан QR камерой ───│
  │                                     │◄── 5. POST /link/confirm │
  │                                     │      (Bearer + подпись   │
  │                                     │       Ed25519 над данными │
  │                                     │       из QR своим ключом) │
  │                                     │──► device_id нового ────►│
  │                                     │                         │
  │                                     │◄── 7. POST /recover/provide
  │                                     │      (ключи истории,     │
  │                                     │       перезавёрнутые на  │
  │                                     │       новое устройство)  │
  6. POST /link/claim (опрос,          │                         │
     claim_token) ────────────────────►│                         │
  │◄── user_id, device_id, ─────────────│                         │
      access_token
```

Подпись на шаге 5 — не формальность: сервер проверяет её по `signing_pub`,
уже сохранённому за подтверждающим устройством при ЕГО регистрации, поэтому
подделать подтверждение, зная только `session_id`/`secret` (например, из
логов), нельзя — нужен ещё и приватный ключ устройства, которое держит в руках
человек. Раскладка байт нормативна и продублирована байт-в-байт на Go
(`linkSigningBytes` в `device_link.go`) и Kotlin (`DeviceLinkSignature.kt` в
`messenger-crypto`).

**Подтверждать вправе только телефон** (`platform IN ('android','ios')`,
миграция 0029). Телефон остаётся якорем доверия: десктоп своё доверие
наследует, а не раздаёт дальше. Десктоп в ответ на `/link/confirm` получает
403 `not_a_phone`, и в штатном клиенте пункт «Подключить устройство (QR)» на
нём вообще не показывается.

> **Насколько это сильная проверка.** Платформу устройство сообщает о себе само
> (`PUT /devices/me/platform`, клиент вызывает при запуске). До аппаратной
> аттестации (Play Integrity / App Attest, Фаза 6) сервер проверить её не может:
> изменённый клиент объявит себя телефоном. Это **правило порядка, а не граница
> безопасности** — оно не даёт ошибиться штатному клиенту и фиксирует модель в
> коде, но злоумышленника с модифицированной сборкой не останавливает. Станет
> настоящей проверкой в тот день, когда появится аттестация: точка, где её
> подключать, — та же строка в `linkConfirm`.
>
> Устройства, зарегистрированные до миграции 0029, имеют пустую платформу и
> подтверждать не могут — до первого запуска обновлённого клиента, который
> объявит платформу сам. Обходить это правило для пустого значения было бы
> равносильно его отмене: пустой платформой прикрылся бы кто угодно.

**Передача истории — шаг 7, и он обязателен.** Сразу после подтверждения
подтверждающее устройство перезаворачивает ключи сообщений своих личных чатов
под X25519-ключ нового устройства (`shareHistoryWithDevice` → тот же
`/recover/provide`, что у восстановления, §4). Иначе новое устройство видело бы
переписку только с момента подключения: обёртки ключей адресуются per-device, а
старые сообщения заворачивались, когда этого устройства ещё не существовало.

Почему отдаёт именно подтверждающее устройство, а не запрашивает новое: у нового
устройства **нет ключа личности из секретной фразы**, а `chatRecover` требует
подписать им запрос (барьер против угона номера, §4). Попросить историю оно не
может по построению — значит, отдать её должен тот, кто и так подтвердил
привязку осознанным действием. Отдельного согласия не спрашиваем: скан QR и есть
согласие.

**Ключ личности при этом не передаётся.** Новое устройство получает доступ к
содержимому переписки, но не право выступать от имени аккаунта: воссоединение
личности, восстановление у собеседников и подтверждение других QR ему
недоступны — для всего этого нужна фраза. Это осознанная асимметрия: отозвали
устройство — оно не сможет ни писать под вашим именем, ни утащить аккаунт.

Отдаётся **вся** переписка, а не последняя страница: и выдача ключей
(`provideChatKeys`), и догон на принимающей стороне (`pullHistory`) идут
страницами по `before` до конца. Односторонняя правка тут не работала бы —
ключи ко всей истории при одностраничном догоне так и остались бы на сервере
неиспользованными.

Групповые чаты в передачу не входят: там доступ даёт `GK` версии, а не обёртка
на сообщение, и путь выдачи отдельный. Новое устройство получит групповые ключи
обычным порядком при первой же ротации.

### Десктоп без телефона: что он может

Правило «подтверждает только телефон» ограничивает **QR-привязку**, а не
многоустройственность как таковую. Полная картина:

| Сценарий на десктопе | Работает |
|---|---|
| Завести новый аккаунт (SMS, фраза генерируется и показывается) | да |
| Войти в существующий аккаунт по SMS + секретной фразе | да |
| Быть единственным устройством аккаунта | да |
| Добавить себе второе устройство по SMS + той же фразе | да |
| Подключиться по QR (нужен телефон, который подтвердит) | нет |
| Подтвердить чужой QR | нет |

Экран регистрации один и тот же на всех платформах (`newIdentity` /
`identityFromPhrase` живут в `jvmCommon`), а `SetOrCheckIdentity` пускает второе
устройство в аккаунт по совпадению `identity_pub` — то есть **ввод той же фразы
и есть штатный путь многоустройственности без QR.** QR — ускорение для случая,
когда телефон под рукой, а не единственная дорога.

Существенная разница между двумя путями:

- Десктоп, вошедший **по фразе**, получает ключ личности — значит, может просить
  историю у собеседников (`chatRecover` подписывается этим ключом), делать
  воссоединение личности и читать резервную копию «сообщений себе». Полноправное
  устройство.
- Десктоп, подключённый **по QR**, ключа личности не получает (см. выше) — ему
  историю отдаёт телефон в момент привязки, но сам просить он её не может.

Отдельного «демо-режима» в коде нет: десктоп без привязки — это обычный аккаунт,
который просто ничего не наследует от прежних устройств.

**Оговорка, которую важно не потерять:** сквозной сценарий (реальная камера,
два физических устройства) не проверялся физически — среда разработки этого не
позволяет. Проверено модульными тестами протокола (сервер: `device_link_test.go`;
Kotlin: `DeviceLinkSignatureTest.kt`, `DeviceLinkQrTest.kt`) и сборкой на машине
с тулчейном (см. `ОТЧЁТ-О-РАБОТЕ.md`), но не «человек навёл камеру и увидел
результат». Перед боевым использованием — ручная проверка на двух устройствах.

Windows-клиент не проходит аппаратную аттестацию — его доверие по-прежнему не
завязано на QR ([client-attestation.md](./client-attestation.md)); это отдельный,
ещё не подключённый пункт readiness-gate Фазы 6.

**Смежный (не идентичный!) случай** — воссоединение личности после потери
устройства БЕЗ второго живого устройства под рукой: подпись ключом, выведенным
из секретной фразы, криптографически неотличима от подписи «живым» устройством
на шаге 5 выше — тот же ключ, та же проверка. `POST /users/me/reidentify/challenge`
+ `POST /users/me/reidentify` (`server/internal/api/identity_reunion.go`)
доказывают владение прежним ключом ЛИЧНОСТИ и переносят текущее устройство на
новую, проверяемую голову цепочки идентификаторов — в отличие от QR-привязки
выше, здесь нет ни QR, ни второго устройства, только фраза. Подробности —
`ДОКУМЕНТАЦИЯ/02-приложение/перенос-аккаунта-на-новое-устройство.md`.

## 3. Мультиустройство в повседневной работе

- Каждое сообщение получает wrapped_key для **всех активных устройств** отправителя и получателя ([crypto-protocol.md](./crypto-protocol.md) §3.2).
- Ratchet-сессии по-устройствные; их синхронизация между устройствами не выполняется (устройство без сессии использует путь B).
- Список устройств виден пользователю; «выйти со всех устройств» — массовый отзыв (§5).

## 4. Восстановление

| Сценарий | Что происходит |
|----------|---------------|
| Забыт пароль входа | Восстановление через SMS + email + резервный код; ключи устройств не затрагиваются |
| Потерян телефон, есть другое доверенное устройство | Второе устройство становится якорем; старый device отзывается |
| Потеряны все устройства | Новый вход по SMS+email+резервному коду → аккаунт восстановлен, но **защищённая история недоступна**: wrapped keys адресованы identity-ключам утраченных устройств, перезавернуть их некому, escrow пользователю недоступен (осознанное свойство схемы) |
| Забыт пароль локальной БД | Локальный кэш сбрасывается; история восстанавливается как «потеряны все устройства» |

Восстановления «через escrow» для пользователей **нет** — escrow только для юридической процедуры ([escrow-legal-access.md](./escrow-legal-access.md)).

## 5. Отзыв и компрометация

```
Отзыв устройства (revoked_at):
1. Сессии и push-токен аннулируются; WS разрывается
2. Wrapped keys для устройства перестают создаваться; существующие помечаются deleted
3. Во всех личных группах пользователя — ротация GK (устройство больше не получит новых версий)
4. Собеседникам 1:1 — событие key.changed (UI-предупреждение при смене identity)
```

- Компрометация identity-ключа = отзыв устройства + перегенерация на чистом устройстве.
- Смена identity собеседника всегда видима в UI (safety number) — защита от подмены сервером.

**Реализовано** (появилось вместе с QR-привязкой — подключать устройство одним
сканом и не уметь отключать было бы однобоко): `GET /api/v1/devices` — свои
активные устройства с именами, `DELETE /api/v1/devices/{deviceID}` — отзыв.
Список и кнопка отключения — в настройках клиента.

Границы реализованного отзыва, чтобы не было ложных ожиданий:

- Отзыв ставит `revoked_at`; устройство немедленно теряет доступ к API (все
  запросы к `devices` фильтруют `revoked_at IS NULL`) и перестаёт получать
  новые обёртки.
- **Уже скачанное на отозванном устройстве остаётся у него.** Отзыв закрывает
  доступ к новому, но не стирает старое на чужой стороне — так и написано в
  диалоге подтверждения, чтобы человек не рассчитывал на большее.
- Существующие обёртки в базе не удаляются: они могут быть нужны ОСТАЛЬНЫМ
  устройствам аккаунта как источник восстановления. Их стирание — работа GC по
  ретеншену, а не отзыва.
- Пункт 3 выше (ротация GK при отзыве) **реализован как просьба, а не как
  действие сервера**: групповой ключ генерирует клиент, сервер его не видит
  никогда (crypto-protocol §4) — ротировать ему нечем. При отзыве сервер шлёт
  админским устройствам групп событие `group.rotation_needed`, клиент-админ
  выполняет обычную ротацию, и новый GK заворачивается только на действующие
  устройства. Следствие: **ротация происходит не мгновенно, а когда админское
  устройство окажется в сети.** До этого момента отозванное устройство держит на
  руках действующую версию GK — доступа к серверу у него уже нет, но ciphertext,
  полученный иным путём, под этой версией остаётся читаемым.
- Событие уходит всем админским устройствам сразу, поэтому первым успевает одно,
  остальные получают `version_conflict` — это штатная гонка, а не сбой.
- Последнее активное устройство отозвать нельзя (`last_device`, 409): аккаунт
  остался бы без единой точки входа. Для «уйти совсем» есть удаление аккаунта.

## 6. PreKeys (фаза ratchet)

- Каждое устройство поддерживает на сервере: 1 Signed PreKey (ротация раз в 7 дней) + пул 100 One-Time PreKeys (пополнение при остатке < 20).
- Signed PreKey обязан быть верифицирован подписью identity при handshake (условие gate, [ADR-0005](../adr/0005-kodium-readiness-gate.md)).
- Consumed OTK помечаются и не переиспользуются; при исчерпании X3DH деградирует на Signed PreKey (штатно).

## 7. Временный режим (аккаунт без телефона/email)

Пользователь может начать работу **без указания телефона и email** ([22-auth-registration](../doc_UI/22-auth-registration.md)).

| Свойство | Временный аккаунт |
|----------|-------------------|
| Идентификация | Только device_id + локальный пароль; `account_type = 'temporary'` |
| Ключи | Identity/signing генерируются как обычно; крипто-протокол идентичен полному аккаунту (конверт + wrapped keys + escrow) |
| Устройства | Ровно одно; QR-привязка недоступна (нет якоря доверия) |
| Восстановление | **Отсутствует.** Потеря устройства/пароля = потеря аккаунта |
| Поиск по номеру | Невозможен (номера нет); добавление в контакты — по QR/username |
| Срок жизни | Удаление после 30 дней неактивности (`last_active_at`) с предупреждением |
| Апгрейд | `POST /auth/upgrade`: привязка телефона + email → выдача резервных кодов → аккаунт становится полным, устройство — якорем доверия. Ключи и история не меняются |

Ограничения против злоупотреблений (антиспам): пониженные rate-лимиты, аттестация обязательна, невозможность создавать публичные группы/каналы до апгрейда.

## 8. Ключи виртуальных пользователей

У ВП нет собственных устройств ([virtual-users.md](../01-product/virtual-users.md)) — его ключами владеют устройства команды:

```
1. Создание ВП: устройство владельца генерирует identity + signing пары ВП
2. Приватные ключи существуют ТОЛЬКО wrapped на устройства владельца и операторов
   (vu_wrapped_keys, версия ключа); в Keystore не кладутся — расшифровка по требованию
3. Входящее к ВП: обычный конверт, wrapped_key на identity-ключ ВП
4. Исходящее от ВП: подпись signing-ключом ВП; actor_user_id — в серверном аудите
5. Смена состава операторов → ротация (новая версия ключей, перевыдача wrapped)
6. Передача ВП: ротация обязательна по умолчанию — старый владелец гарантированно
   не читает сообщения ПОСЛЕ передачи (копии, сделанные до неё, неустранимы)
```

Ограничение MVP: ВП не участвует в звонках и не имеет ratchet-сессий (только конвертный путь B).
