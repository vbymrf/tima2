# Escrow и юридический доступ

> Политика controlled escrow: зачем, как, с какими гарантиями и как это коммуницируется пользователям. Решение — [ADR-0004](../adr/0004-controlled-escrow.md), техника — [crypto-protocol.md](./crypto-protocol.md) §6.
>
> **§5–6 обновлены 2026-08-11** под фактически реализованную модель эпох
> ([ADR-0012](../adr/0012-escrow-key-epochs.md)) — она заменяет описанный ниже
> план «единый ключ, ротация раз в 12 месяцев», который в коде не появлялся.
> Добавлено §9 про подпись конфига анклава (тот же ADR-0012, «Что осталось»).

## 1. Суть

Каждый ключ защищённого контента дополнительно инкапсулируется (ML-KEM-768) на публичный escrow-ключ. Приватный escrow-ключ существует только внутри HSM/анклава и может быть применён исключительно по формальной процедуре. Это позволяет исполнять юридически обязывающие запросы **без** компрометации identity-ключей пользователей и без бэкдора в протоколе.

## 2. Терминология для пользователей

Юридически схема **не является strict E2E**: существует технический канал доступа по процедуре.

| Где | Формулировка |
|-----|--------------|
| UI (статус чата) | «Защищённый чат — сообщения шифруются на вашем устройстве» |
| UI (окно информации, [16-profile-popup](../doc_UI/16-profile-popup.md)) | Краткое пояснение + ссылка на политику |
| Политика конфиденциальности | Полное описание: шифрование на клиенте; доступ провайдера возможен только по юридически обязывающему запросу через многостороннюю процедуру с аудитом |
| Маркетинг | Не использовать «E2E»/«сквозное» без оговорки |

Внутри документации термин «E2E» допустим только как UI-ярлык со ссылкой сюда.

## 3. Процедура доступа

```
1. Юридически обязывающий запрос (суд/уполномоченный орган) → Security Officer
2. Проверка объёма запроса: конкретный пользователь/чат + период (не bulk)
3. M-of-N (Shamir, минимум 3-of-5 держателей долей) → разблокировка операции в HSM
4. HSM: для каждого escrow_blob запрошенного периода → decapsulate → message_key / GK
5. Расшифровка payload'ов — в изолированной среде следственного ПО, не в продакшн-контуре
6. Append-only audit log: кто, основание, объём («N сообщений, из них M soft-deleted»)
```

**Инварианты:**
- Никакого автоматического или программного доступа из бэкенда к приватному ключу escrow.
- Держатели долей — разные роли/юрисдикции; ни один сотрудник не имеет доступа единолично.
- Audit log недоступен для редактирования (WORM-хранилище) и периодически сверяется.
- Ключи выдаются **по периоду**, не «мастер-ключ навсегда».

## 4. Soft delete

- «Удалить для всех» → `deleted = TRUE`: клиентам не отдаётся, физически сохраняется.
- Юридический доступ видит удалённые сообщения периода; факт удаления отражается в аудите.
- Физическое удаление — по retention-политике (§5) фоновыми джобами.

## 5. Ключи эпох, а не единый ключ навсегда ([ADR-0012](../adr/0012-escrow-key-epochs.md))

Реализовано иначе, чем было задумано изначально: не один escrow-ключ на весь
сервис с ежегодной ротацией, а свой ключ на каждую пару **«чат × календарный
месяц» (эпоха)**. Молчащий чат ключа не имеет вовсе — он создаётся лениво, при
первом сообщении чата в эпохе.

Из этого прямо следуют два свойства, ради которых и затевалась эта модель:

- **Радиус утечки одного ключа — один чат за один месяц**, а не вся история
  сервиса за всё время.
- **Срок хранения — физический факт.** Ключ живёт `конец эпохи + срок хранения
  по закону` (сейчас 1 месяц + 6 месяцев = 7 месяцев — так сообщение последнего
  дня эпохи получает положенный срок целиком, а не на день меньше) и потом
  уничтожается автоматически, по таймеру, а не по запросу оператора.

`escrow_key_version` в `EscrowBlob` (формат конверта не менялся) стал
идентификатором записи реестра ключей, а не версией единственного глобального
ключа.

### Что означает уничтожение ключа

Уничтоженный по сроку ключ и никогда не существовавший — неразличимы снаружи:
анклав не раскрывает, что у него когда-то было что-то, чего сейчас нет. Запрос
на уничтоженный ключ получает штатный отказ, а не «ключ найден, но истёк» —
разница важна: вторая формулировка утекала бы информацию о прошлом.

Реестр публичных частей ключей (не приватного материала) хранится у бэкенда как
кэш — там же лежит `destroy_at`, по которому решается, можно ли уже физически
стирать связанное содержимое сообщений (см. [01-сервер §6](../../ДОКУМЕНТАЦИЯ/01-сервер/README.md#6-ключи-содержимого-живут-периодами-а-не-навсегда)).

## 6. Уничтожение — не ротация

Плановой ротации «раз в 12 месяцев» в реализованной модели нет — она не нужна:
каждый ключ и так живёт ограниченный, короткий срок (§5), после чего физически
уничтожается, а не заменяется на новый при живом старом. Уничтожение — автоматический
проход по таймеру, каждый прогон пишет в append-only журнал, какие идентификаторы
уничтожены: без такой записи «мы удалили» нельзя проверить ни аудитору, ни
команде самой.

Компрометация анклава (не отдельного ключа периода, а самой изолированной среды)
— по-прежнему немедленная ротация ВСЕЙ инфраструктуры анклава (не одного ключа)
+ расследование + уведомление по применимому праву.

## 7. Стадии внедрения

| Фаза | Реализация |
|------|-----------|
| MVP / бета | Stub-анклав: изолированный контейнер, тот же API (encapsulate на клиенте — уже настоящий ML-KEM), доли Shamir у команды. Данные беты помечаются как подлежащие escrow-политике |
| Публичный релиз (gate) | Production HSM или AWS Nitro Enclave; формализованные держатели долей; юридическая проверка политики; WORM audit log |

## 8. Риски

| Риск | Митигация |
|------|-----------|
| Восприятие «escrow = backdoor» | Прозрачная публичная политика, M-of-N, аудит, честная терминология (§2) |
| Принуждение к bulk-доступу | Технически ключи выдаются по периодам/чатам; политика отклонения bulk-запросов |
| Компрометация держателей долей | Разные юрисдикции/роли, ротация долей |
| Утечка audit log | Лог не содержит контента, только метаданные доступа |
| Компрометация бэкенда подменяет публичный ключ escrow, который получает клиент | §9 |

## 9. Подпись конфига анклава (реализовано 2026-08-11)

Между анклавом и клиентом стоит бэкенд, который физически видит и технически
может подменить `public_key`, отдаваемый клиенту (`/v1/pubkey`, `/v1/key`,
`/v1/keys/{id}`) — до этого пункта ничто не мешало скомпрометированному бэкенду
подсунуть клиенту чужой ключ и получить доступ к содержимому в обход всего
описанного выше механизма (порога долей, аудита, срока уничтожения).

Анклав подписывает каждый такой ответ отдельным ключом Ed25519 (не тем, что
инкапсулирует контент), бэкенд подпись только пересылает — проверить её он не
может и не должен: он и есть та сторона, от чьей компрометации подпись защищает.

Клиент проверяет подпись заранее известным публичным ключом анклава — не через
запоминание при первом обращении (TOFU): адрес сервера в приложении вводится
пользователем вручную, и доверие, укоренённое в первом ответе того же сервера,
было бы неотличимо от доверия бэкенду напрямую. Ключ анклава — константа,
приезжающая с сборкой приложения, а не по сети (так же, как доли Шамира
распространяются оператором вручную при инициализации анклава — см. §3).

**Честная граница**, не снятая этим пунктом: до отделения анклава от бэкенда на
физически отдельный, независимо администрируемый хост подпись защищает от
компрометации бэкенда — не от компрометации хоста, на котором прямо сейчас
работает сам анклав (см. §7, gate публичного релиза).
