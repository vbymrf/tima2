# ADR-0011: модель содержимого сообщения — узлы, разметка, профили возможностей

**Статус:** принят · **Дата:** 2026-07-30 · **Реализация:** частичная (2026-08-11) — см. «Что реализовано» в конце файла

## Контекст

Сейчас содержимое сообщения — `MessageBody` (`schema/proto/message.proto`): плоская
строка `text` плюс `entities` со смещением и длиной **в кодовых единицах UTF-16**.

Проблемы этой модели:

- Смещения в UTF-16 — известная ловушка совместимости (в самом proto стоит пометка
  «фикс interop»): они расходятся между платформами на эмодзи и составных символах.
- Любая правка текста требует пересчёта смещений всех последующих сущностей.
- Структуры сложнее плоского текста со стилями (заголовки, списки, таблицы,
  контейнеры) в модель смещений не ложатся вообще.
- Публичный контур (`channel_posts.text TEXT`) и приватный не имеют общей модели
  содержимого, хотя редактор и рендер должны быть общими.

## Решение

### 1. Текст — массив узлов, без якорей и смещений

Содержимое разделяется на две части: **текст** (массив строк) и **разметка**
(сущности, стили, структура). Якорные символы внутри текста не используются:
текст остаётся чистым текстом.

### 2. Идентичность узла отдельно от позиции

Порядок узлов даёт массив, идентичность — отдельный список идентификаторов в
разметке, параллельный массиву: `n[i]` — идентификатор узла `nodes[i]`.
Счётчик на документ, значения не переиспользуются.

```
nodes  = ["Заголовок", "Текст абзаца"]
markup = { "n": [7, 3],
           "l": [["h", [7]], ["p", [3]]] }
```

Почему не «идентификатор = индекс в массиве»: вставка узла в середину сдвигает все
последующие индексы, и каждая ссылка из блока становится неверной, хотя сама
разметка не менялась. Стабильные идентификаторы делают вставку и удаление
локальными операциями.

Идентификаторы в **массив текста не попадают** — он остаётся чистым.

### 3. Разметка отсутствует у обычного сообщения

Нет разметки — нет и идентификаторов: ссылаться на узлы некому.

```
nodes  = ["привет, как дела"]
markup = NULL
```

**Требование:** путь обычного сообщения не должен стать дороже нынешнего. Сегодня
это `SecretBox(zstd(protobuf(text)))`, после рефакторинга — то же самое.

### 4. Два контура, одна модель

| Контур | Где лежит содержимое |
|---|---|
| **Приватный** | Узлы и разметка — **внутри зашифрованной нагрузки**. Сервер хранит непрозрачные байты, как и сегодня. Схема базы **не меняется** |
| **Публичный** | `nodes TEXT[]` + `markup JSONB` открытым текстом. Сервер индексирует и ищет |

Разметка приватного сообщения **не хранится открытой**. Она выведена из содержимого
и раскрывает структуру, количество и положение ссылок, наличие медиа, а через
упоминания — идентификаторы пользователей, то есть социальный граф внутри
переписки. Для приватного контура JSONB не даёт ничего: сервер по нему всё равно не
имеет права искать.

### 5. Метаданные — типизированные колонки плюс ограниченный JSONB для редких полей

| Что | Где | Как добавляется |
|---|---|---|
| **Основные метаданные** — всё, по чему сортируем, ищем, чистим по срокам и гейтим escrow. Версия, ревизия, режим контента сюда же | типизированные колонки, **закрытый список** | миграцией |
| **Редкие поля, специфичные для типа** — длительность звонка, число вариантов опроса, идентификатор набора стикеров | одна колонка JSONB | правкой кода, но по документированному перечню |

**Правило для JSONB: ничего выведенного из содержимого сообщения.**

Почему основные метаданные не в JSONB, хотя их набор со временем растёт (у зрелых
мессенджеров это порядка 25–30 полей, у нас сейчас около 11):

- В PostgreSQL `ADD COLUMN` с NULL или неизменяемым значением по умолчанию **не
  переписывает таблицу** — это правка каталога, доли секунды на любом размере.
  «Миграция при росте метаданных» — дешёвая операция, а не то, от чего надо
  спасаться.
- Самый горячий запрос — упорядочивание `(chat_id, message_id DESC)`; ему нужен
  обычный btree, а не индекс по выражению над JSONB.
- Теряются проверки типов, NOT NULL и внешние ключи; форму данных начинают угадывать
  три клиента вместо одного объявленного места.
- Имена ключей хранятся в каждой строке.

И главное. Метаданные лежат **открыто и вечно**, поэтому их набор обязан быть
закрытым списком. С колонками добавление поля требует файла миграции — а это точка,
где кто-то спрашивает «это точно можно хранить открыто?». С JSONB новое поле
появляется правкой кода, которую никто не рецензирует как решение о приватности.
Трение здесь — не издержка, а функция.

### 6. Один формат разметки, читаемый человеком

Сокращённого формата с однобуквенными ключами нет. Полезная нагрузка сжимается zstd
**до** шифрования, а повторяющиеся длинные ключи — идеальный корм для словарного
сжатия: после сжатия разница между `"entities"` и `"e"` близка к нулю. Второй формат
стоил бы таблицы соответствий, синхронной между клиентом, сервером и редактором,
двух парсеров и класса ошибок, где они разъехались.

Если замер когда-нибудь покажет реальный выигрыш — компактизацию добавлять как
чистое кодирование на границе, а не как вторую схему.

### 7. Один редактор, два пути хранения

Редактор общий для приватного и публичного контура: одна реализация, и оформление
доступно в том числе в личной переписке. Куда лягут его результаты — в зашифрованную
нагрузку или в колонку JSONB — решает контур.

### 8. Блочное дерево в обоих контурах + профили возможностей (обязательны)

Блоки (контейнеры, таблицы, flex, grid) поддерживаются и в переписке, и в
публикациях. Формат один, но возможности ограничены **профилем**:

| Профиль | Что поддерживается |
|---|---|
| Пузырь сообщения | Подмножество: таблицы прокручиваются горизонтально, сложные сетки упрощаются |
| Публикация | Полный набор |

Профили не косметика. Таблица внутри пузыря шириной в 70% экрана телефона — реальная
проблема вёрстки, и без явного профиля она всплывёт как «сломанное сообщение».

### 9. Каскад стилей: фиксированный порядок + режим читателя

Три уровня стилей — глобальные (приложение → сообщество → чат), стили типов,
инлайн-стили. Порядок внутри режима **фиксирован**:

```
инлайн → тип → чат → сообщество → приложение
```

Поверх него — режим, который выбирает **читатель**:

| Режим | Что видит читатель |
|---|---|
| Как оформил автор | Замысел отправителя |
| Моё оформление | Выигрывают настройки читателя; от автора остаётся структура |
| По умолчанию | Оформление приложения |

Переопределяемый порядок приоритета не вводится: настраиваемый каскад — то место,
где пользователь видит результат и не может объяснить, почему он такой.

**Защитный пол действует во всех режимах, включая «как оформил автор»:** минимальный
кегль, обязательный контраст с фоном, запрет полноэкранной заливки. Без него
отправитель может прислать текст 4pt белым по белому — это не гипотеза, а рабочий
приём в травле и мошенничестве.

### 10. Кеш рендера

Клиент рендерит дерево один раз и переиспользует результат при прокрутке. Ключ кеша
обязан включать версию стилей чата и сообщества, тему, ширину и масштаб шрифта:
оформление живёт вне сообщения и меняется, иначе после смены стилей пользователь
увидит старую картинку.

## Последствия

- **`MessageBody` меняется аддитивно**: новые поля `nodes` и `markup` получают новые
  номера, старые клиенты их игнорируют. Но старый клиент отрисует такое сообщение
  пустым, поэтому на переходный релиз отправитель кладёт **и** плоский `text`
  (склеенные узлы), **и** новую структуру.
- **Приватный контур не требует миграции базы** — меняется только содержимое
  зашифрованной нагрузки.
- **Публичный контур требует миграции**: `channel_posts.text TEXT` → `nodes TEXT[]`
  + `markup JSONB`.
- Появляется работа по рендеру на всех платформах и по профилям возможностей — это
  основная стоимость решения, а не формат.
- Тест-векторы формата обновляются (обязательная часть `messenger-crypto`).

## Что реализовано (2026-08-11, Р5б)

Среда этого захода без Compose/Gradle-тулчейна не даёт писать и визуально
проверять блочный рендерер (таблицы, контейнеры, каскад на экране) — сам ADR
называет это «основной стоимостью». Сделана часть, что проверяется логикой без
визуального цикла:

- **Закрытый каталог типов** — `EntityType` (bold, italic, underline,
  strikethrough, code, link, mention, hashtag) и `BlockType` (paragraph, heading,
  quote, list, list_item, container, table, row, cell), оба с `UNKNOWN` для
  прямой совместимости: разметка от более новой версии клиента с незнакомым типом
  не роняет сообщение целиком, деградирует до текста без оформления для этого
  конкретного узла/сущности. `MarkupEntity.type`/`MarkupBlock.type` стали этими
  enum'ами вместо свободной строки.
- **Публичный контур** — `channel_posts` (миграция `0026`): `nodes TEXT[]`,
  `markup JSONB`, `markup_version INT`. `server/internal/api/channels.go` принимает
  и отдаёт nodes/markup, с тем же переходным путём, что у личных сообщений (нет
  nodes от клиента — сервер заворачивает `text` в один узел). Сервер проверяет
  только валидность JSON, не разбирает `Markup` семантически.
- **Профили возможностей** (`ContentProfile`, `ContentProfiles.apply`) —
  структурная часть §8: таблица шире `maxComfortableTableColumns` помечается
  `horizontalScroll`, контейнер глубже `maxContainerDepth` — `simplified` (дети
  дальше не разворачиваются). `BUBBLE` против `PUBLICATION`. Признаки для
  рендерера, а не порог, зашитый в код каждой платформы отдельно.
- **Каскад стилей** (`StyleCascade.resolve`) — чистая функция: порядок
  инлайн → тип → чат → сообщество → приложение; три режима читателя (`AS_AUTHOR` —
  полный каскад, `READER` — только слой приложения, несущий личные настройки
  читателя, `DEFAULT` — вообще ни один слой); защитный пол применяется последним
  во всех режимах — минимальный кегль, WCAG-контраст (цвет без гарантированного
  контраста с фоном отбрасывается, а не подгоняется), запрет полноэкранной заливки
  документу и настройкам чата/сообщества (у приложения — можно, угроза именно от
  автора и пространства, не от собственной темы).
- **Точечный инлайн-рендер** (`client/.../chat/InlineStyle.kt`) — сущности ОДНОГО
  узла → `AnnotatedString`/`SpanStyle` (Compose). Многоузловые сообщения (реальные
  блоки) показываются объединённым текстом без инлайн-оформления: смещения
  сущностей заданы в символах своего узла, а не склеенного текста. Подключено в
  пузыре личных/групповых сообщений и в ленте канала — `msg.markup`/`post.markup`
  теперь доходят из `MessageBody`/`channel_posts` до экрана (были раньше только на
  границе кодека, схлопывались в `plainText()` до рендера).
- **Локальное хранилище** (ADR-0016): `messages.markup_enc` — та же схема
  добавления колонки на месте (`ensureColumn`), что уже была у `attach_enc`/`kind`.

**Не сделано, открыто честно:** редактор (нет UI совсем), полный блочный рендерер
на экране (таблицы/контейнеры/списки — только текст, без структуры), кеш рендера
(бессмысленен без рендерера, который бы что-то кэшировал). Кросс-языковой
KAT-вектор `markup_json` не заведён — `schema/test-vectors/README.md` объясняет,
почему его нельзя честно заморозить руками без прогона `kotlinx.serialization`.
