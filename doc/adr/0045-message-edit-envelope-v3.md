# ADR-0045. Правка сообщения — версия 3 конверта

**Дата:** 2026-10-18

## Контекст

Правка по Решениям §8 — **новая запись, а не замена**: одно взломанное устройство иначе переписало
бы историю без следа. Запись правки несёт номер исходного сообщения. Вопрос был, где этот номер
живёт.

- **Только внутри тела.** Тогда сервер не знает, что это правка, и не может проверить «только
  автор», «не больше трёх», «до смены ключа», не может погасить уведомление и счётчик.
- **Открыто, но вне подписи.** Сервер видит номер, но любой, кто подменит его по пути, переносит
  правку на чужое сообщение того же автора.
- **Открыто и под подписью.** Номер в подписываемых байтах — значит, новая раскладка
  `canonical_bytes`, а по правилу этого файла раскладка меняется только новой версией.

Решение 5 плана (`doc_mig/Plan.md §0.0`: «формат конверта не меняется до v2») заказчик отменил
2026-10-06: формат меняется, но **только новой версией** — новый домен в подписываемых байтах, новый
вектор, прежняя версия принимается.

## Решение

### 1. Версия 3 — только у правок

Обычные сообщения остаются версии 2 (личные) и `tima.group_message.v2` (группы). Версию 3 несёт
только запись правки. Приёмная сторона принимает 1, 2 и 3.

### 2. Личная переписка: `canonical_bytes` v3

Раскладка версии 2 с `format_version = 3` и **хвостом** `u64(edit_of)` после `key_commitment`:

```
canonical_bytes_v3 = canonical_bytes_v2(format_version = 3) ⊕ u64(meta.edit_of)
```

`Metadata.edit_of = 8` (envelope.proto) — открытое поле: сервер читает его, не расшифровывая тело.
Хвостом — по той же причине, что и обязательство в версии 2: раскладка прежних версий не меняется
ни на байт, их векторы и подписи сходятся.

### 3. Группа: домен `tima.group_message.v3`

```
group_message_canonical_v3 =
    lp("tima.group_message.v3") ⊕ <поля как у v1> ⊕ sha256(payload)
  ⊕ u64(edit_of)
  ⊕ key_commitment            // 32 байта у закрытой группы; у публичной — пусто
```

У публичной группы ключа нет — нет и обязательства. Номер стоит **до** обязательства: длина
обязательства зависит от вида группы, а поле фиксированной длины после поля переменной длины
сделало бы раскладку неоднозначной без префикса.

### 4. Тело правки — изменённые узлы

`MessageBody.edits = 6`, элементы `NodeEdit{index, text, entities}`. `text`, `nodes`, `markup` записи
правки пусты.

- `index` — **позиция** узла в `nodes` исходного, не идентификатор: у сообщения без разметки
  идентификаторов нет, а узел есть — один.
- `entities` — инлайн-оформление узла (JSON-массив сущностей разметки, `node` = идентификатор узла
  исходного). Прежние сущности узла заменяются целиком: их смещения к новому тексту не подходят.
- Строение (блоки, ряды, ячейки, виджеты) правка не трогает: «разметка на месте» (Решения §8).

Правки применяются **по порядку номеров**: вторая правка того же узла перекрывает первую.

### 5. Что проверяет сервер

| Правило | Личная | Группа |
|---|---|---|
| исходное в той же переписке и не удалено | да | да |
| автор правки = автор исходного | да | да |
| правка не правит правку | да | да |
| правок у исходного меньше трёх | да | да |
| до первой смены ключа | месяц UTC (эпоха, ADR-0036) исходного = месяц правки | `gk_version` правки = `gk_version` исходного |

Отказ — `409` с причиной (`edit_limit`, `edit_closed`, `edit_not_author`, `edit_missing`). Тело сервер не
читает: проверить, что внутри только узлы, он не может, и это ему не нужно — подпись автора
под правкой и так говорит, что текст его.

Правка **не** поднимает уведомление, счётчик непрочитанного и последнюю строку в списке чатов.

### 6. Что делает клиент

- Правку без исходного **не показывает** (вступивший позже).
- Исходное показывает с применёнными правками и пометкой «изменено».
- Удалено исходное — правки скрываются вместе с ним.
- «Изменить» прячет, когда правок три или ключ сменился, и говорит об этом на экране.

## Последствия

- Два новых вектора: `canonical_bytes_v3`, `group_message_canonical_v3`
  (`schema/test-vectors/gen/edit-v3.mjs`, `node:crypto`); Go и Kotlin сходятся байт-в-байт.
- Клиент, не знающий версии 3, подпись правки не проверит и покажет запись как нечитаемую. Таких
  клиентов на стенде не остаётся после выкатки (`Plan.md §0.0` решение 3), а сервер выкатывается
  раньше клиента — расширение API ничего не ломает.
- Колонка `edit_of` в `personal_messages` и `group_messages` — аддитивная миграция.
