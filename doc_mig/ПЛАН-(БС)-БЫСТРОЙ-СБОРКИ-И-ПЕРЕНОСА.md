## Решения заказчика (2026-10-08)

| Вопрос | Решение |
|---|---|
| Что раздаётся | **отладочная, как есть**: журнал внутри, агент читает через `run-as`, инструменты не трогаем |
| Быстрая сборка | **отдельно, по надобности**, журнал тоже внутри; агент его не читает, только «Сообщить о проблеме» |
| Что берём из ветки `work/redmi-perf` | **всё, что можно забрать** |
| Подвисание при смене окна | **песочные часы ожидания** (а не окно, следующее за пальцем) |
| Код | **все восемь пунктов** из разбора; аватары — **несколько размеров, под каждый используемый в приложении** («в звонке у нас больше») |
| Redmi | **пусть стоит быстрая** до следующего обновления: «потом и так поменяем» |

## Э2. Решение «два вида сборки» — ADR-0043

`doc/adr/0043-…` и строка в `doc/README`. Содержание:

| | Отладочная | Быстрая |
|---|---|---|
| Команда | `assembleDebug` | `assembleFast` |
| Раздаётся стендом | да, как сейчас | **нет**, руками на нужный телефон; на стенд — только по прямому указанию |
| Пакет, подпись, номер | `io.tima.app.v2`, `5877a0b5…`, общий номер | те же |
| Имя версии | `2.0.N-dev-v2` | `2.0.N-dev-v2-fast` |
| Флаг отладки | есть | нет |
| Журнал | внутри; агент читает `run-as` | внутри; только «Сообщить о проблеме» |
| Сценарии агента, файлы стенда звонков | работают | не работают (`run-as`) |
| Скорость на Redmi A3 | прокрутка 69 / 150 мс | 22 / 48 мс сразу, 14 / 17 мс после компиляции |

Правила, которые из этого следуют, — туда же:

- **Быстрая живёт до ближайшего обновления.** Номер у неё общий: следующая раздаваемая версия
  встаёт поверх и возвращает отладочную. Забыть быструю на телефоне нельзя.
- **Компиляция по профилю** — в фоне, когда телефон на зарядке и не используется (раз в сутки,
  обычно ночью); каждое обновление её сбрасывает. На стендовых телефонах агент компилирует сразу
  после установки (`cmd package compile -m speed-profile -f io.tima.app.v2`).
- Замер скорости делается **только на быстрой**: замер на отладочной говорит о флаге отладки, а не о коде.

## Э3. Инструкция «как сделать быструю сборку»

- **Документ** `doc_mig/ВИДЫ-СБОРКИ.md` — для человека и для агента: когда какую; как собрать;
  как поставить; как проверить (имя версии с `-fast`, в `dumpsys package` нет `DEBUGGABLE`,
  отпечаток `5877a0b5…`); как скомпилировать сразу; как вернуть отладочную; чего на быстрой не
  сделать (журнал, сценарии, наборы стенда).
- **Скрипт**: ключ `-Быстрая` у `update-and-install-phone.ps1` — собирает `assembleFast`, берёт
  `outputs/apk/fast`, печатает отпечаток, ставит, компилирует на телефоне. `release.ps1` не трогается:
  он раздаёт, а быстрая не раздаётся. Скрипт с кириллицей — сохранять **с BOM**.
- **Ссылки**: `ВЕРСИИ/КЛИЕНТЫ.md` — столбец «вид сборки» у каждого телефона;
  `ЖУРНАЛ-И-ОТЛАДКА/ПОДКЛЮЧЕНИЕ.md` — «на быстрой `run-as` нет; это не поломка, не чинить»;
  навык сценариев на телефонах — «на телефоне с быстрой сценарии не гонять».
- Пакет в `doc_add/packages/` — `TIMA-N-fast.apk`, чтобы не спутать с раздаваемым.

## Э4. Песочные часы при смене окна

Смена окна строит новое окно с нуля, и на слабом телефоне кадр перехода бывает долгим (отладочная
на Redmi — около секунды). Человек не видит, что свайп пойман, и свайпает снова.

- Жест пойман (`windowSwipe` решил «вбок») — **сразу** песочные часы поверх содержимого окна.
- Смена окна — **в два кадра**: первый рисует часы, второй строит новое окно. Иначе часы не
  успеют появиться: тяжёлый кадр и есть тот, в котором их надо показать.
- Часы снимаются, когда новое окно нарисовало первый кадр.
- Жест отменён (вернули палец, не дотянули) — часы снимаются.
- Переход быстрый (быстрые телефоны, быстрая сборка) — часы не должны мигать: показывать с
  задержкой в один кадр или не показывать, если новое окно готово сразу. Порог — по замеру.
- Как выглядят часы (знак, место, фон) — показать заказчику снимком до раздачи.
- Проверка: на отладочной на Redmi свайп «Телефон» → «Стенд» — часы видны до появления «Стенда»;
  на Samsung и realme — не мигают.

## Э5. Код — восемь пунктов

Все помогают обоим видам сборки. По одному, каждый — коммит, тесты, замер на Redmi на быстрой
сборке до и после (прокрутка «Звонков», переход «Телефон» → «Стенд»), там, где это про скорость.

| № | Что | Где (по разбору) | Зачем | Риск |
|---|---|---|---|---|
| 1 | **«Стенд»**: ленивый список вместо одной колонки со всеми разделами; чтение и разбор файла наборов — не на главном потоке | `BenchScreen.kt`, `Root.kt` (`bench.reload()`), `BenchStore.kt` | переход на «Стенд» строит всё сразу | низкий |
| 2 | **Открытая переписка**: подписка на настройки запоминается, а не заводится заново каждую секунду; секундный тик — только для строки статуса | `Root.kt` (`settings.all().collectAsState`, `tickMs`) | лишняя работа каждую секунду в открытой переписке | низкий |
| 3 | **Индекс книги**: имя, «незнакомый», «забанен», раздел — поиском по ключу, а не проходом по книге в каждой строке; индекс строится раз на смену книги | `Root.kt` (`entryOfChat`, `strangerId`, `blockedId`, `kindOfId`, `personOfId`, `personOfChat`) | прокрутка «Чатов» и «Звонков» при большой книге | средний |
| 4 | **Справочник пачкой**: карточки людей спрашиваются из эффекта по видимым строкам одним запросом, а не по одному из каждой строки | `People.want`, `Root.kt` | первая прокрутка, сеть | средний |
| 5 | **Аватары нескольких размеров** — см. ниже | `People.kt`, `ImageCodec.android.kt`, `Avatar.kt` | память и первая прокрутка | низкий |
| 6 | **Звонок**: секунды разговора читает только плашка звонка, а не корень приложения | `Root.kt` (`LocalActiveCall provides ActiveCall(seconds = …)`), `CallHost.kt` | во время звонка и прогона стенда всё приложение перестраивается раз в секунду | средний |
| 7 | **Строка «Чатов»** без трёх невидимых образцов текста: ширина места под счётчик и время считается один раз на экран | `ChatsScreen.kt` (`Counter(SLOT_SAMPLE…)`, `FiveChars`) | каждая строка списка | низкий; вид строки не должен измениться — сверить снимком |
| 8 | **Очередь отправки** не ходит в базу на главном потоке при каждом изменении списка переписок | `BackgroundLoops.kt` | рывки при входящих | средний |

### Пункт 5 — аватары под каждый размер

В приложении четыре размера аватара (`AvatarSize`): `Small` (0,76 от обычного), `Normal`, `Big`
(1,9), `Huge` (3 — окно звонка, страница). Сейчас картинка одна — 512×512 — на все, а в строке
списка нужно около 84 точек.

- Байты аватара качаются **один раз** на человека; картинка раскодируется **под размер** — по
  стороне `AvatarSize.side` в пикселях этого экрана, с запасом до ближайшего уменьшения в два раза
  (`inSampleSize`), не больше исходной.
- Хранится по паре «человек, размер»; аватар сменился — сбрасываются все размеры человека.
- Раскодирование — не на главном потоке (уже так с `29c7f3cf`).
- Строка подписывается только на свою картинку, а не на всю карту лиц: пришёл один аватар —
  перестроилась одна строка.
- Проверка: снимки списка, страницы человека, окна звонка — картинка не мыльнее прежней; память
  процесса на Redmi до и после (`dumpsys meminfo`).

## Э6. Проверка целиком

- Тесты клиента после каждого шага.
- Redmi — быстрая и отладочная: прокрутка «Звонков», переход «Телефон» → «Стенд», свайпы
  (прямой, косой, после разгона списка, прокрутка с наклоном) — скрипты из беды.
- **Окно звонка**: свайп по картинке во время звонка — пара телефонов; ещё не проверялось ни разу.
- Второй телефон (Samsung или realme) — жест и часы.
- Итог — в беду и в отчёт дня.
