## 0. Карта целиком

```
        ТЕЛЕФОН А                    НАШ СЕРВЕР                    ТЕЛЕФОН Б
  ┌──────────────────┐         ┌──────────────────┐         ┌──────────────────┐
  │  CallScreen      │         │  POST /calls     │         │  CallScreen      │
  │  (feature-call)  │         │  /answer  /end   │         │                  │
  ├──────────────────┤         ├──────────────────┤         ├──────────────────┤
  │  CallHost        │──HTTP──▶│  calls.go        │         │  CallHost        │
  │  (shared)        │         │  ↓               │         │                  │
  ├──────────────────┤         │  device_events   │         ├──────────────────┤
  │  CallsOverHttp   │         │  + Redis Pub/Sub │──WS────▶│  EventStream     │
  │  (core-network)  │         └──────────────────┘ кадры   │  (core-network)  │
  ├──────────────────┤                  │                   ├──────────────────┤
  │  LiveKitCallEngine│                 │ вебхуки           │ LiveKitCallEngine│
  └────────┬─────────┘                  │                   └────────┬─────────┘
           │                    ┌───────┴────────┐                   │
           └────── медиа ──────▶│    LiveKit     │◀───── медиа ──────┘
                   SRTP         │      SFU       │
                                └────────────────┘
```

**Две дороги, и они не пересекаются.** Кто кому звонит — идёт через наш сервер. Звук и
картинка — мимо него, через SFU. Смешать их нельзя: сигналинг общий на все платформы,
медиа платформенное.

## 1. Из чего состоит

| Модуль | Строк | Что знает |
|---|---|---|
| `core-call` (общее) | ~400 | контракт звонка, пресеты, события, разрешения — **без Compose и без сети** |
| `core-call` (Android) | ~700 | LiveKit, микрофон, камера, поверхность видео, служба переднего плана |
| `feature-call` | ~500 | экран звонка: четыре состояния, лента событий, видео |
| `shared/CallHost.kt` | 656 | **состояние звонка как факт приложения** |
| `core-network` | ~200 | `POST /calls`, разбор кадров канала |
| `server/api/calls.go` | 429 | ручки, вызов, повтор, «занят» |
| `server/calls/` | ~250 | токены LiveKit и RoomService |
| `server/store/calls.go` | 210 | таблица `calls` и уборка |

**Экран не знает про LiveKit, движок не знает про сервер, сервер не знает про медиа.**
Каждый разрыв заведён намеренно, и каждый уже окупился: смена отрисовщика с `SurfaceView`
на `TextureView` не коснулась ни одной строки выше `core-call`.

## 2. Три контракта

### `CallEngine` — что умеет медиа

```kotlin
interface CallEngine {
    val state: StateFlow<CallState>
    val localVideo: StateFlow<VideoHandle?>
    val remoteVideo: StateFlow<VideoHandle?>

    suspend fun connect(door: CallDoor, publish: PublishPreset? = null)
    suspend fun disconnect()
    suspend fun setMicrophone(on: Boolean)
    suspend fun setCamera(on: Boolean)
    suspend fun setRemoteVideo(on: Boolean) = Unit
}
```

Сигналинга здесь нет намеренно: движку отдают **готовую дверь**.

```kotlin
data class CallDoor(val callId: String, val room: String, val url: String, val token: String)
```

Адрес SFU приходит **с сервера**, а не зашит в клиент: он зависит от развёртывания.

### `Calls` — что умеет сигналинг

```kotlin
suspend fun start(peerId: String, video: Boolean): CallStep
suspend fun answer(callId: String): CallStep
suspend fun end(callId: String, busy: Boolean = false): Boolean
```

`busy` — **слово от устройства**: только оно знает, что разговаривает. Сервер этого
состояния не наблюдает (ADR-0025 §1а).

### `VideoHandle` — дорожка, которую можно показать

```kotlin
interface VideoHandle
```

Пустой интерфейс, и это главное. Картинка рисуется платформенной поверхностью
(`TextureViewRenderer` из libwebrtc), Compose-вида у неё нет. Экран знает, что дорожка
**есть**, и просит платформу сделать под неё вид:

```kotlin
@Composable expect fun CallVideo(handle: VideoHandle, modifier: Modifier)
```

## 3. `CallHost` — сердце

Держит то, чего не знает ни экран, ни движок: **идёт ли звонок, кто собеседник, сколько
длится, что случилось**.

```kotlin
var active   by mutableStateOf(false)   // окно 0 показано
var state    by mutableStateOf(CallState())
var incoming by mutableStateOf(false)   // нам звонят, а не мы
var seconds  by mutableStateOf(0)
val events = mutableStateListOf<CallEvent>()
```

### Разница, которая стоила пяти часов простоя

```kotlin
private val busy: Boolean get() = active && state.stage != CallStage.Ended
```

`active` значит «окно показано» — после конца оно остаётся нарочно, там «Перезвонить» и
«Закрыть». **`busy` значит «я занят».** Пока проверялось `active`, завершённый звонок
глушил все входящие, и «чинилось» это погасшим экраном: Android пересоздавал окно.

### Три состояния вместо одного

```kotlin
val stage = when {
    roomState == DISCONNECTED  -> Ended
    roomState == RECONNECTING  -> Reconnecting
    roomState != CONNECTED     -> Connecting     // идём в комнату
    others.isNotEmpty()        -> Connected      // РАЗГОВОР
    everAnswered               -> Ended          // собеседник ушёл
    else                       -> Connecting     // в комнате одни: «Звоним…»
}
```

`Room.State.CONNECTED` значит «мы вошли», **а не «нам ответили»**. Пока стадия бралась
прямо оттуда, время шло с момента набора.

### Сторож набора

```kotlin
delay(RINGING_LIMIT_MS)                       // 45 секунд
if (!active || stage == Connected || stage == Ended) return@launch
note(if (incoming) words().call.missedCall else words().call.noAnswer)
hangUp()
```

Стоит **у обеих сторон и одним числом**: разойдись они, одна гасила бы звонок, который у
другой ещё идёт.

## 4. Путь звонка

### Исходящий

```
📞 в шапке  →  callPerson(peerId, name, video)
                  ├─ callHost.start(...)
                  └─ showCall()                    ← окно 0 И закрыть подокно
                       │
   askCallAccess(video) ──отказ──▶ событие «Нет доступа к микрофону» + кнопка
                       │
   POST /api/v1/calls ──409 busy──▶ событие «Собеседник занят»
                       │ 201
   engine.connect(door) → вошли в комнату → микрофон опубликован
                       │
   сторож 45 с ──────▶ «Не дозвонились», POST /end
```

**`showCall()` — один вход на все случаи**, и он существует потому, что забывался второй
шаг:

```kotlin
fun showCall() {
    window = Window.Call
    where = Where.Nothing     // подокно лежит ПОВЕРХ окна
}
```

Переписка, книга, страница — подокна. Сменить окно под подокном значит открыть звонок
невидимым. Эту беду чинили дважды: сперва для исходящего, потом — когда она вернулась на
входящем.

### Входящий

```
call.incoming (кадр канала)
   → Receiver.aboutCall → Assembly.callPings = "callId|from|kind"
   → Root: LaunchedEffect(callPing)
       ├─ callHost.ring(...)
       └─ showCall()
```

`ring()` защищается двумя проверками, и обе от настоящих бед:

```kotlin
if (active && callId == this.callId) return      // повтор того же вызова
if (busy) { calls.end(callId, busy = true); return }  // мы правда заняты
```

Первая — потому что сервер **повторяет** вызов; без неё повтор попал бы в ветку «занят» и
положил трубку собственному звонку. Вторая говорит звонящему «занят» словом того, кто
действительно занят.

## 5. Сервер

### Ручки

| | Что делает |
|---|---|
| `POST /api/v1/calls` | заводит звонок, шлёт `call.incoming`, **повторяет дважды** |
| `GET /api/v1/calls` | журнал: страница прошлого, `?limit=&before=`, только личные |
| `POST /api/v1/calls/{id}/answer` | `answered`, гасит звонок на **других устройствах ответившего** |
| `POST /api/v1/calls/{id}/end` | `ended`, из `ringing` → `missed`, с `?reason=busy` → `busy` |
| `POST /livekit/webhook` | `participant_joined` → `answered`; `participant_left`, `room_finished` → `ended` |
| `POST /api/v1/calls/{id}/join` | токен на перезаход — **только пока `ringing` или `answered`** |

**Вход перечисляет живые состояния, а не хоронит по списку.** Было
`if state == "ended" || state == "missed"`, и список уже протекал: `busy` в нём не
значился. Всякое новое состояние обязано быть закрытым по умолчанию — это единственная
сторона, в которую здесь можно ошибаться.

**Строка журнала отдаётся сырой** — `initiator_id`, `state`, `ended_by` и времена, без
посчитанных «направления» и «исхода». Причина: одна и та же запись читается по-разному у
двоих (`missed` у звонившего — «не дозвонился», у вызываемого — «пропущенный»), и поле,
зависящее от того, кто спросил, нельзя ни кэшировать, ни сверить двумя запросами.
Складывает клиент. Подробности — [ПЛАН-ЖУРНАЛА-ЗВОНКОВ.md](ПЛАН-ЖУРНАЛА-ЗВОНКОВ.md).

**`ended_by` — кто положил трубку.** Без него «отменил» и «отклонил» неразличимы: `/end`
зовут обе стороны, состояние выходит одно. Пишется **первый нажавший** и поверх не
переписывается; пусто — звонок закрыл уборщик или вебхук, то есть его бросили.

### Повтор вызова

```go
var ringAgainAfter = []time.Duration{2 * time.Second, 6 * time.Second}

for _, after := range ringAgainAfter {
    <-time.After(after)
    call, err := deps.store.GetCall(ctx, callID)
    if err != nil || call.State != "ringing" { return }
    ringPeer(deps, ctx, peerID, payload)
}
```

Живая доставка — Redis Pub/Sub, то есть **«не более одного раза»**. Потерянный кадр
означал, что человеку просто не позвонили. Это заплатка; лечение — Streams.

### «Занят» — только про звонящий телефон

```sql
SELECT EXISTS (
    SELECT 1 FROM calls
    WHERE (initiator_id = $1 OR peer_id = $1)
      AND ended_at IS NULL
      AND state = 'ringing'
      AND created_at > now() - interval '2 minutes'
)
```

Состояния `answered` здесь **нет намеренно**: оно закрывается снаружи и само не истекает.
Один незакрытый звонок пятичасовой давности сделал двоих недоступными.

### Токены LiveKit: у каждой ручки своё право

Измерено у живого LiveKit, а не выведено:

| Ручка | Право | Область |
|---|---|---|
| `DeleteRoom` | `roomCreate` | **служебная** |
| `ListRooms` | `roomList` | **служебная** |
| `RemoveParticipant` | `roomAdmin` + комната | одна комната |

```go
token, err := c.Issuer.ServiceToken(VideoGrant{RoomCreate: true}, roomAdminTTL, time.Now())
```

Пока слался `roomAdmin` на всё, `DeleteRoom` отвечал 401 — **комнаты не закрывались
вообще**.

### Уборка брошенных

```go
open, _ := w.Store.OpenCalls(ctx, abandonedAfter, 200)   // старше 5 минут
for _, c := range open {
    alive, err := w.Rooms.RoomExists(ctx, c.Room)
    if err != nil || alive { continue }       // ошибка → считаем живым
    state := "lost"                                   // разговор шёл, конец неизвестен
    if c.State == "ringing" { state = "missed" }      // трубку не брали вовсе
    w.Store.SetCallState(ctx, c.CallID, state, "")    // трубку не клал никто
}
```

**Два состояния, а не одно, и раньше это была ложь в журнале.** `ended_at` ставится **в
момент уборки**, а уборщик ходит раз в час (`TIMA_GC_INTERVAL`) по звонкам старше пяти
минут. Разговор на минуту, чей `/end` не доехал, читался как час с лишним. Теперь
`ringing` → `missed` (длительности нет вовсе, врать нечем), `answered` → `lost` — «конец
неизвестен», и журнал длительность не рисует.

**Возраст только отбирает кандидатов, решает живая комната.** Закрывать по возрасту значило
бы назначить разговору предельную длину.

**Журнал звонков не удаляется вовсе: `calls_journal_days = 0` (0054).** До этого
законченные звонки убирались по `delivery_retention_days`, и это было чужое число. Но
развязать оказалось мало — **удалять было нечего с самого начала**: в строке звонка нет
ничего, кроме метаданных, а у нас правилом записано и тестом охраняется, что метаданные
не удаляются никогда (`store.PurgeMessageContent`, `api/retention_test.go`). Ноль означает
«не убирать», уборщик при нуле задачу пропускает. Стирает звонки только стирание аккаунта,
то есть ручной запрос.

Сколько журнала держит **телефон** — отдельное решение и отдельное место: настройка
«Память и трафик», срок и число строк, что наступит раньше. Серверу она не указ, и
наоборот.

## 6. Медиа

### Пресет публикации

```kotlin
val codec: VideoCodec = VideoCodec.H264      // AV1 и VP8 исключены решением заказчика
val layers: LayerMode = LayerMode.Single
val width: Int = 640
val height: Int = 480                        // обе стороны кратны 16 — см. ниже
val fps: Int = 15
val bitrate: Int = 800_000
val degradation = Degradation.MaintainResolution
```

Два числа здесь добыты бедой, а не выбраны:

**480 вместо 360.** Аппаратный кодер Unisoc у realme на невыровненной высоте выдаёт
полосы. Своё изображение при этом целое — оно идёт мимо кодера, и это указало на причину.

**`MaintainResolution`.** WebRTC роняет разрешение ступенями, и на одной из них кодер
ломался. Размер теперь не плавает, жертвуется частота.

### Что видно в журнале

```
CALL уходящее видео  кадр=480×640 ужато=none кодер=OMX.sprd.h264.encoder кбит/с=801
```

Четыре величины, каждая отвечает на свой вопрос: плавает ли размер, кто ужал (`bandwidth`,
`cpu`, `none`), **какой кодер работает на самом деле**, доходит ли битрейт до заданного.

### Отрисовка

`TextureViewRenderer`, а не `SurfaceViewRenderer`. Второй — отдельный слой композитора:
система пробивает под него дыру, и всё, что нарисовано в её границах, теряется. Отсюда
были и пропавшая «Завершить», и полосы окна.

## 7. Служба переднего плана

```kotlin
startForeground(id, notification, FOREGROUND_SERVICE_TYPE_MICROPHONE)
```

Свёрнутое приложение без неё теряет микрофон. Обмерено: Samsung держал сеанс час, realme
оборвал через 3,5 секунды. **Работавший Samsung был случайностью.**

Типа `camera` нет намеренно: с Android 14 объявленный тип требует выданного разрешения, и
заявить камеру, не имея её, — падение вместо звонка.

## 8. Сквозные правила

**Устройство говорит только о себе, и только когда доступно** (ADR-0025 §1а). Молчание —
не сведения. Всё, во что сервер верит про человека, обязано истекать само.

**Конец определяется от обратного.** Продолжается только `answered`, всё остальное —
конец. Перечень конечных состояний обещал бы, что мы знаем их все.

**События двух родов.** Случившееся остаётся, длящееся снимается, когда кончилось. И
событие, которое чего-то просит, снимается, когда просьбу исполнили.

**В журнал идёт каждый шаг**, по которому потом придётся отличать «не дошло» от «дошло и
не сработало». Немой звонок был невидим именно потому, что этого правила не существовало.

## 9. Чего нет

**Входящего при закрытом приложении** — push нет вовсе ([ПЛАН-ПУШ-УВЕДОМЛЕНИЙ](ПЛАН-ПУШ-УВЕДОМЛЕНИЙ.md)).

**Гарантии доставки кадра** — Pub/Sub теряет молча ([ADR-0027](../doc/adr/0027-event-delivery.md)).

**Журнала звонков** — вкладка «Звонки» заглушка, события никуда не ложатся (З1–З6).

**Групповых звонков** — ручки на сервере есть, клиента нет.

**Звонков на ПК** — движок только под Android.

**Выбора пресета и чисел стенда** — С3–С8, и без них любая правка качества это гадание.
