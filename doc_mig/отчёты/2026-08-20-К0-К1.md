## К0.1 — инвентарь поведения · сделано

**Результат:** [инвентарь-поведения.md](../инвентарь-поведения.md), **16 пунктов**
вместо запланированных 10.

Шесть нашлись при вычитке и в плане их не было. Три из них стоит прочитать:

**⚠ РЕШЕНИЕ · пункт 13 — сборка только под `arm64-v8a`.** В `build.gradle.kts` v1
оставлен один ABI (нативные WebRTC и zstd под все ABI раздувают APK), и там же
записано капсом: **эмулятор x86_64 перестаёт работать, проверять надо на телефоне.**
Это упирается прямо в К8: ферма либо из живых телефонов, либо в v2 собирается второй
ABI для отладочных сборок. Заложить дешевле в К1, поэтому пункт поднят туда.

**Пункт 14 — подпись APK.** Отладочный ключ генерируется на каждой машине свой,
поэтому смена машины сборки давала «Приложение конфликтует с другим пакетом» у всех
установленных. Ключ в `keystore/` вне гита, его потеря = переустановка у всех. Плюс
распространяется **debug**-сборка со стабильной подписью: `release` потребовал бы
отдельной проверки R8.

**Пункт 12 — уведомление о загрузке обновления даёт только прогресс, без «нажми,
чтобы открыть».** По такому нажатию APK открывает система своим обработчиком, и на
Samsung им оказывается посторонний компонент — разрешение на установку она просит для
него, а не для нас.

Заодно уточнилось то, что в плане было сказано приблизительно:

- потолок zstd-бомбы — **16 МиБ, и проверяется до распаковки** через
  `Zstd.getFrameContentSize`; проверка после распаковки — уже съеденная память;
- `LinkState` — не «три состояния», а таблица из **13 признаков** в тексте
  исключения, каждый из журналов настоящих испытаний;
- `EscrowTrust.ENCLAVE_SIGNING_PUBLIC_KEY = null`, и проверка подписи анклава при
  этом **тихо пропускается**. В v2 переезжает как есть, но пропуск надо сделать
  видимым в диагностике.

Все 16 пунктов разложены по этапам: 13–15 в К1 (сборка и распространение), 1–3 в
К3.1, 4–6 в К2, 7–10 в К3, 11–12 в К7, 16 в К5.

## К1 — каркас · в работе

### Главная находка: у меня есть настоящая проверка

Репозиторий **публичный**, и Actions API читается анонимно. Значит каркас
проверяется машиной, а не пишется вслепую — той болезнью, которой этот проект уже
болел («код Р2/Р4/Р5б писался вслепую и ни разу не собирался» до 2026-08-12).

Заодно выяснилось: **раннеры macOS для публичных репозиториев бесплатны.** Из этого
следует то, чего не было в плане: прогон крипто-векторов на iOS-симуляторе можно
делать в CI, то есть **долг К2-iOS закрывается без покупки железа**. В задачу iOS
добавлен шаг с тестами на симуляторе — если он зелёный, решение 8 («iOS держим
компилируемым, но не запускаем») можно смягчить.

### Ограничение, которое пришлось обойти

**Логи прогонов через API отдаются только с токеном** (403 анонимно), а состояние
шагов — без него. Токена у меня нет и просить его ради этого не стоит.

Обход: CI перестроен так, что **имя упавшего шага само локализует поломку**. Шаг
делает по одному действию; задачи iOS разложены матрицей по gradle-задачам, поэтому
видно не «iOS упал», а какая именно задача. Крипто дополнительно печатает имена
упавших тестов в сводку прогона и выкладывает отчёты артефактом.

Это не стилистика, а единственный доступный здесь способ диагностики — и, кстати,
неплохой сам по себе: гранулярные шаги полезны и с логами.

### Первый прогон

| Задача | Итог |
|---|---|
| client · JVM | **зелёный** — каркас собирается, тесты идут |
| client · iOS klib | упал на компиляции |
| messenger-crypto | упал на тестах |
| server · build + vet | зелёный |

**Падение крипто важнее падения iOS.** Крипто я не трогал вовсе: значит это либо
предсуществующее падение (и тогда заявление «72 теста зелёные» от 2026-08-12
относилось к другому окружению), либо особенность CI. И то и другое надо знать до
К2, потому что К2 — гейт именно по этим тестам.

### Как выбраны версии и API

Ничего не угадано:

- версии Gradle, Kotlin, AGP, Compose — из тега `ref/client-v1`: они собирались;
- версии Konsist, Koin, coroutines, datetime — запросом к Maven Central;
- API Kodium, KyberKotlin и Wire — вычитаны из `messenger-crypto`, где они
  используются, а не восстановлены по памяти.

### core-model: идентификаторы типами, а не строками

В v1 `chatId`, `peerUserId` и `deviceId` были одним типом `String` — компилятор не
поймал бы перестановку аргументов. В v2 это `value class`, то есть в рантайме те же
строки без обёртки. `ServerMessageId` только положительный: ноль как «ещё не
отправлено» в v1 ездил в том же поле, что настоящий идентификатор, и это ровно тот
случай, когда отсутствие значения притворяется значением.

### Второй и третий прогон: диагностика заработала

Ключевое: **аннотации прогона отдаются анонимно, а логи нет.** Первый же разбор
дал ответ, который логами я бы не увидел:

| Что выглядело как | Чем оказалось |
|---|---|
| «упали тесты messenger-crypto» | `exit code 126` — у `messenger-crypto/gradlew` **не было бита исполнения**. Не тесты упали, а мой CI не смог их запустить |
| «упал iOS» | имена задач `compileKotlin*` не те, при этом `iosSimulatorArm64Test` **прошёл** |

Из этого CI перестроен: вывод Gradle перехватывается и при падении печатается
командами `::error::`, то есть превращается в аннотации. Без этого падение
выглядит как «exit code 1» и не сообщает ничего.

Заодно нашлась моя ошибка: шага `generateProtos` в плагине Wire нет — кодоген и так
вызывается компиляцией.

### Главная новость: iOS не просто компилируется, он исполняется

**`:core:core-model:iosSimulatorArm64Test` прошёл на раннере macOS.** То есть общий
код собирается под iOS **и тесты идут на симуляторе**, бесплатно, в CI.

Из этого следует то, чего не было ни в плане, ни в дорожной карте:

- **долг К2-iOS закрывается без покупки железа Apple** — векторы крипто можно
  прогонять на симуляторе в CI;
- решение 8 («iOS держим компилируемым, но не запускаем») можно смягчить до «iOS
  проверяется в CI, ручная проверка на устройстве — отдельно»;
- вопрос «доступ к сборочной машине Apple» из §7 плана перестаёт быть блокирующим
  для К2 и К5; он остаётся нужным только для того, что симулятор не покрывает:
  установка на устройство, камера, push, App Store.

**⚠ РЕШЕНИЕ:** подтвердить это смягчение? Оно снимает одну внешнюю зависимость с
длинным плечом, но не отменяет необходимости живого устройства к К7 (звонки) и
позже.

### Опорная точка получена: крипто зелёное в CI

После выставления бита исполнения **messenger-crypto проходит целиком**: тесты,
включая сверку с BouncyCastle как независимым оракулом. Это важно не само по себе, а
как точка отсчёта для К2: теперь «перенос ничего не сдвинул» будет означать
«те же тесты остались зелёными», а не «на моей машине работало».

Заодно снимается подозрение, возникшее на первом прогоне: заявление «72 теста
зелёные» от 2026-08-12 подтвердилось независимо от той машины.

### Что ещё красное и почему это нормально на этом этапе

| Задача | Состояние |
|---|---|
| `server · build + vet` | зелёная |
| `messenger-crypto` | **зелёная** |
| `спайк · jvmTest` и `iosSimulatorArm64Test` | красные — разбираются |
| `client · iOS compileKotlin*` | красная: имя задачи не то (зависящий от неё тест проходил) |
| `client · JVM build` | красная, потому что собирает и спайк |
| `архитектурные правила` | красная — разбирается |

Спайк красный — это не провал, это его работа: он задаёт вопрос «поедут ли
зависимости крипто на iOS» и обязан дать ответ до К2. Ответ пока не получен: до
последней правки CI падение выглядело как «exit code 1» без текста.

### Найдена настоящая ошибка каркаса

Аннотации в собранном виде наконец дали текст:

> «The request for this plugin could not be satisfied because the plugin is already
> on the classpath with an unknown version»

`architecture-tests` запрашивал `kotlin.jvm` с версией, тогда как
`kotlin.multiplatform` уже лежал на classpath из корневого блока `plugins`. Правится
одной строкой: **все плагины объявляются в корне с версией и `apply false`**, даже
если применяются в одном модуле. Правило записано в корневом файле, чтобы не
наступить снова.

### Ограничение, о котором надо знать: 60 запросов в час

API GitHub без токена даёт **60 запросов в час на адрес**. Я опрашивал прогоны
слишком часто и квоту исчерпал: сброс через ~40 минут. Виновата не платформа, а моя
частота опроса — по несколько запросов на проверку.

Вывод на будущее, он же способ работы дальше: **один запрос на проверку, не чаще
раза в две минуты.** Этого хватает: прогон идёт 3–6 минут.

Токен решил бы и это, и главное — дал бы доступ к логам (сейчас 403). Но просить
секрет ради удобства не стоит: диагностика через аннотации работает, а частоту
опроса я исправил.

## К1.4 — спайк дал ответ, и он плановый

**⚠ РЕШЕНИЕ ЗАКАЗЧИКА. Это главный результат дня.**

Спайк задавал один вопрос: поедут ли зависимости крипто на iOS. Ответ получен на
первой неделе — ровно там, где он и должен был найтись.

| Зависимость | Роль | Артефакты Apple |
|---|---|---|
| **Kodium** | NaCl: SecretBox, Box, Ed25519, HKDF | **есть** (iosArm64, iosSimulatorArm64, iosX64, macOS) |
| **Wire runtime** | конверт и тело сообщения (protobuf) | **есть** |
| **KyberKotlin** (`asia.hombre:kyber`) | **ML-KEM-768 для escrow** | **нет ни одного** |
| **keccak** (SHAKE, зависимость Kyber) | внутренность ML-KEM | **нет ни одного** |

Проверено листингом Maven Central, а не предположено: у `kyber` опубликованы
`androidnative*`, `js`, `jvm`, `linuxx64`, `mingwx64`, `windows` — и ничего Apple.
Сборка падала на «Unresolved platforms: [iosArm64, iosSimulatorArm64]».

**Чем это плохо.** Escrow не опция: каждое исходящее сообщение оборачивает ключ
сообщения на ключ эпохи escrow через ML-KEM. Значит **iOS не может отправить ни
одного сообщения**, пока у ML-KEM нет провайдера под Apple. Это отсутствие
обязательного слоя, а не нехватка удобства.

**Чем это хорошо.** Комментарий в `messenger-crypto` обещал у KyberKotlin «поддержку
KMP» — обещание не подтвердилось, и узнали мы это в К1, а не на гейте К2, и не в
К4, когда на iOS начали бы отправлять сообщения.

### Варианты и их цена

| Вариант | Суть | Цена | Инварианты |
|---|---|---|---|
| **A. Вендорить исходники** KyberKotlin и keccak в `messenger-crypto` и собирать самим под все таргеты | тот же код → **те же байты** | ~163 КБ чужого кода под нашим присмотром; отслеживать правки апстрима вручную | целы: провайдер один, реализация та же |
| **B. Форкнуть и публиковать свои артефакты** с таргетами Apple | тот же код, чистая зависимость | инфраструктура публикации; сборка Apple-таргетов — на бесплатном раннере macOS | целы |
| **C. Второй провайдер только для iOS** через expect/actual (CryptoKit ML-KEM, BoringSSL через cinterop) | не трогаем существующее | **две реализации одного примитива**; CryptoKit требует iOS 18+, а канон обещает 15+ | **нарушает** «один провайдер на примитив» |
| **D. Попросить автора опубликовать таргеты Apple** | ноль работы | срок неизвестен, зависит от чужой воли | целы |

**Рекомендую A**, с D как параллельным письмом (оно бесплатно). Причина: тот же код
даёт те же байты, а значит тест-векторы остаются доказательством, а не надеждой.
B отличается от A только тем, где лежит код, и добавляет инфраструктуру. C — единственный
вариант, который трогает инварианты, и брать его стоит только если A и B невозможны.

**Что сделано, пока решения нет:** KyberKotlin вынесен в `jvmMain` спайка. Спайк
доказывает, что две из трёх зависимостей работают на iOS, а третья названа блокером
в коде — чтобы это не выглядело красной сборкой без объяснения.

### Заодно: архитектурные правила зелёные

Задача `архитектурные правила` прошла — включая проверку, которая **обязана поймать**
образец нарушения. То есть правила не просто настроены, а работают.

## К1.9 — пустые приложения

Написаны входы для ПК (`app-desktop`) и Android (`app-android`): окно Compose,
обращение к `core-model`. Пусто по замыслу — задача этапа доказать, что тулчейн
собирается, а не показать интерфейс. Интерфейс приезжает в К5, из дизайн-системы.

Обращение к `ChatId` в обоих входах неслучайно: оно проверяет, что общий модуль
**виден** из приложения, то есть граф зависимостей собран, а не только объявлен.

### Одно решение из инвентаря оказалось преждевременным

Пункт 13 (ABI) я сначала записал как развилку для вас — и это было поспешно.
В v1 стоял `abiFilters = arm64-v8a`, потому что WebRTC и zstd тянут нативные
библиотеки под все ABI и раздувают APK; следствием был неработающий эмулятор
x86_64.

**В v2 нативного кода пока нет вовсе, поэтому ограничивать нечего**, и ограничение
не введено: эмулятор работает. Вопрос возвращается **в К2**, когда приедет zstd, и
решается тогда осознанно — например, все ABI в отладочной сборке и один в релизной.
Так решение принимается тогда, когда у него есть предмет.

Пункты 14 (стабильная подпись APK) и 15 (исключения при слиянии ресурсов) записаны

## Что это значит для К2: блокеров два, и они одной природы

ML-KEM — не единственная зависимость без артефактов Apple. Разбор (**рассуждение, не
прогон**; проверяется в К2):

| Что нужно на iOS | Откуда брать | Состояние |
|---|---|---|
| ML-KEM-768 (`kyber` + `keccak`) | Maven | **артефактов Apple нет** — проверено листингом |
| zstd | системная библиотека | **в iOS SDK zstd нет.** Apple отдаёт `libcompression` с zlib, LZFSE, LZ4, LZMA — zstd там отсутствует |

То есть `libzstd` придётся **собирать под iOS самим** и везти в приложении: cinterop
разберёт заголовок, но линковка требует библиотеки, собранной под нужный триплет.
Homebrew даёт сборку под macOS, а не под iOS-симулятор.

**Вывод, который упрощает решение:** оба блокера — «зависимость не опубликована под
Apple, собери сам». Механизм, который завели для одного, закрывает и второй. Это
довод в пользу варианта A (вендорить и собирать самим) — он один раз ставит конвейер
сборки чужого кода под Apple, вместо двух разных обходных путей.

**Что не сделано намеренно:** спайк на cinterop к zstd не запускался. Ответ выводится
из состава iOS SDK, и жечь цикл CI ради подтверждения того, что и так известно,
незачем. Проверка приедет вместе с настоящей задачей в К2.

## Поиск готовых решений: один блокер снят, второй подешевел

### zstd — снят готовой библиотекой, проверено прогоном

`com.squareup.zstd:zstd-kmp` **0.4.0** (Apache 2.0, без зависимостей) публикует
`iosArm64`, `iosSimulatorArm64`, `iosX64`, `android`, `jvm`, `macos*`, `linux*`,
`mingwX64`, `tvos*`. **Спайк прошёл на iOS-симуляторе** (`a030764`, все пять задач
зелёные): round-trip, степень сжатия, и главное — отказ на бомбе.

Собирать `libzstd` под iOS самим не нужно. Побочно снимается костыль v1: там
исключали jar `zstd-jni` и подключали отдельный `@aar`, потому что в jar не было
Android-нативов (пункт 15 инвентаря). Здесь есть `zstd-kmp-android`.

**И упрощение плана:** одна библиотека на все таргеты означает, что **expect/actual
для zstd не нужен вовсе**, хотя канон (`tech-stack.md`) требует «expect/actual
биндинги». Требование отпадает — надо поправить документ.

**Что меняется в коде, и это правка про безопасность.** API низкоуровневый и
потоковый (`ZSTD_compressStream2`, `ZSTD_decompressStream`), one-shot нет и
**`getFrameContentSize` нет**. Защита от zstd-бомбы поэтому меняется:

| Было в v1 | Будет в v2 |
|---|---|
| спросить у кадра заявленный размер → сверить с 16 МиБ → распаковать | распаковывать потоково и падать при превышении потолка **на выходе** |

Новый способ **строже**: заголовок кадра может врать или отсутствовать
(`ZSTD_CONTENTSIZE_UNKNOWN`), а фактический выход не обманешь. Черновик обёртки и
три теста лежат в спайке (`ZstdKmpSpikeTest`), в К2 переезжают в `messenger-crypto`.

### ML-KEM — готового нет, но блокер оказался дешевле

Проверено: **ни одной KMP-реализации ML-KEM с таргетами Apple нет.**

| Кандидат | Итог |
|---|---|
| `org.kotlincrypto.*` | только хеши, MAC, sponges — KEM отсутствует |
| `dev.whyoleg:cryptography-kotlin` 0.6.0 | операции: хеш, MAC, подпись, AEAD, симметрика, шифрование с открытым ключом, согласование, деривация. **KEM в списке нет** |
| BouncyCastle | JVM-only, уже наш оракул на JVM |

**Зато вот что нашлось в исходниках KyberKotlin и KeccakKotlin:**

```kotlin
    linuxX64()
    mingwX64()
    //iosArm64()
    //iosX64()
    //iosSimulatorArm64()
    androidNativeArm32()
```

**Таргеты Apple просто закомментированы.** Обе библиотеки уже собираются под
Kotlin/Native (linux, mingw, androidNative) — значит дело не в переносимости кода, а
в том, что для публикации klib под Apple нужен Mac, которого у автора, судя по всему,
нет.

Это меняет цену: вариант A (вендорить и собирать самим) — не «портировать чужую
криптографию», а **раскомментировать три строки и собрать**. Риск падает с «может не
собраться вовсе» до «может не сойтись в поведении», а последнее ловится векторами.

### Про оракул на iOS — ответ уже есть, и он лучше второй реализации

Мысль верная: сверять не с чем. BouncyCastle только на JVM.

Но для iOS второй реализации и не нужно: `schema/test-vectors` **порождены внешними
реализациями** (`tweetnacl-js`, `@noble/post-quantum`), то есть уже являются
независимым оракулом — и они платформонезависимы. Прогнать их на iOS-симуляторе мы
теперь умеем.

Разделение получается такое:

| Что проверяем | Чем |
|---|---|
| алгоритм верен | BouncyCastle на JVM (как сейчас) + KAT-векторы от сторонних реализаций |
| **Kotlin/Native ведёт себя как JVM** | те же векторы, прогнанные на iOS-симуляторе |

Второе — единственное, что добавляется на iOS, и вектора для этого достаточно:
расхождение в беззнаковой арифметике или переполнении даст другой байт, а вектор
этого не пропустит.

**Оговорка из ADR-0005 остаётся в силе:** вектор `mlkem768_escrow` не поймал бы
перестановку `d` и `z`, потому что в нём все 64 байта одинаковы. Значит при переносе
нужен вектор с `d != z` — он там уже требовался, и это отдельный пункт К2.

### Поправка: про Mac для публикации я ошибся

Написал выше, что таргеты Apple закомментированы, «потому что для публикации klib
нужен Mac». **Это неверно, проверено.**

В Kotlin Gradle Plugin есть свойство `kotlin.native.enableKlibsCrossCompilation`, и в
исходниках плагина оно читается как `booleanProperty(...) ?: true` — то есть
**включено по умолчанию**. Для чистого Kotlin-кода klib под Apple собирается и на
Linux, и на Windows.

Mac обязателен для другого:

| Нужен Mac | Не нужен Mac |
|---|---|
| линковка итоговых бинарей Apple (framework, исполняемый файл) | сборка klib библиотеки |
| прогон тестов на симуляторе и устройстве | публикация артефактов |
| cinterop к заголовкам Apple SDK | |

Похоже, автор отключил не то, что нельзя собрать, а **то, что нельзя проверить**:
рядом закомментирован и `linuxArm64()`, который кросс-компилируется так же.

**Что из поправки следует полезного.** Вариант D (PR автору) становится не просьбой,
а предложением помощи: у него нет Mac для проверки, а у нас есть бесплатные раннеры
macOS. К PR можно приложить результат прогона тестов на симуляторе — то, чего он сам
получить не может.

И уточнение цепочки: раскомментировать нужно в **двух** репозиториях, `KyberKotlin` и
`KeccakKotlin`. Третья зависимость, `org.kotlincrypto.random:crypto-rand`, таргеты
Apple **уже публикует** — проверено листингом.

### Бит исполнения сломал прогон в третий раз

Задача «форки крипто · iOS» упала на `./gradlew: Permission denied`. Причина та же,
что у `messenger-crypto/gradlew` утром: git на Windows не хранит бит исполнения, файл

Это ровно тот случай, когда правило дешевле памяти: помнить про бит после каждого

### Форки: keccak на iOS прошёл, kyber упал на спрятанном файле

- **`KeccakKotlin` → `iosSimulatorArm64Test` — зелёный.** То есть SHAKE-слой ML-KEM

Починка — четвёртая правка форка: игнор снят. Секрета в файле нет, строку подписи мы
