# Ключи LiveKit: где лежат и куда ставятся

Заведён 2026-09-19 по просьбе заказчика — при разборе С0 («проверить сервер через
`livekit-cli` без телефона»). Без ключей CLI в комнату не войдёт, а где они лежат, нигде
записано не было.

**Секретов здесь нет и не будет.** Здесь — только где их взять и куда положить.

---

## Что это за ключи

Пара `LIVEKIT_API_KEY` / `LIVEKIT_API_SECRET`. Ими подписываются токены доступа в комнату.
**Важно, что пара одна на двоих:**

| Кто | Зачем ему ключ |
|---|---|
| **LiveKit SFU** | проверяет подпись токена, с которым к нему пришли (`livekit.yaml`, секция `keys`) |
| **Наш бэкенд** | выпускает эти токены (`server/internal/calls/token.go`, переменные окружения) |

Разойдутся — бэкенд выдаст токен, который SFU не примет, и звонок не начнётся ни у кого.
Поэтому в шапке `livekit.yaml` стоит предупреждение, и оно не формальное.

## Где они лежат на стенде

Два файла, оба **вне git**:

| Файл | Что в нём |
|---|---|
| `/root/tima2/server/deploy/.env` | `LIVEKIT_API_KEY=…` и `LIVEKIT_API_SECRET=…` — отсюда их берёт бэкенд |
| `/root/tima2/server/deploy/livekit/livekit.yaml` | секция `keys:` — `<ключ>: <секрет>`, отсюда их берёт SFU |

Прочитать на стенде:

```bash
grep LIVEKIT /root/tima2/server/deploy/.env
sed -n '/^keys:/,/^$/p' /root/tima2/server/deploy/livekit/livekit.yaml
```

**В репозитории их нет.** В `livekit.yaml` стоят заглушки `REPLACE_LIVEKIT_API_KEY` и
`REPLACE_LIVEKIT_API_SECRET`, в `.env.example` — подсказка, чем их сгенерировать
(`openssl rand -hex 16` и `-hex 32`). Проверка после любого обновления:
`grep -c REPLACE livekit.yaml` должен дать **0** — она записана во всех записях
`ВЕРСИИ/СТЕНД.md`, потому что `git pull` перезаписывал этот файл заглушками.

## Куда они ставятся у того, кто проверяет

`livekit-cli` берёт их из переменных окружения или из своего файла проекта.

```bash
export LIVEKIT_URL=wss://<домен стенда>/livekit
export LIVEKIT_API_KEY=<ключ>
export LIVEKIT_API_SECRET=<секрет>

lk room list                       # проверка, что ключ принят
lk token create --join --room проба --identity проверка --valid-for 1h
lk room join --publish-demo проба  # войти вторым участником
```

Второй путь, если проверок много: `lk project add` сохраняет URL и пару под именем, и
дальше команды идут с `--project <имя>`. Файл ложится в профиль пользователя
(`~/.livekit/`), **не в репозиторий**.

**Адрес.** SFU слушает `7880`, но снаружи он за Caddy: в `Caddyfile` стоит
`handle /livekit/*`. То есть для CLI адрес — `wss://<домен>/livekit`, а не порт напрямую:
порт 7880 в файрволе закрыт, открыты только UDP-диапазон медиа и TURN.

## Чего делать нельзя

**Не класть ключи в репозиторий** — ни в `livekit.yaml`, ни в скрипты, ни в отчёты.
Файл `livekit.yaml` отслеживается git и уезжает на все машины; заглушки `REPLACE_` в нём
не небрежность, а защита.

**Не выпускать токены в обход бэкенда для чего-либо, кроме проверок.** Токен, выписанный
руками, не знает наших правил: кто с кем может говорить, какая комната кому принадлежит.
Для С0 это допустимо и на то он и С0; в продукте токены выдаёт только
`POST /api/v1/calls`.

**Не менять ключи без пересборки обоих.** Смена пары требует правки и `.env`, и
`livekit.yaml`, и перезапуска обоих контейнеров. Порядок — в
[ПЕРЕУСТАНОВКА-СЕРВЕРА.md](../ПЕРЕУСТАНОВКА-СЕРВЕРА.md).

## Если ключей нет вовсе

Бэкенд это переживает и говорит прямо: `/calls` отвечает **503 `no_livekit`**, а в журнале
при старте появляется «LIVEKIT_API_KEY/SECRET не заданы — /calls отвечает 503»
(`cmd/tima/main.go`). То есть «звонки не работают» отличимо от «сервер не поднялся», и
первым делом при разборе стоит посмотреть именно эту строку.
