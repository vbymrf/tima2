> сломано. Ключ подписи анклава — то, ради чего к серверу идут сейчас, — берётся
> без всякого стирания.

> **Сверено с кодом и живым стендом 2026-08-21.** Сошлось: имя проекта `tima`,
> все семь имён томов, путь `deploy/docker-compose.prod.yml`, наличие `deploy/.env`,
> `psql -U tima -d tima`, пять долей Шамира при пороге три, формат
> `tima-escrow-share-v1:`, строка анклава про ключ подписи конфига. Исправлено
> четыре расхождения — они помечены ниже словом «Поправка».

Инструкция для того, кто выполняет обновление на боевом сервере. Читать целиком
до начала: процедура **необратимая**.

Составлено 2026-08-14. С 2026-08-14 рабочая ветка — `stand`; разворачивают с
неё, а развёрнутый коммит помечают тегом `deploy/ГГГГММДД-NN`.

## Что это и зачем

Обычное обновление ([РАЗВЕРТЫВАНИЕ.md](arhiv/РАЗВЕРТЫВАНИЕ.md), «Обновление сервера»)
пересобирает код и накатывает миграции поверх существующих данных. Здесь другое:
**база, медиа и ключи анклава стираются полностью**, сервер поднимается на
чистом месте.

Так решено сознательно. Накопленные данные — тестовые, схема за последние
итерации менялась много раз, и переносить нечего. Чистая установка снимает целый
класс вопросов «а не осталось ли чего-то от прежней схемы».

### Что будет потеряно навсегда

| | |
|---|---|
| Все аккаунты и личности | восстановлению не подлежат |
| Все ключи устройств | у каждого клиента придётся регистрироваться заново |
| Вся переписка — личная, групповая, каналы | шифртекст без ключей бесполезен, но и он стирается |
| Все медиафайлы | и метаданные в базе, и блобы в MinIO |
| Ключи escrow и журнал аудита анклава | прежние `escrow_blob` не расшифруются никогда |
| Секретные фразы | останутся у людей на руках, но восстанавливать ими будет нечего |

**Отката нет.** Ни на каком шаге. Если через час выяснится, что данные были
нужны, вернуть их будет неоткуда.

### Почему это допустимо сейчас и не будет допустимо потом

Клиенты — тестировщики, и все они знают, что делают. Это последний момент, когда
полное стирание стоит дёшево.

С появлением людей, которые не в курсе, вступает в силу правило из
[ПРАВИЛА-РАБОТЫ.md](ПРАВИЛА-РАБОТЫ.md): **сервер обязан работать со старым
клиентом**. Настоящая процедура его нарушает намеренно и является
**однократным исключением, а не образцом**. Ссылаться на неё в следующий раз
нельзя.

## Перед началом

**1. Убедиться, что все согласны.** После этого шага у каждого тестировщика
пропадёт аккаунт. Предупредить заранее, а не по факту.

**2. Проверить, что берётся нужный коммит.** Ветка `stand`. Записать точный
хеш — он понадобится и в отчёте, и в теге развёртывания:

```bash
cd /opt/tima && git fetch && git log --oneline -1 origin/stand
```

**3. Понять, что нового едет.**

> **Поправка 2026-08-21.** Здесь стоял список из трёх миграций — `0027`…`0029`. Он
> был верен на 14 августа и с тех пор устарел дважды: эти три **уже применены** на
> стенде (29 из 29 на коммите `3c491bb`), а сверх них появилась `0030`. Список
> номеров в инструкции гниёт при каждой миграции, поэтому его здесь больше нет —
> вместо него команда, которая всегда верна:

```bash
# что применено на стенде
docker exec tima-postgres-1 psql -U tima -d tima \
    -tAc "select count(*), max(name) from schema_migrations"
# что есть в коде
ls server/migrations/*.sql | tail -3
```

Разница между этими двумя ответами и есть «что нового едет». Прочитать сами файлы
разницы — это и будет понимание, а не пересказ.

Плюс серверная правка, о которой стоит знать: **отозванное устройство теперь
теряет доступ немедленно.** Раньше `revoked_at` ставился, но JWT продолжал
работать до истечения (до суток). Теперь аутентифицированные маршруты требуют
живую запись устройства.

**4. Никаких резервных копий не делать.** Сохранённая копия базы с чужими
ключами и телефонами — это риск, а пользы от неё в этой процедуре нет. Если
копия зачем-то нужна — это другая задача, решать её до, отдельно и осознанно.

## Порядок

Все команды — на сервере, из `/opt/tima`.

### Шаг 1. Остановить всё

```bash
cd /opt/tima/server
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env down
```

Без `-v` — тома пока целы. Стирать будем прицельно и по одному, чтобы не задеть
лишнее.

### Шаг 2. Забрать код

```bash
cd /opt/tima
git fetch
git checkout stand
git pull --ff-only
git log --oneline -1        # записать хеш
```

`--ff-only` намеренно: если он отказал, на сервере есть локальные изменения, и
разбираться с ними надо до, а не в процессе.

### Шаг 3. Стереть данные

Именно эти четыре тома, поимённо:

```bash
docker volume rm tima_postgres-data     # база
docker volume rm tima_minio-data        # медиафайлы
docker volume rm tima_escrow-data       # состояние анклава escrow
docker volume rm tima_redis-data        # шина событий и лимиты
```

Имена томов привязаны к имени compose-проекта `tima`. Перед удалением сверить их
с `docker volume ls`; если префикс отличается, подставить имена из его вывода, а
не угадывать.

**Про `escrow-data` отдельно.** Там живут seed анклава, соответствие
«область → идентификатор ключа» и журнал аудита. Стереть базу и оставить анклав
нельзя: реестр `escrow_keys` в базе — это кэш, а источник истины у анклава.
Разъехавшись, они дадут расхождение нумерации, и понять это будет трудно.

**Чего НЕ трогать:**

| Том | Почему остаётся |
|---|---|
| `pii-data` | ключ и pepper персональных данных. Стирать незачем: данных, которые ими зашифрованы, всё равно не останется. Терять — лишний риск испортить настройку |
| `caddy-data`, `caddy-config` | сертификаты TLS. Стереть — заново проходить выпуск и упереться в лимиты Let's Encrypt |

### Шаг 4. Поднять

```bash
cd /opt/tima/server
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env up -d --build
```

Первый старт бэкенда прогонит миграции `0001`…`0030` на пустой базе. Это дольше
обычного — подождать.

> Число миграций сверено 2026-08-21: `0030_delivery_retention.sql` добавлена в тот
> же день. Если здесь снова окажется меньше, чем в `server/migrations/`, — верно то,
> что в каталоге.

### Шаг 5. Забрать новые доли Шамира

С новым томом `escrow-data` анклав создаёт новый unlock-секрет и печатает ровно
пять строк `tima-escrow-share-v1:...`. Это единственная выдача: повторный
запуск их не покажет, а без трёх из пяти нельзя выполнить unseal.

```bash
docker compose -f deploy/docker-compose.prod.yml logs escrow-stub \
  | grep 'tima-escrow-share-v1:'
```

Сохранить все пять строк **вне сервера и вне репозитория**: передать
держателям долей или поместить в согласованное защищённое хранилище. Не
вставлять их в командную историю, журнал деплоя, issue или чат.

Только после подтверждения, что все пять строк сохранены, продолжать.

### Шаг 6. Проверить

> **Поправка 2026-08-21: API живёт на поддомене `api.`, а не на корневом домене.**
> Здесь стояло `https://<домен>/healthz`. Проверено сегодня: корневой домен отдаёт
> **404**, `api.<домен>` отдаёт **200**. То есть прежняя команда провалилась бы и
> прочиталась как «выкатка не удалась». Поддомены заведены DNS-записями
> `api.`, `s3.`, `lk.` — [arhiv/РАЗВЕРТЫВАНИЕ.md §1](arhiv/РАЗВЕРТЫВАНИЕ.md).
>
> Домен интернационализированный, поэтому в `curl` едет **punycode**, а не
> кириллица.

```bash
docker compose -f deploy/docker-compose.prod.yml ps        # все сервисы healthy
curl -s https://api.<домен>/healthz                        # {"status":"ok"}
docker compose -f deploy/docker-compose.prod.yml logs backend | tail -50
```

В логах бэкенда искать:

- применение миграций до `0030` включительно, без ошибок;
- строку анклава `escrow-stub: ключ подписи конфига (Ed25519, ...)`.

**Проверить, что анклав отвечает:**

```bash
curl -s https://api.<домен>/api/v1/escrow/pubkey
```

Ответ `503` означает, что `ESCROW_URL` не задан или анклав не поднялся. С таким
состоянием отправка сообщений работать не будет: escrow обязателен на каждом
сообщении.

**Проверить, что база действительно чистая:**

```bash
docker compose -f deploy/docker-compose.prod.yml exec postgres \
  psql -U tima -d tima -c "select count(*) from persons; select count(*) from devices;"
```

Оба счётчика должны быть нулевыми. Ненулевые — старый том не стёрт, начинать
заново с шага 1.

### Шаг 7. Поставить тег развёртывания

> **Поправка 2026-08-21: этого шага в инструкции не было.** Тег упоминается дважды
> — в шапке и в «Перед началом» («хеш понадобится в теге развёртывания»), — а шага,
> который его создаёт, не было ни одного. Из этого и вышло, что на развёрнутом
> `3c491bb` тега нет: неподвижной записи о выкатке не существует, только таблица в
> `arhiv/СТЕНД.md`. Откатываться в такой ситуации некуда.

```bash
# на машине разработки, не на сервере
git tag -a deploy/ГГГГММДД-NN <хеш> -m "<содержимое блока из СТЕНД.md>"
git push origin deploy/ГГГГММДД-NN   # удалённый называется origin, не tima2
```

`NN` — порядковый номер выкатки за день. Тег **аннотированный**, потому что в него
кладётся состояние: коммит, уровень миграций, кем и когда. Заодно обновить
`arhiv/СТЕНД.md`: расходится с тегом — **верен тег**.

Порядок обязателен: **сервер поднят и проверен, только потом клиенты.**

> **Поправка 2026-08-21: этот раздел писался про клиента v1, которого больше нет.**
> Дерево `client/` удалено (этап К0.4), исходники v1 остались только тегом
> `ref/client-v1`, а v2 ещё не выпускалась. Значит «собрать и раздать новый APK»
> сейчас выполнить нечем, и до К4 этот раздел не действует. Развёрнутый клиент —

1. **Собрать и раздать новый APK.** Старая сборка не знает про объявление
   платформы и не сможет подтверждать привязку по QR.
2. **Каждый тестировщик регистрируется заново.** Прежний вход не сработает:

всего снести данные приложения на телефоне и каталог `~/.tima` на ПК — иначе
клиент будет пытаться открыть кэш ключами, которых больше нет.

## Отчёт о выполнении

По правилу из [ПРАВИЛА-РАБОТЫ.md](ПРАВИЛА-РАБОТЫ.md) результат обязан называть
коммит. Написать в свободной форме:

- хеш коммита, на котором поднят сервер;
- дата и время;
- дошли ли миграции до последней, что есть в `server/migrations/` (номер не зашивать: он меняется);
- ответил ли `/healthz`;
- ответил ли `/api/v1/escrow/pubkey` (или `503` — и почему);
- нулевые ли счётчики `persons` и `devices` после старта;
- что пошло не так, если пошло.

Без хеша отчёт бесполезен: неизвестно, что именно проверено.

## Если что-то пошло не так

**Миграции упали.** Смотреть, на какой именно, в логах бэкенда. Не пытаться
править базу руками — снести том и начать с шага 3: она всё равно пустая, терять
нечего.

**Бэкенд не стартует, в логах база недоступна.** Postgres не успел подняться.
Перезапустить только бэкенд: `up -d backend`.

**`/healthz` отвечает, но клиенты не регистрируются.** Проверить логи на предмет
`ESCROW_URL` — без анклава регистрация проходит, а отправка сообщений нет.

**Сомнение в любой момент.** Остановиться и спросить. Данных, которые можно
потерять неправильным решением, здесь уже нет, а времени — сколько угодно.

## Обновление, а не переустановка

**Решение 2026-08-21.** Для первого сквозного сообщения (К4) сервер **обновляется**
по [arhiv/РАЗВЕРТЫВАНИЕ.md](arhiv/РАЗВЕРТЫВАНИЕ.md) («Обновление сервера»), а не
переустанавливается. Причина не в осторожности, а в том, что переустановка здесь
ничего не даёт и кое-что отнимает.

**Что нужно от сервера сейчас:** накатить `0030_delivery_retention.sql` (аддитивная:
вставка двух строк в `retention_policy`) и пересобрать бинарь. Это ровно обычное
обновление.

**Что нужно от анклава:** его публичный ключ подписи конфига, чтобы зашить в клиент.
И вот главное, что стоит знать: **этот ключ печатается при КАЖДОМ старте анклава и
не меняется между перезапусками** — сид лежит в его state-файле
(`server/internal/escrow/escrow.go`, `loadOrCreateSigningKey`). Однократная выдача —
это про **доли Шамира**, а не про ключ подписи. Значит ключ берётся из журнала без
какого-либо стирания:

```bash
docker compose -f deploy/docker-compose.prod.yml logs escrow-stub \
  | grep 'ключ подписи конфига'
```

Формат в журнале — **base64url без выравнивания**, 32 байта. Он же зашивается в
`EscrowTrust.enclaveSigningPub` (`client/core/core-encryption`). Не секрет: печатать
и хранить в репозитории клиента можно и нужно — на нём держится проверка того, что
ключ эпохи escrow не подменён бэкендом.

**Чего стоила бы переустановка.** Новый том `escrow-data` — это новый unlock-секрет,
то есть **новые пять долей Шамира**, а вот они выдаются однократно: прежние
становятся бесполезны, и держателям нужно передать новые. Плюс новый ключ подписи
(значит зашивать всё равно новый), плюс чистая база. Ни одна из трёх потерь ничего
не покупает: отправка сообщений пока не работает, `escrow_blob` в базе нет, терять
нечего и незачем.

**Когда переустановка всё-таки нужна.** Три случая, и только они:

| Состояние | Что делать |
|---|---|
| Анклав работает | обновить сервер, ключ забрать из журнала. Переустановка не нужна |
| Анклав остановлен, том `escrow-data` на месте | поднять сервис; ключ и доли те же, что были |
| Тома `escrow-data` нет или состояние непонятно | анклав поднимется на чистом месте: напечатает пять долей и ключ. **База при этом не трогается** — стирать её ради анклава не надо |

Иначе говоря, полное стирание из этого документа — процедура для случая «схема
разошлась, данные тестовые, начинаем заново», а не для «нужен ключ анклава».

**Проверить, в каком из трёх состояний сервер**, до всяких решений:

```bash
curl -s https://api.<домен>/api/v1/escrow/pubkey     # 503 → анклав не отвечает
docker compose -f deploy/docker-compose.prod.yml ps  # есть ли escrow-stub и здоров ли
docker volume ls | grep escrow-data                  # существует ли том
```

**2. `server/deploy/livekit/livekit.yaml` правится НА МАШИНЕ, и это не мусор.** В
репозитории он лежит с заглушками (`REPLACE_LIVEKIT_API_KEY`,
`REPLACE_TURN_DOMAIN`), а на стенде в него подставлены настоящие ключи LiveKit и
домен TURN. Переключение ветки или `git checkout --` по этому файлу **сотрёт ключи**,
и звонки перестанут работать — причём выглядеть это будет как поломка LiveKit, а не
как потеря конфигурации.

Отсюда порядок для будущего обновления: сохранить файл вне репозитория, переключить
ветку, вернуть файл, только потом пересобирать. И то же про `deploy/.env` — рядом с
ним лежат пять его резервных копий `.env.bak-*`, значит так уже делали.

### Ключ подписи анклава

Берётся без перезапуска — анклав печатает его при каждом старте:

```bash
cd /opt/tima/server
docker compose -f deploy/docker-compose.prod.yml logs escrow-stub \
  | grep 'ключ подписи конфига'
```

Формат — base64url без выравнивания, 32 байта; не секрет. Место в клиенте —
`EscrowTrust.enclaveSigningPub` (`client/core/core-encryption`). До того как он там
появится, клиент не отправит ни одного сообщения: отказ закрытый.

> **Доли Шамира читать и печатать нельзя** — они выдаются однократно и являются
> секретом. Команда выше берёт **только** строку ключа подписи.
