## §2. Дельта: не «переписать» и не «рефакторить», а **достроить**

Новое ТЗ само формулирует требования к бэкенду —
[интерфейс.md §11](../doc/интерфейс.md) «Что обязан уметь бэкенд», и там честно
сказано: «что из этого уже есть в API и схеме — вопрос к коду». Сверка сделана.

**Чего в схеме нет вовсе** (проверено по `CREATE TABLE` во всех 29 миграциях):

| Отсутствует | Где требуется по ТЗ |
|---|---|
| `chat_folders` — **разделы и каталог** | §3–§6: полоса разделов, гармошка, счётчики по разделу — сквозная механика всех окон |
| `comments` | §4, §5, §9 «Комментарии»: ветки, вложенность, эмоции на комментарий |
| `reactions` / `emotions` | §2, §4–§6: шкала девяти эмоций, «настроение» от −1 до +1, «+/−» |
| `posts` (общая лента) | §4: записи ленты; сейчас есть только `channel_posts` |
| `subscriptions` (общие) | §4, §7: подписки и подписчики; сейчас только `channel_subscriptions` |
| `feeds` | §4, §5: общая лента и лента друзей |

| `notifications` | §9 «Настройки»: три уровня, тихие часы |
| `invites` | §12: QR и инвайт-ссылки |
| `reports` | модерация |
| `bots` | Bot API |
| коллекции, истории, псевдонимы | §5–§8 |

**Вывод.** Существующее ядро — это фаза 1 (личное общение) плюс каналы и голосовые
комнаты. **Весь социальный слой нового ТЗ серверной части не имеет.** Значит:

- «переписать заново» — заплатить второй раз за то, что работает, и **заново
  заслуживать доверие к крипто-части**: 118 тестов, эпохи escrow, цепочка
  идентификаторов, канонические байты, сверка с BouncyCastle. Это месяцы и риск
  молчащей поломки;
- «рефакторить» — неверное слово: рефакторить нечего, отсутствующего кода не бывает;
- **«достроить»** — то, что действительно требуется: добавить социальный слой рядом,
  сверив по ходу существующее.

## §3. Инварианты — не обсуждаются

Взяты из [server-compatibility](../.cursor/rules/server-compatibility.mdc) и
[crypto-invariants](../.cursor/rules/crypto-invariants.mdc), нарушение любого стоит
дороже всей карты:

1. **Миграции аддитивные, применённые не правятся.** База пересоздаётся, но привычка
   «поправить старую миграцию» станет опасной ровно тогда, когда её уже не отследить.
2. **API только расширяется. Сервер раньше клиента.** И клиент обязан переживать
   отсутствие поля: нет значения — нет функции, а не блокировка.
3. **Крипто, конверт, эпохи escrow, цепочка идентификаторов, канонические байты — не
   трогаем.** Оплачено, проверено, застыло в отправленных данных.
4. **«Проверено» относится к коммиту**, а не к ветке.

**Работаю последовательно, а не на два фронта.** Причина в утверждённом решении 5:
пока v2 не отправит первое сообщение, формат и API — единственное заведомо верное. Если
одновременно менять контракт и строить клиент, упавшее сообщение перестаёт что-либо
означать.

Поэтому: **С1 и С2 сейчас** (они ничего не меняют — только измеряют и включают
проверку), **С3 по мере надобности клиента**, **С4 и дальше — после К4**.

## §8. Первая сверка со стендом · 2026-08-20

Проверено по адресу, который дал заказчик (IP, без домена):

| Проверка | Результат | Вывод |
|---|---|---|
| порт 80 | открыт, `HTTP 308` на HTTPS | Caddy жив, конфигурация на месте |
| порт 443 | TCP встаёт | сервис слушает |
| TLS по IP | алерт `internal_error` (80), и с `-k` тоже | сертификата для IP нет и быть не может — Caddy отдаёт его по имени |
| переадресация с 80 | ведёт на тот же IP | домена в ответе нет |

**Стенд работает, но адресуется только по доменному имени.** Для С1.2 нужен домен —
тот, что стоит в `DOMAIN=` его `.env`.

**Обходить это отключением проверки сертификата не буду.** Клиент, умеющий не
проверять TLS, — это клиент, у которого однажды не проверят TLS; а `serverUrl` в TIMA
вводится человеком вручную, то есть проверка сертификата — единственное, что отличает
настоящий сервер от подставленного.

### Регистрация тестовых аккаунтов: разобрано по коду

`TIMA_DEV_SMS` выключен, и это блокирует auth-водопровод К4. Как устроено
(`server/internal/api/auth.go:102`):

- **с флагом** — код возвращается в ответе `POST /api/v1/auth/sms/request`, поле
  `dev_code`;
- **без флага** — код уходит **только в лог сервера**; в таблице `sms_codes` лежит
  `hashCode(requestID, code)`, то есть из базы его не восстановить.

Значит вариантов ровно два: включить флаг (одна строка, работает в автотестах) или
читать лог по SSH при каждом входе (в автотестах непригодно). Запрошено включение;
оговорка про то, что при этом регистрация открыта любому знающему домен, записана в
`doc_add`.
