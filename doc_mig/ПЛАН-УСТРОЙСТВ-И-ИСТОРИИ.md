# План: доверие к устройствам и история на новом устройстве — Б

Заведён 2026-10-02 по решению заказчика после разбора ключей. Две беды одного корня: **устройство
в аккаунте ничем не подтверждено**, и **новое устройство не получает прежнюю переписку** («на ПК
не видно чатов с телефона»).

Родственное: [ADR-0010](../doc/adr/0010-history-recovery-multidevice.md) — восстановление истории,
[ADR-0014](../doc/adr/0014-identity-chain.md) — цепочка личности,
[ADR-0017](../doc/adr/0017-group-key-rotation.md) — смена ключа группы,
[key-lifecycle.md](../doc/03-security/key-lifecycle.md), [ПЛАН-КЛЮЧЕЙ-ГРУПП.md](ПЛАН-КЛЮЧЕЙ-ГРУПП.md),
[ПЛАН-ВЫХОДА-ИЗ-АККАУНТА.md](ПЛАН-ВЫХОДА-ИЗ-АККАУНТА.md) — вход по QR,
[ДОРОЖНАЯ-КАРТА.md](ДОРОЖНАЯ-КАРТА.md) К5.1б–К5.1г.
Перед правкой `messenger-crypto/**`, `core-encryption`, `schema/**` — `.cursor/rules/crypto-invariants.mdc`.

## 0. Как устроено сейчас (по коду, 2026-10-02)

| Ключ | Сколько | Откуда | Где закрытая часть | Для чего |
|---|---|---|---|---|
| Ключ личности | один на аккаунт | из фразы, 12 слов (`AccountMnemonic.kt`) | нигде: выводится из фразы на время подписи | «это я, хозяин аккаунта»: восстановление, перенос |
| Ключи устройства | пара на устройство: шифрование X25519, подпись Ed25519 | устройство само, случайно (`DeviceIdentity.kt`) | на устройстве | получать зашифрованное, подписывать своё |
| Ключ группы | один на версию группы | участник при смене (`GroupKeyManager.kt`) | у участников | сообщения группы |

- **Шифруем ключами устройств.** Ключ сообщения упаковывается для каждого устройства получателя и
  своих других устройств (`PersonalMessageSealer.kt`); сообщение подписано ключом устройства.
  Ключ личности в шифровании не участвует.
- **Устройство никто не одобряет.** `/auth/register`: код SMS и открытые ключи — устройство сразу
  рабочее. Ключ личности при регистрации необязателен; не прислан — проверка совпадения не
  делается вовсе (`store/identities.go:150`).
- **Клиенты верят списку устройств сервера** (`Sender.kt:166`, `Receiver.kt:954`, `GroupKeyRotation.kt`):
  нет ни подписи устройств, ни знания ключа личности собеседника, ни предупреждения о смене.
- **Отсюда:** укравший SIM регистрирует устройство без фразы и получает **новые** личные
  сообщения сразу, ключ группы — при следующей смене. Старая история закрыта: её восстановление
  подписывается фразой. Взломанный сервер может подложить своё устройство так же.
- **Новое устройство** получает только новые сообщения и список групп; личных чатов не видит до
  следующего сообщения в них; старых сообщений не получает ни личных, ни групповых — в первом
  приложении это было, в новое не перенесено (К5.1в «не начато»; экран QR сам предупреждает:
  «Прежняя переписка туда не переедет», `Words.kt:3360`).
- **Отзыв устройства не меняет ключ группы:** сервер шлёт причину `device_revoked`, которую сам не
  принимает (`groups.go:460`); клиент делает из неё плановую смену, а плановую сервер отклоняет
  без новых сообщений и чаще 15 минут.

## 1. Решения заказчика (2026-10-02)

| Р1 | **Ключи устройств из мастера (HKDF) не выводим.** Ключи устройств случайные и независимые; доверие даёт обязательная подпись, а не вывод |

| Р6 | **Переход сразу строгий** (1б): клиенты собеседников не шифруют для неподписанного устройства; мягкого режима с предупреждениями не будет. Момент включения — настройкой сервера (Р24) |

| Р13 | **«Присоединить прежний аккаунт»** — этапом плана (ДУ7): нашёлся прежний телефон — возврат к прежней личности и её группам |
| Р14 | **Подтверждение личности в группе меняет ключ группы**, а не передаёт текущий (перенос-аккаунта §6) |
| Р15 | **Уведомления «у контакта новое устройство» нет** — новое устройство видно только в списке устройств владельца |
| Р16 | **Документ «Перенос аккаунта на новое устройство» правится** в части 4 вместе с ADR-0010 и `key-lifecycle.md` |

| Р18 | **Аттестация включается настройкой сервера, настройка есть всегда**; на стенде выключена (проверочные боты на ПК её не пройдут) |
| Р19 | **Аттестация — элемент защиты «на потом»** (ДУ8): сейчас не реализуется, но части 2 закладываются так, чтобы потом её включить, а не переписывать, и чтобы старые клиенты не отвалились |
| Р20 | **Свой ключ аттестации:** телефон заводит в чипе отдельный ключ P-256 с аттестацией (Android 8+) и подписывает им открытые ключи устройства. Наши ключи (Ed25519, X25519) и `KodiumPrivateKey.fromRaw` не меняются |
| Р21 | **Настройка сервера — три положения:** выключено (поле не смотрим; стенд), записывать (проверяем и пишем, не отказываем), требовать (отказ без аттестации) |
| Р22 | **Клиент Android собирает и присылает аттестацию с первой версии ДУ1**; на рабочем сервере — «записывать»: видно, какие телефоны и прошивки проходят |
| Р23 | **Шаг вызова от сервера (challenge) в регистрации — сейчас, вместе с ДУ1**: без случайного числа сервера аттестацию можно переиграть, а добавить шаг потом — снова сломать старые клиенты |
| Р24 | **Строгость по подписям устройств (Р6) включается настройкой сервера, а не выпуском клиента:** сначала клиенты присылают подписи, потом сервер и клиенты начинают их требовать. Общее правило: **клиент начинает присылать задолго до того, как сервер начнёт требовать** |
| Р25 | **Отпечатки подписи APK для аттестации:** пока идёт отладка, и на стенде, и на рабочем сервере разрешены оба — отладочный ключ и ключ выпуска; список — настройкой сервера (1б) |
| Р26 | **Один чат — склейкой на телефоне** (1а, 2026-10-02): идентификатор личного чата по-прежнему из пары личностей (`PersonalChatId` не меняется); сервер отдаёт цепочку «новая личность — продолжение прежней», телефон показывает старый и новый чат одним со строкой «сменил ключ личности», новые сообщения идут в новый |
| Р27 | **«Начать заново» — без задержки:** заводится новая личность, привязывается к тому же аккаунту (номер, ник, профиль). **Прежнее устройство может отменить новую личность** — она удаляется из системы (её устройства отзываются, прежняя личность снова текущая); вор остаётся только с тем, что успел написать сам. Аккаунт один, меняются личности |
| Р28 | **Живая проверка строгого режима на стенде — разрешена** (3а): подтвердить фразой телефоны, заверить ПК, включить `require`, проверить отказ вору; вернуть `record` можно в любой момент |
| Р29 | **Отменить новую личность можно в любой момент**, пока живо прежнее устройство (1а) |
| Р30 | **Сообщения отменённой личности остаются у собеседников** с пометкой «личность отменена владельцем» (2а) |
| Р31 | **Отмена подтверждается фразой** на прежнем заверенном устройстве (3б): заверенность устройства плюс подпись ключом личности |
| Р32 | **Уже подключённое устройство заверяется только по QR** (1б): оно показывает код заверения, телефон с ключом подписи устройств сканирует; кнопка «Заверить» по строке списка убирается — список приходит от сервера, и по нему можно заверить и устройство вора |
| Р33 | **Перенос истории на новое устройство — как сделано** (б, 2026-10-05): доверенное устройство перезаворачивает ключи личных сообщений через сервер (ИУ2), новому достаётся то, что моложе срока хранения обёрток — 90 дней (`delivery_retention_days`). Отвергнуты: (а) вся история пакетом из местной базы телефона, зашифрованным под новое устройство; (в) хранить обёртки до срока ключа депозитария — около 7 месяцев |
| Р34 | **Перерегистрация при компрометации и смена SIM — две заявки и подтверждение через 3 месяца** (2026-10-05). «Перерегистрация» (фраза + SMS) сразу заводит новую личность с новой фразой и отзывает все выданные заверения; встречная «Аккаунт украден — заблокируйте доступ к моей личности» (фраза + SMS) снова отзывает их и запрещает новые. Через 3 месяца в окне длиной месяц исход решает подтверждение: пришло от одной стороны — удаляется другая личность, от обеих — срок продлевается (без предела), ни от кого — новая личность удаляется. Заявки — только после входа, с телефона с ключом личности; SMS — всегда на прежний номер. Смена SIM — по той же схеме, новая SIM нужна только для подтверждения. Порядок — §2б, этап ДУ9 |

## 2а. Устройство ДУ1–ДУ3 (решено при работе, 2026-10-02)

**Ключи.** Промежуточный ключ аккаунта — «ключ подписи устройств» (далее КПУ) — Ed25519, случайный,
порождается телефоном. **У аккаунта их может быть несколько — по одному на телефон**: телефон,
вошедший по фразе, выпускает свой КПУ; закрытые ключи никуда не переезжают (перенос-аккаунта §3).
Телефон, привязанный по QR, подписан КПУ подтвердившего, но своего КПУ не имеет — получит его,
когда человек введёт на нём фразу.

**Что подписывается** (UTF-8, ключи — base64url без выравнивания; Go и Kotlin байт в байт):

| Подпись | Кто подписывает | Байты |
|---|---|---|
| Свидетельство КПУ | ключ личности (фраза) | `tima.ask.v1\|<ask_pub>` |
| Свидетельство устройства | КПУ **или** ключ личности (вход по фразе без телефона, например ПК) | `tima.device.v1\|<encryption_pub>\|<signing_pub>` |
| Отзыв КПУ (ДУ4) | ключ личности | `tima.ask-revoke.v1\|<ask_id>` |

`user_id` в байтах нет: при заведении аккаунта его ещё нет, а к аккаунту свидетельство привязывает
подписавший ключ — ключ личности у аккаунта свой. Свежести (вызова сервера) здесь не нужно:
свидетельство привязано к открытым ключам устройства, и повтор чужого свидетельства заводит
устройство, закрытых ключей которого повторяющий не имеет. Вызов от сервера (Р23) понадобится
аттестации — им станет `registration_token`.

**Сервер.**
- Таблица КПУ аккаунта (`account_signing_keys`): ключ, свидетельство, телефон-держатель, отзыв.
- У устройства: кем подписано (`identity` / `ask`), каким КПУ, подпись.
- `POST /auth/register` — новые необязательные поля: КПУ со свидетельством, свидетельство устройства.
- `POST /users/me/signing-keys` — телефон, на котором ввели фразу, выпускает свой КПУ.
- `PUT /devices/{id}/certificate` — подписать своё другое устройство (КПУ этого телефона или фразой).
- `POST /link/confirm` — новое необязательное поле: свидетельство нового устройства от КПУ
  подтверждающего.
- `GET /keys/devices` — новые поля: ключ личности, действующие КПУ со свидетельствами, у каждого
  устройства — его свидетельство, и **режим доверия** сервера.
- **Режим доверия — настройка `TIMA_DEVICE_TRUST`** (Р24): `off` — не смотрим; `record` —
  проверяем и пишем в журнал, не отказываем; `require` — регистрация в аккаунт с фразой без
  годного свидетельства — отказ, аккаунт без фразы — отказ (Р7), клиенты не шифруют для
  неподписанных устройств (Р6). Стенд начинает с `record`: устройства, заведённые до ДУ1,
  подписей не имеют, и строгий режим отрезал бы их до того, как человек введёт фразу.

**Клиент.**
- Регистрация с фразой (новый аккаунт, вход по фразе, «Начать заново»): фраза в руках — телефон
  выпускает КПУ и подписывает им себя, ПК подписывает себя ключом личности.
- Подтверждение QR: телефон с КПУ подписывает новое устройство.
- Устройство, заведённое до ДУ1: «Устройства» → «Подтвердить фразой» — телефон выпускает свой КПУ;
  дальше он подписывает другие свои устройства **по выбору человека**, а не всё подряд из списка
  сервера — иначе вместе со своими подписалось бы и устройство вора.
- Проверка у собеседника: ключ личности запоминается при первой встрече (смена — ДУ6);
  устройство доверено, если его свидетельство сходится с ключом личности или с действующим КПУ,
  а свидетельство КПУ — с ключом личности. В `require` недоверенному не упаковываются ни ключ
  сообщения, ни ключ группы, и его подписи не принимаются; в `record` — пишется в журнал.

## 2б. Перерегистрация при компрометации и смена SIM (Р34, ДУ9)

Решено заказчиком 2026-10-05 в разговоре. Обозначения: **С** — прежняя личность, её фраза
**Ф1**; **Н** — новая, её фраза **Ф2**. **Устройство с фразой** — то, у которого есть ключ
личности: ключом личности заверяется телефон, телефон заверяет ПК.

**Где подаются.** Только изнутри приложения: «Секретная фраза и устройства» на телефоне с ключом
личности. Не войдя, подать их нельзя. Вход по фразе (в прежнюю личность, ДУ7) заявку не заменяет
и не отменяет: сначала вход, потом заявка.

**SMS — всегда на прежний номер (SIM 1)**: и перерегистрация, и «Аккаунт украден». Новая SIM
(SIM 2) участвует в одном — подтверждении смены номера через 3 месяца, если встречных заявок не
было.

**Две заявки, обе — фраза и SMS на номер аккаунта.**

| Заявка | Запуск | Что происходит сразу | Подтверждение |
|---|---|---|---|
| **Перерегистрация** (заводит Н) | Ф1 + SMS | Н с новой фразой Ф2 становится текущей. **Все выданные заверения отзываются**: работают только устройства с ключом личности. Встречной заявки нет — Н заверяет свои устройства как обычно | Ф1 + Ф2 + SMS |
| **«Аккаунт украден — заблокируйте доступ к моей личности»** (С) | Ф1 + SMS | Бывает **только встречной**: кто-то запустил перерегистрацию на себя, то есть удаление моей личности. Выданные заверения снова отзываются, **заверять нельзя никому**, новую личность завести нельзя. У обеих сторон работают только устройства с ключом личности; ПК не работает | Ф1 + SMS |

**Срок и окно.** Ожидание — 3 месяца от запуска. Затем окно подтверждения длиной **1 месяц**.
Исход — по тому, кто подтвердил за окно:

| Пришло за окно | Исход |
|---|---|
| только от Н | удаляется С |
| только от С | удаляется Н |
| от обоих | ничего не меняется, срок продлевается ещё на 3 месяца и новое окно — **без предела** |
| ни от кого | удаляется Н — возврат к тому, что было до запуска |

Удаление Н — извещение «ваш аккаунт будет удалён через месяц: можно повторить процедуру или
создать совсем новый» и удаление через месяц (стандартная процедура).

**Кто что видит.** Обе стороны — «идёт спор за аккаунт до <дата>, подтвердите». Собеседники —
только причину строкой. Больше ничего.

**Почему спор кончается.** Обе заявки и оба подтверждения требуют SMS, а SIM в каждый момент у
одного. Встречная заявка означает, что телефон за срок побывал у обоих; к окну он снова у одного —
он и решает.

**Смена SIM — по той же схеме.**
1. Заявка — номер аккаунта перерегистрируется на новую SIM.
2. Всем устройствам аккаунта — извещение «меняется телефон».
3. Через 3 месяца — подтверждение: фраза + SMS на новую SIM, если встречных заявок не было.
4. «Это не вы» — с устройства запускается **перерегистрация** по схеме выше (SMS — на прежний
   номер); кто её запустил, тот и Н.
5. Пришла заявка «Аккаунт украден» — снова отзываются выданные заверения и запрещаются новые.

**«Начать заново» в Р34 — не процедура, а выбор в извещении**: проигравшая или удаляемая сторона
может бороться за аккаунт (повторить заявку) или создать совсем новый.

## 6. Переход

Решено (Р6, Р7): строго сразу, аккаунт без фразы — отказ. Ниже — разбор вопросов заказчика,
решений по нему нет.

Вопросы заказчика 2026-10-02, ответы — в разговоре, решения нет:

- **Прочитает ли клиент свои сообщения после правок.** Сообщения зашифрованы ключами устройств,
  а не личности; подпись устройств их не трогает — уже работающие устройства читают всё, что
  читали. Им нужна только подпись: устройство, получившее промежуточный ключ по фразе, подписывает
  остальные свои устройства (подтверждение «это мои устройства» или QR).
- **Не отрежем ли доступ.** Устройство со старой версией подписи не получит; как только клиенты
  собеседников начнут отказывать неподписанным (ДУ3), оно перестанет получать новые сообщения до
  обновления. Отсюда предложение: сначала мягкий режим — подписи собираются, неподписанным пишем
  предупреждение, но шифруем; строгий — когда подписаны все устройства живых аккаунтов.
- **Аккаунты без фразы** (на стенде 35 из 49, все старые): при входе — завести фразу (сервер
  позволяет установить личность, если её нет), а не отказ.
