## Зачем

R8 — оптимизатор байткода при сборке: встраивает, выкидывает неиспользуемое, сжимает. Быстрая
сборка сейчас без него, и всё равно втрое быстрее отладочной; R8 — следующий шаг:

- **Объём кода.** В быстром APK четыре dex на 38 МБ (11,3 + 10,4 + 12,7 + 4,0). На слабом телефоне
  загрузка и проверка классов и компиляция по профилю стоят пропорционально объёму.
- **Compose.** Правила самой библиотеки вырезают служебные вызовы (`sourceInformation`, трассировку)
  из каждой составной функции — но только под R8.
- Руководство Compose прямо требует R8 для скорости; у чужих приложений — заметно быстрее холодный
  старт (цифры Google — чужие, у нас надо мерить).

## Что делаем

**Р1. Включить** в виде сборки `fast` (отладочная не трогается):

```kotlin
create("fast") {
    initWith(getByName("debug"))
    signingConfig = signingConfigs.getByName("debug")   // явно: отпечаток 5877a0b5…
    isDebuggable = false
    isJniDebuggable = false
    isProfileable = true          // Perfetto и simpleperf на не отладочной
    isMinifyEnabled = true
    isShrinkResources = true
    proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"), "proguard-rules.pro")
    versionNameSuffix = "-v2-fast"
    matchingFallbacks += listOf("release")
}
```

**Р2. Правила** — новый `client/app-android/proguard-rules.pro`:

```
# Имена не переименовывать: журнал и отчёты пишут имена классов, стек падения читается без карты.
# Оптимизация и выкидывание неиспользуемого при этом остаются.
-dontobfuscate
-keepattributes SourceFile,LineNumberTable,*Annotation*,InnerClasses,Signature
# zstd-kmp: натив находит классы и поля по имени (FindClass, inputBytesProcessed,
# outputBytesProcessed), своих правил у библиотеки нет. Без этого R8 может счесть поля
# неизменяемыми и подставить 0 — тогда не отправится и не прочитается ни одно сообщение.
-keep class com.squareup.zstd.** { *; }
```

Остальное — **только** `-dontwarn` из `build/outputs/mapping/fast/missing_rules.txt`, каждое прочитав.
Свои правила уже несут: LiveKit (WebRTC JNI, protobuf), kotlinx-serialization, CameraX, ZXing.
Без отражения: SQLDelight, Ktor с явным движком OkHttp, Wire, Kodium (с 2026-10-29 и ML-KEM — форков Kyber и Keccak больше нет),
kotlincrypto. BouncyCastle в APK не едет. Отражения в коде клиента нет.

**Р3. Карта.** `mapping.txt` при `-dontobfuscate` почти пуст, но класть его рядом с
`TIMA-N-fast.apk` — на случай, если правило изменится.

## Чем проверить (модульные тесты R8 не видят)

Прогон по телефону с быстрой сборкой — по одному на поломку каждого вида:

| Что | Что ловит |
|---|---|
| запуск, вход | база, ключи |
| «Чаты», переписка, отправить и получить | сериализация, **zstd**, шифрование |
| звонок, личный и групповой | LiveKit, WebRTC JNI |
| сканер QR | CameraX, ZXing |
| проверка обновления со стенда | установщик, сверка подписи |
| «Сообщить о проблеме» | журнал, отправка |
| `adb logcat` | `ClassNotFound`, `NoSuchMethod`, `NoSuchField`, `UnsatisfiedLink`, `JNI DETECTED ERROR` |

Сценарии Maestro работают и на не отладочной сборке (метки элементов от отладки не зависят); не
работают только шаги через `run-as`.

**Замер** на Redmi: быстрая без R8 против быстрой с R8 — прокрутка «Звонков», переход «Телефон» →
«Стенд», холодный запуск (`am start -W`), размер APK. Выигрыша нет — R8 не нужен, план закрывается
с этим итогом.

## Риски

- Поломка, которую видно только в редком пути (звонок по видео, восстановление по фразе), — список
  проверки выше её не поймает. Поэтому быстрая с R8 **не раздаётся стендом** так же, как без него.
- Подпись: только общий `debug.keystore` (`5877a0b5…`). `keystore/tima-release.jks` для `io.tima.app.v2`
  не подключать — другой сертификат сломает обновление на месте.

автоматическим прогоном на телефоне; имеет смысл после R8.
