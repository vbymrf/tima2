# План: Звонки на ПК

Заведён 2026-09-26 по решению заказчика. ПК привязан вторым устройством к аккаунту Redmi,
и выяснилось: «На ПК нет возможности использовать веб камеру и микрофон. Сделай план».

Статус: **обсуждается**. Кода по плану нет. Это развёртка клеток К7.1 и К7.3
[ДОРОЖНОЙ-КАРТЫ](ДОРОЖНАЯ-КАРТА.md) — маршрут в них до сих пор не выбран
([ПЛАН-ЗВОНКОВ](ПЛАН-ЗВОНКОВ.md), вопрос З-В6).

## 0. Как сейчас

Проверено по коду и живым прогоном 2026-09-26 (сборка 2.0.83-dev на ПК, 83 на телефонах).

**Звонков на ПК нет вовсе — ни микрофона, ни камеры, ни звука.** Дело не в разрешениях:
на ПК нет самого движка звонка.

| Что | Где | Как |
|---|---|---|
| Движок | `app-desktop/…/Main.kt` | `Root(...)` вызывается без `callEngine` → `null` |
| `CallEngine` для ПК | `core-call/src/jvmMain` | нет. Там четыре пустышки: доступ, строка «идёт звонок», замер нагрузки, отчёт стенда |
| Разрешения | `Access.jvm.kt` | `askCallAccess` → сразу `true`, `callAccessState` → «не знаю» (строк в «Разрешениях» нет) |
| Видео | `feature-call/…/CallVideo.jvm.kt` | пустое место |
| Зависимости | `core-call/build.gradle.kts` | у ПК нет ничего медийного; `livekit-android` только у Android |
| Кнопки «позвонить» | `CallHost.possible` = `engine != null` | на ПК скрыты везде — позвонить с ПК нельзя |

**Что при этом ПК делает с входящим — живой прогон samsung → Redmi + ПК:**

| Проверка | Итог |
|---|---|
| Звонит на обоих устройствах | ✅ Redmi — уведомление с «Ответить»; ПК — окно звонка и мелодия |
| Ответ на Redmi гасит ПК | ✅ ПК: `CALL ответили на другом устройстве`, окно закрылось |
| Пропущенный снимается на всех по «просмотрено» | ❌ → починено `1d6dca46`, перепроверено живьём: вкладка «Звонки» на ПК сняла пропущенный в шторке Redmi (см. §0б) |
| «Принять» на ПК | ❌ **кнопка есть и ничего не делает**: `accept()` начинается с `engine ?: return`. Звонящий слушает гудки до 50-й секунды, в журнале ПК ни строки |
| «Перезвонить» в окне конца на ПК | ❌ кнопка есть, звонить нечем |
| Имена в журнале звонков ПК | «Без имени» у всех строк: книга контактов на новое устройство не переехала. К звонкам на ПК не относится — отмечено, чтобы не потерять |

### 0б. Попутная находка — починена

Звонящий кладёт трубку своим сторожем на той же 50-й секунде, что и сервер, и чаще
успевает первым. Запись становится «отменён», шторка вызываемого по `cancelled` всё равно
ставит «пропущенный», а вкладка «Звонки» слала «просмотрено» только за `missed` — строка
висела на прочих устройствах. Починено `1d6dca46` (`CallsStore.missedNotice`, тест
`открыли_вкладку_просмотр_уходит_и_за_отменённый_звонящим`).

Осталось расхождение слов: **в журнале такой звонок — «отменён», в шторке — «пропущенный»**.
Это развилка 3 в §4.

## 2. Маршруты — что известно на 2026-09-26

Предпочтение A → C → B ставилось, когда вопрос был «как ПК доберётся до LiveKit». Сейчас
он конкретнее: **микрофон и камера**. Под этим углом маршруты расходятся сильнее, чем
казалось.

| | **A. LiveKit Rust SDK (`livekit-ffi`) через JNA** | **C. Встроенный Chromium (KCEF) + `livekit-client` JS** | B. `webrtc-java` + свой сигналинг |
|---|---|---|---|
| Привязка к JVM | **готовой нет.** `livekit-ffi` — запросы и события protobuf через одну функцию и обратный вызов; обёртку пишем сами. `livekit-uniffi` (Kotlin) — экспериментальный и покрывает только журнал и токены | готовая библиотека `compose-webview-multiplatform` поверх KCEF | готовые биндинги |
| Захват микрофона | **наш**: SDK принимает готовые кадры (`NativeAudioSource`). Микрофон — `javax.sound.sampled` из JDK | Chromium (`getUserMedia`) | биндинги |
| Звук собеседника | **наш**: кадры из `NativeAudioStream` → `javax.sound` | Chromium | биндинги |
| Камера | **наша**: в JDK API нет — библиотека или Media Foundation через JNA | Chromium | биндинги |
| Эхоподавление | **главный риск**: без него ПК с колонками даёт эхо. Есть ли обработка WebRTC (APM) в `livekit-ffi` — проверить в К7.1 | Chromium | биндинги |
| ADR-0006 | протокол их; **захват, вывод и эхо — наши**, то есть часть качества медиа уходит к нам | не нарушает: всё медиа у Chromium и LiveKit | нарушает прямо |
| Вес | нативная библиотека FFI + libwebrtc | **целый Chromium**; сейчас MSI ≈ 84 МБ (сборка 2.0.13) — прибавку измерить | libwebrtc |
| Окно звонка | наш Compose, как на Android | веб-страница внутри окна; состояние — мостом Kotlin ↔ JS | наш Compose |

**Вывод, который надо подтвердить замером:** A сохраняет единый Compose-интерфейс, но
микрофон, камеру и эхо заставляет делать нас. C даёт всё медийное даром ценой веса и
моста к JS. Поэтому **предлагаю мерить C первым**, а A — вторым (развилка 1).

Источники: [livekit/rust-sdks](https://github.com/livekit/rust-sdks),
[livekit-uniffi](https://github.com/livekit/rust-sdks/tree/main/livekit-uniffi),
[compose-webview-multiplatform, desktop](https://github.com/KevinnZou/compose-webview-multiplatform/blob/main/README.desktop.md).

## 3. Срезы

### ПК0. Честный ПК, пока движка нет — сейчас, малый

Сегодня ПК обещает то, чего не умеет. Чинится без выбора маршрута.

- Входящий на ПК: окно звонка и мелодия остаются (человек видит, кто звонит), но вместо
  «Принять» — строка «На ПК звонки пока не работают — ответьте на телефоне». «Отклонить»
  остаётся.
- В окне конца звонка на ПК нет «Перезвонить».
- Журнал: `CALL` «на этом устройстве звонков нет — показан без „Принять“». Без записи
  «нажал и ничего» не отличить от зависания.
- Условие одно — `callHost.possible`, а не «это ПК»: появится движок — кнопки вернутся
  сами.

### ПК1. Замер маршрутов (К7.1)

Два опытных образца на этой машине, каждый — звонок ПК ↔ Android через наш стенд. Мерится
одно и то же:

| Мерка | Как |
|---|---|
| Голос в обе стороны | живой звонок с samsung |
| Эхо через колонки | ПК без наушников, говорит телефон |
| Картинка с веб-камеры у собеседника и обратно | видеозвонок |
| Прибавка к MSI и к памяти в звонке | размер сборки; диспетчер задач |
| Время до первого звука после «Принять» | журнал обеих сторон |
| Переподключение при обрыве сети | выдернуть сеть на 10 с |
| Выбор микрофона и камеры, если их несколько | вручную |
| Объём кода | строки обёртки |

Итог — отчёт в `doc_mig/отчёты`, выбор делает заказчик. Проигравший образец удаляется,
а не остаётся «на потом».

### ПК2. Движок на выбранном маршруте (К7.3)

`CallEngine` для ПК, `Main.kt` передаёт его в `Root`. Контракт `core-call` не меняется:
экраны не знают маршрута (Plan.md §3.8). Ограничитель §3.8.1 остаётся — ни битрейта, ни
таймаутов ICE в контракте.

### ПК3. Микрофон и камера в «Разрешениях» ПК

На Windows доступ даёт не приложение, а «Параметры → Конфиденциальность → Микрофон /
Камера → Разрешить классическим приложениям». Когда он выключен, захват молчит без
ошибки. Поэтому:

- `callAccessState` на ПК отвечает по факту — есть ли устройство и отдаёт ли оно звук или
  кадр; `null` («не знаю») больше не возвращается;
- «Открыть настройки» ведёт на `ms-settings:privacy-microphone` и
  `ms-settings:privacy-webcam`;
- в «Разрешениях» ПК появляются строки «Микрофон» и «Камера» — те же `PermissionRow`, что
  на телефоне;
- в журнал идёт `CALL-DEVICE`: устройства нет или Windows не дала доступа. Запись в
  [РЕЕСТР](ЖУРНАЛ-И-ОТЛАДКА/РЕЕСТР.md) — по [ПРАВИЛУ](ЖУРНАЛ-И-ОТЛАДКА/ПРАВИЛО.md).

### ПК4. Видео на ПК

`CallVideo.jvm.kt` рисует кадры — свои и собеседника. Вид окна — как на Android: свой
кадр малым окном в углу.

### ПК5. Раздача

MSI с новыми нативными частями (WiX, `WIX_HOME`), версия по [ВЕРСИИ](ВЕРСИИ/КЛИЕНТЫ.md).
Вес MSI — в отчёт.

### ПК6. Живая проверка

- звонок Android → ПК и ПК → Android, голос и видео;
- ПК вторым устройством: ответ на ПК гасит телефон, и наоборот;
- эхо без наушников;
- доступ к микрофону выключен в Windows → «Разрешения» ПК это показывают.

## 4. Развилки — решает заказчик

1. **Порядок замера: C (Chromium) первым или A (Rust SDK), как в Plan.md?** Предлагаю C:
   микрофон, камера и эхо там готовые, а у A это наша работа. Решение правит Plan.md §3.8.
2. **ПК0 делать сейчас, до выбора маршрута?** Предлагаю да — это малый срез, а сегодня
   «Принять» на ПК оставляет звонящего слушать гудки.
3. **Звонок, отменённый сторожем звонящего на 50-й секунде: в журнале «отменён», в шторке
   «пропущенный».** Предлагаю у вызываемого писать в журнале «пропущенный» для любого
   неотвеченного входящего, будь то `missed` или `cancelled` после 50 с. Для человека
   разницы нет, он просто не ответил.
