## 0. Зачем

Три требования, вокруг которых собран весь рефакторинг:

1. **Метаданные храним всегда и в открытом виде.**
2. **Персональные данные скрываем.**
3. **Ключи живут ограниченный срок, и срок — настройка, а не константа.**

Отсюда главная идея: **разделить сроки жизни трёх вещей, склеенных сейчас в одной
строке таблицы.**

| Плоскость | Что | Срок | Видимость |
|---|---|---|---|
| Метаданные | кто-кому-когда-какого типа | вечно | открыто, но псевдонимно |
| Контент | текст, медиа | пока жив нужный ключ | шифртекст |
| Личность | телефон ↔ идентификатор, имя | пока живёт аккаунт | под ключом |

Связывает крипто-шреддинг: истёк срок ключа — контент недоступен, метаданные целы.

## 1. Принятые решения

| № | Решение |
|---|---|
| 1 | Модель угроз для персональных данных — **утечка базы или бэкапа**, не компрометация хоста |
| 2 | Escrow — **только для ордеров**. Пользователю недоступен; потерял ключи — потерял переписку |
| 3 | Удаление пользователем — **пометка**, не стирание. Физически стираем, когда аккаунт удалён / чат в архиве **и** уничтожен escrow-ключ периода |
| 4 | Escrow-ключ — на пару **«чат × эпоха»**, генерируется лениво при первом сообщении чата в эпохе |
| 5 | Срок ключа = длина эпохи + срок по закону = **1 месяц + 6 месяцев = 7 месяцев** |
| 6 | Состояния аккаунта: **временный / постоянный / архивный**. Постоянный по неактивности не удаляется никогда |
| 7 | Аккаунт — **цепочка идентификаторов**. Текущий тот, чьи ключи доказуемы |
| 8 | Связка идентификаторов без подписи прежним ключом — собеседник видит **предупреждение о смене личности** |
| 9 | **Key-commitment делаем**, конверт версии 2 |
| 10 | Звонки: **в работу LiveKit не вмешиваемся**. Реализуем только групповые звонки |
| 11 | Ключ персональных данных — **отдельно от базы**, за одним интерфейсом. Отдельный сервер — позже |
| 12 | Содержимое сообщения — **массив узлов + разметка**, без якорей и смещений; разметка приватного шифруется; блоки в обоих контурах, профили возможностей обязательны ([ADR-0011](../../doc/adr/0011-message-content-model.md)) |
| 13 | Данные текущей базы **выбрасываемые**: база пересоздаётся с нуля, сохранять и переносить нечего |

## 2. Швы, которые режем сразу

Дёшевы сейчас, дороги потом. Не требуют ни второго сервера, ни шардирования.

1. **`key_id` рядом с каждым шифртекстом** — иначе первая же ротация упрётся в «каким ключом это зашифровано». ✅ сделано в Р1а.
2. **Регион в реестре escrow-ключей**, пусть значение пока одно.
3. **`chat_id` как единственный ключ разбиения** — ни одна функция не должна требовать запроса по всем чатам сразу.
4. **Ключи только за интерфейсом или по адресу** — у escrow уже так (`ESCROW_URL`), у персональных данных сделано в Р1а.
5. **Миграции остаются append-only.** База пересоздаётся, но правку прошлых миграций не делаем: через несколько недель появятся живые данные, и привычка «поправить старую миграцию» станет опасной ровно тогда, когда её уже не отследить.

## 3. Найденные нестыковки и как разрешены

Сверка сведённого плана, 2026-07-30.

| Нестыковка | Разрешение |
|---|---|
| **Р1а закоммичена, но не выкачена.** В бою последняя миграция `0016`, 6 пользователей, 9 сообщений | Данные выбрасываемые (решение 13): база пересоздаётся с нуля, backfill на живых данных не нужен |
| **`BackfillPII` и двухрелизный переход** проектировались, чтобы не потерять существующие строки | При пересоздании базы переносить нечего. Backfill удалён, открытые колонки убирает `0018` сразу |
| **«Эпоха × регион × шард» против «ключ на чат × эпоха»** — выбирали одно, уточнили до другого | Ключ на чат **тоньше** шарда и его отменяет. Реестр — `(регион, эпоха, chat_id)`. Шард, если понадобится, останется только операционной группировкой, а не границей изоляции |
| **«Р3 и Р5б выпускать вместе, потому что обе трогают формат»** | Неточно. Key-commitment меняет подписываемые байты конверта; узлы и разметка живут **внутри** зашифрованной нагрузки и добавляются аддитивно. Технически независимы; вместе — только чтобы сэкономить цикл выкатки клиента |
| **Имя «Фаза 1» занято** продуктовой дорожной картой | Этапы рефакторинга названы Р0…Р6 |
| **`phone_bidx` нельзя делать `NOT NULL`**, хотя на чистой базе соблазн есть | Временные аккаунты заводятся **без телефона** (`key-lifecycle.md` §7, решение 6). Ограничение пришлось бы снимать через две недели. Колонки остаются nullable, уникальность — частичным индексом |
| **Уникальность номера** сейчас `WHERE phone_bidx IS NOT NULL`, по документации нужна `WHERE deleted_at IS NULL` | Меняется в Р4, когда появится состояние «архивный». Условие записано в комментарии `0017` |
| **Защита `ResetForTests`** требует суффикса `_test`; боевая база называется `tima` | Совпадений нет, защита работает. Проверено |

### Р2 — escrow-эпохи (осталась валидация escrow_key_version на приёме)

**Анклав:**
- [x] Связка ключей: ключ на пару «чат × эпоха», хранится отдельным файлом
- [x] **Независимые seed'ы** — никакой деривации из общего корня
- [x] Ленивая генерация: ключ появляется при первом обращении к области
- [x] Уничтожение по сроку: физическое удаление файла + запись в аудит
- [x] Автоматический проход уничтожения по таймеру, а не по кнопке
- [x] `POST /v1/key`, `GET /v1/keys/{id}`, `POST /v1/unseal-scoped`
- [x] Ордер со scope: наружу только ключи сообщений, приватный ключ — никогда
- [x] Срок ключа = конец эпохи + срок по закону (покрывает и последний день эпохи)
- [x] Ключ подписи Ed25519 (отдельный от ML-KEM): генерируется при инициализации,
      переживает перезапуск, дозаписывается в состояния, заведённые раньше этого поля
- [x] `/v1/pubkey`, `/v1/key`, `/v1/keys/{id}` подписывают ответ этим ключом

**Бэкенд:**
- [x] Реестр `escrow_keys` (миграция `0020`): публичные части + `destroy_at` для гейта Р4
- [x] `GET /escrow/key?chat_id=` — ключ области, лениво через анклав, с кэшем в реестре
- [x] Перекрытие эпох: у границы отдаётся и следующий ключ
- [x] Регион как измерение, значение пока одно
- [x] Миграция `0025`: колонка `signature` в реестре; подпись анклава пробрасывается
      клиенту неизменной и на пути через анклав, и из кэша реестра
- [x] [ADR-0012](../../doc/adr/0012-escrow-key-epochs.md)

**Клиент:**
- [x] Выбор ключа по чату вместо legacy-ключа; кэш до конца окна валидности
- [x] Групповой ключ депонируется на ключ эпохи своей группы
- [x] Подпись конфига анклавом и проверка клиентом (иначе компрометация бэкенда даёт подмену ключа)
- [ ] Валидация `escrow_key_version` на приёме — после того, как все клиенты перейдут

**Найдено при выполнении подписи:** обсуждали TOFU («запомнить ключ анклава при
первом обращении») — отклонили. `serverUrl` вводится пользователем вручную
(`Session.serverUrl`), поэтому доверие, укоренённое в первом ответе ТОГО ЖЕ
сервера, ничем не отличалось бы от доверия бэкенду напрямую — ровно та дыра,
которую подпись должна закрывать. Решение: ключ анклава — константа
(`EscrowTrust.ENCLAVE_SIGNING_PUBLIC_KEY` в клиенте), приезжающая с сборкой
приложения, а не по сети; несовпадение — жёсткий отказ, без мягкого
переукоренения. Сейчас константа `null` — реальный прод-анклав ещё не
развёрнут, зашить туда нечего; анклав печатает свой публичный ключ подписи в
лог при каждом старте (`escrow-stub: ключ подписи конфига`), оператор
подставит его в клиент перед сборкой релиза. До этого момента проверка честно
пропускается — не регресс (подписи не было нигде до этой правки), но
незакрытый пункт разворачивания.

Формат конверта не ломается: `escrow_key_version` становится суррогатным идентификатором записи реестра.

> **Найдено при выполнении хвоста:** оба пункта в документации (ДОКУМЕНТАЦИЯ/02 §2,
> §5, §8) описаны через QR — новый телефон показывает код, старый его сканирует и
> подписывает. Но привязка устройства по QR ранее отложена (ФАЗА-1-СТАТУС.md):
> нужна камера, протокол сессии линковки, и это непроверяемо без двух живых
> устройств. Реализовывать untested security-критичный флоу — риск больше пользы.
>
> Разрешение: подпись из **секретной фразы** криптографически неотличима от подписи
> «живым» устройством — тот же ключ, та же проверка `ed25519.Verify`. Реализован
> путь «ввести фразу → подписать серверный челлендж → доказанная связка» — тестируется
> без камеры и без второго устройства. QR-пункт на экране занятого номера показан,
> но задизейблен («пока недоступно») — заглушка, а не забытая функция; сама QR-привязка
> остаётся отдельной, отложенной работой (см. `doc/doc_UI/24-device-linking.md`).
>
> Челлендж — короткоживущий JWT (`ScopeReidentify`, 5 минут, subject = текущий
> user_id): без него подпись, полученная один раз, годилась бы для повторного
> использования где угодно.

> **Обновление 2026-08-12: QR-привязка реализована отдельным заходом.** Нашёлся
> прототип протокола (`doc_add/timaNC/server/internal/phase1/device_link.go`,
> другая ветка развития проекта) — адаптирован под здешнюю модель устройств
> (`server/internal/api/device_link.go` + `store/device_link.go` + миграция
> `0027`; клиент — `PhoneScreen` «Войти по QR», `HomeScreen` «Подключить
> устройство (QR)»). Подробности — `doc/03-security/key-lifecycle.md` §2,
> `ФАЗА-1-СТАТУС.md`. Секретная фраза выше остаётся отдельным, независимым
> путём для случая без второго устройства под рукой — QR её не заменяет, а
> дополняет. Оговорка не снята: физически на двух устройствах с камерой
> не проверялось, только модульными тестами и сборкой.

> **Найдено при выполнении:** план числил Р4 как «сервер готов». Готовы были
> хранилище и воркер, а ручек не было ни одной — удаление аккаунта существовало
> только как состояние, в которое его переводил воркер по неактивности.

**Архив чата решён и реализован (вариант Б):** архив у каждого участника свой,
чат готов к удалению только когда его убрали **все**. Уборка одного человека не
назначает удаление переписки другому.

**Аккаунт без номера и почты** живёт ограниченное время (90 дней), дальше вход
только после привязки данных. Это отдельный срок от месяца неактивности: первый
про «нет данных», второй про «молчит».

**Номер уходит новому владельцу** (оператор перевыпустил): прежний аккаунт теряет
номер, но сохраняет переписку и получает срок на привязку нового.

**Главной при воссоединении** остаётся личность с более ДЛИННОЙ перепиской, а не
просто более ранняя: обычно это одно и то же, но не всегда.

Зависело от Р1б (состояния на `persons`) и Р2 (гейт по уничтожению ключа) — оба готовы.

- [x] UI: сетка участников, состояния звонка

### Р5б — модель содержимого сообщения (формат и структурная часть готовы; полный блочный рендер, редактор и кеш — открыты)

Решение — [ADR-0011](../../doc/adr/0011-message-content-model.md).

- [x] `MessageBody`: поля `nodes` и `markup` новыми номерами, аддитивно
- [x] Переходный релиз: отправитель кладёт и плоский `text`, и новую структуру
- [x] Стабильные идентификаторы узлов в разметке, не позиция в массиве
- [x] Клиент отправляет и читает через кодек, а не через поле `text` напрямую
- [x] Испорченная разметка не теряет сообщение — текст без оформления
- [x] Закрытый каталог типов блоков и сущностей (`EntityType`, `BlockType`,
      `messenger-crypto/MarkupTypes.kt`) — реализация пункта ADR-0011 «что осталось
      за рамками»: «конкретный набор типов блоков… отдельным документом при
      реализации». Незнакомый тип деградирует до `UNKNOWN`, не роняя сообщение
- [x] Публичный контур: `channel_posts` получил `nodes TEXT[]`, `markup JSONB`,
      `markup_version INT` (миграция `0026`); `text` остаётся переходным путём —
      тот же приём, что и в личных сообщениях
- [x] Метаданные: `markup_version` — типизированная колонка, закрытым списком
      (ADR-0011 §5), а не поле в JSONB
- [x] Профили возможностей (`ContentProfile.BUBBLE` / `PUBLICATION`,
      `ContentProfiles`) — структурная часть: таблица шире порога помечается для
      горизонтальной прокрутки, контейнер глубже предела — для упрощения.
      Визуального рендера, который эти признаки применял бы на экране, нет
- [x] Каскад стилей (`StyleCascade`) — чистая функция: порядок инлайн → тип → чат →
      сообщество → приложение, три режима читателя, защитный пол (минимальный
      кегль, обязательный контраст по WCAG, запрет полноэкранной заливки документу
      и пространству чата/сообщества даже в режиме «как оформил автор»)
- [x] Тест-векторы формата — частично: `MessageContentTest`/`MarkupTypesTest`
      проверяют round-trip и деградацию незнакомых типов кросс-язычно по духу
      (Kotlin), но полноценный кросс-языковой KAT-вектор `markup_json` (по образцу
      `message_body`) не заведён — see `schema/test-vectors/README.md` §«Открыто»:
      его нельзя честно заморозить руками, без прогона `kotlinx.serialization`
- [ ] Редактор: один на оба контура — UI не начат
- [ ] Полный блочный рендер на экране (таблицы, контейнеры, списки) — есть только
      точечный инлайн-рендер (жирный/курсив/код/ссылка/упоминание/хэштег через
      `AnnotatedString`, `client/.../chat/InlineStyle.kt`), применённый в пузыре
      личных/групповых сообщений и в ленте канала. Блочная структура, каскад стилей
      и профили возможностей существуют как чистые функции, но не подключены к
      рендереру — блочного рендерера, который их вызывал бы, ещё нет
- [ ] Кеш рендера с ключом по версии стилей, теме, ширине, масштабу шрифта —
      бессмысленен без блочного рендерера, который бы что-то кэшировал

**Почему именно так разрезано:** «отрисовка блоков на всех платформах» — то, что
сам ADR называет основной стоимостью, а в этой среде нет Compose/Gradle-тулчейна,
чтобы писать и визуально проверять таблицы, контейнеры и сетки — код, который
нельзя даже скомпилировать вслепую, тем более полагаться на его вёрстку. Сделано
то, что проверяется логикой и модульными тестами без визуального цикла:
типы, структурные профили, каскад как чистая функция, публичный контур, точечный
инлайн-рендер. Редактор, полный блочный рендер и кеш рендера остаются открытыми —
честно, а не тихо пропущенными.
