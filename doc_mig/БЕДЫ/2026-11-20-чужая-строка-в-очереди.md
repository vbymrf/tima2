# Чужая строка в очереди роняет приложение (2026-11-20)

Поняли 2026-11-20 на realme (266) при проверке «потерянного входа»: переход в переключателе на аккаунт `52438fdf`
закрыл приложение. Симптом — в переключении аккаунтов, причина — в одной строке очереди неотправленного этого аккаунта.

## Что было видно

Нажали в переключателе окон на аккаунт `52438fdf` — приложение пропало, на экране рабочий стол. Повторный запуск уже не
падал (экран «вход потерян» встал раньше), но тексты переписок этого аккаунта — «расшифровывается…».

## Чем это казалось

- **«Падает новый экран „вход потерян“» (свежая правка 3.1)** — нет: стек не касается ни экрана, ни отметки потерянного
  входа; падает фоновый цикл очереди.
- **«Испорчен весь аккаунт»** — наполовину: тексты сообщений действительно не открываются, но приложение роняет не лента
  (у неё правило обратное — нечитаемая строка не лишает всей истории), а одна строка неотправленного.

## Доказательство

`logcat -b crash`, realme, 2026-11-20 20:54:19:

```
FATAL EXCEPTION … io.tima.app.v2
java.lang.IllegalArgumentException: тело 871f95d8-44e7-4633-a357-a933d1ea9e5a не открывается ключом покоя: база принадлежит другой установке
  at io.tima.core.database.SqlOutboxStore.toEntry(SqlOutboxStore.kt:135)
  at io.tima.core.database.SqlOutboxStore.pending(SqlOutboxStore.kt:97)
  at io.tima.core.outbox.Outbox.pending(Outbox.kt:574)
  at io.tima.shared.BackgroundLoopsKt$BackgroundLoops$6$sleepMs$1.invokeSuspend(BackgroundLoops.kt:115)
```

Аккаунт `52438fdf` на стенде — личность, удалённая 2026-10-05 («disputed»); тексты его переписок на realme —
«расшифровывается…»: база записана не тем ключом покоя, что выводится из секрета устройства этого аккаунта.

## Настоящая причина

**Намеренное громкое падение в общем месте.** `SqlOutboxStore.toEntry` падал (`requireNotNull`), если тело строки не
открывается ключом покоя: пустое тело ушло бы на сервер как сообщение. Но эту строку читают пять мест — фоновый цикл
очереди (`pending`), выбор следующей (`nextQueued`), захват запечатанной (`claimSealed`), поиск по ключу. Цикл очереди
ходит по ней на каждом проходе, сразу после открытия аккаунта, — и одна чужая строка роняла всё приложение, каждый раз.
Откуда строка под чужим ключом — не выяснено: у удалённых в октябре личностей realme база, похоже, записана при
прежних схемах хранения (до списка аккаунтов Д11 сессия и база были одни на телефон).

## Как починено

1. `fix(аккаунты)` (267): известный потерянный вход — экран сразу, до сети; «только чтение» — без фоновых циклов. Сняло
   падение для помеченных аккаунтов.
2. 269: **нечитаемая строка откладывается, а не роняет.** `SqlOutboxStore.readable()`: тело не открылось — строка
   становится «мёртвой» с причиной `unreadable_body` (остаётся в базе, на сервер не уходит), журнал пишет
   `QUEUE-UNREADABLE` с началом номера; `pending` её пропускает, `nextQueued` и `claimSealed` выбирают следующую — очередь
   не встаёт. Гарантия прежняя: пустое тело никуда не уходит.

## Чем проверено

- `UnreadableOutboxTest`: строка, положенная с другим секретом, — чтение очереди не падает и её не отдаёт; строка
  «мёртвая» с `unreadable_body`; `nextQueued` отдаёт следующую свою; поиск по ключу — `null`. core-database 266 — падений 0.
- Живьём: 267 — переход на `52438fdf` → экран «вход потерян» → «Читать» → переписка, падений 0. Строку под чужим ключом у
  аккаунта **без** отметки потерянного входа живьём не воспроизводили — такого на телефонах нет; закрыто тестом.

## Чему учит

**Громкое падение — для разработки, а не для общего места, которое читает фоновый цикл.** Защита «не отправить пустое»
верна, но её исполнение должно ограничиваться записью (отложить, сказать журналу), а не процессом целиком. И правило
для данных телефона: строка, которую нельзя прочитать, — повод отложить её с пометкой, а не повод не дать открыть всё
остальное.
