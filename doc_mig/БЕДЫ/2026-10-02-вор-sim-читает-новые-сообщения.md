# Вор SIM-карты читает новые сообщения

**Статус: не закрыта.** Поняли 2026-10-02 при разборе ключей; работа — [ПЛАН-УСТРОЙСТВ-И-ИСТОРИИ.md](../ПЛАН-УСТРОЙСТВ-И-ИСТОРИИ.md),
ДУ1–ДУ3. Беда в коде с самого начала нового клиента; живьём её никто не встречал — её нашли
чтением кода и доказали тестом.

## Что было видно

Ничего — и в этом беда. Человек, перевыпустивший чужую SIM-карту (или получивший номер у
оператора), ставит TIMA, вводит код из SMS — и становится ещё одним устройством аккаунта
жертвы. Жертва ничего не замечает: её устройства работают как работали. Её собеседники ничего
не замечают: их телефоны сами начинают шифровать и для нового устройства.

## Чем это казалось

- **«Фраза защищает от угона номера».** Так написано в
  `ДОКУМЕНТАЦИЯ/02-приложение/перенос-аккаунта-на-новое-устройство.md` §7 («угон номера → новый
  **пустой** аккаунт») и в комментариях кода (`groups.go:270`, `RecoverySignature.kt`). Это верно
  только для **старой истории**: восстановление ключей подписывается фразой. Для новых сообщений
  фраза не спрашивается нигде.
- **«Сервер сверяет ключ личности при регистрации».** Сверяет — но (1) поле необязательное, и без
  него сверки нет вовсе (`store/identities.go:150`: пустой ключ — `return nil`); (2) сверяется
  только равенство открытого ключа, а он открытый — сервер сам отдаёт его любому
  (`/users/identities`). Доказательства владения закрытым ключом нет.

## Доказательство

Тест на настоящей базе (портативный Postgres), код ветки `stand` на `b82be3f8`, 2026-10-02:

```
=== RUN   TestSimThiefProbe
    жертва с фразой: 201 user=b0f76bb3-…
    вор без фразы: 201  user=b0f76bb3-…                       ← тот же аккаунт
    вор с открытым ключом личности жертвы: 201  user=b0f76bb3-… ← тот же аккаунт
    собеседник шифрует для устройств жертвы: 3 шт.
      5a2b4f21-… (жертва=true  вор-А=false вор-Б=false)
      f55051d7-… (жертва=false вор-А=true  вор-Б=false)
      f3d4f60d-… (жертва=false вор-А=false вор-Б=true)
ok
```

Список устройств, который видит собеседник, — тот самый, по которому его телефон упаковывает
ключ каждого личного сообщения (`Sender.kt:166`) и ключ группы при смене (`GroupKeyRotation.kt:66`).
Проверки этого списка на клиенте нет: ни подписи устройств, ни знания ключа личности собеседника
(`Receiver.kt:954` — подпись сообщения сверяется с ключом из того же списка).

## Настоящая причина

**Устройство в аккаунте ничем не подтверждено.** Доверие к нему дают два факта, оба — слова
сервера: «код из SMS сошёлся» и «устройство в списке». Ключ личности (из фразы) существует, но
в цепочке «аккаунт → устройство» не участвует: он подписывает только восстановление истории,
перенос виртуального аккаунта и воссоединение личности. Отсюда:

- вор SIM получает **новые** личные сообщения сразу, ключ группы — при следующей смене;
- старая история закрыта — её восстановление требует подписи фразой;
- тот же путь открыт самому серверу (или тому, кто его взломал): подложить своё устройство в
  список — и клиенты начнут шифровать для него.

## Как починено

Не починено. Решение заказчика 2026-10-02 — схема В ([ПЛАН-УСТРОЙСТВ-И-ИСТОРИИ.md](../ПЛАН-УСТРОЙСТВ-И-ИСТОРИИ.md)
§1, Р2): фраза подписывает промежуточный ключ аккаунта, он подписывает устройства; регистрация в
аккаунт с фразой — только с доказательством владения фразой или подписью доверенного устройства;
клиенты собеседников не шифруют для неподписанного устройства.

## Чем проверено

Пока — только пробой выше. Закрытие проверяется тем же сценарием: под настройкой «требовать» вор
без фразы и вор с открытым ключом получают отказ, собеседник видит одно устройство.

## Чему учит

**Сверка открытого ключа — не доказательство.** Открытый ключ на то и открытый: проверка «прислал
тот же ключ» пропускает любого, кто его прочитал. Доказывает только подпись закрытым ключом над
свежими данными сервера.

И второе: **комментарий «барьер угона» стоял рядом с кодом, который барьером не был.** Обещание в
документе и в комментарии проверяется тестом, который пытается его нарушить, — а не чтением.
