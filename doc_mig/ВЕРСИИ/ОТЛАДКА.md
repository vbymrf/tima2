# Отладка: как агент попадает на телефоны

Заведён 2026-09-06 по решению заказчика. **Читается агентом перед любой работой с
телефоном** — установкой, снимком экрана, чтением журнала, живым прогоном.

Файл для двоих: слева порядок для заказчика (что запустить на своей машине), справа —
для агента (как проверить и что делать, когда не вышло). Новые способы и новые поломки
дописываются сюда же, а не остаются в переписке.

Конкретные адреса телефонов, коды сопряжения и фразы аккаунтов — в
[ТЕЛЕФОНЫ.local.md](ТЕЛЕФОНЫ.local.md), который git не отслеживает. Здесь только порядок.

---

## Главное правило

**Агент проверяет связь перед каждым обращением к телефону — и не чинит её молча.**

Связи нет — значит на стороне человека что-то не запущено или перебито, и агент об этом
пишет, а не начинает перезапускать службы и переподключать устройства. Причина простая:
почти все способы «починить» связь со стороны гостя (`adb kill-server`, `disconnect`,
смена портов) **рвут живые сессии заказчика**. Так уже вышло 2026-09-06: `kill-server` в
гостевой машине сбросил подключения, которые до этого работали.

Порядок: агент проверил → пусто → написал, что именно видит → разбираемся вместе.

---

## Рабочий способ: adb-сервер на машине заказчика

Гостевая машина VMware телефонов по USB не видит и с ними не сопряжена. Поэтому она
работает **через adb-сервер хоста**: сервер держит устройства, гость подключается к нему
по сети.

### Что делает заказчик (на своей машине, PowerShell)

```powershell
adb kill-server
Start-Process adb -ArgumentList '-a','nodaemon','server','start' -WindowStyle Hidden
```

`-a` — слушать не только петлю, иначе гость не достучится. `nodaemon` держит сервер в
этом процессе, поэтому запуск через `Start-Process`: обычный вызов занял бы окно.

**Как выглядит успех:**

```
netstat -ano | findstr :5037
  TCP    0.0.0.0:5037    0.0.0.0:0    LISTENING
```

`0.0.0.0` означает «слушаю на всех интерфейсах сразу» — это и нужно. Поломка выглядела бы
как `127.0.0.1:5037`: только петля, гостю не достучаться.

**Привязать сервер к конкретному адресу нельзя, и не надо.** Флага `--server-host` у adb
не существует: есть `-a` (серверу — слушать всё) и `-H`/`-P` (клиенту — куда идти).
Попытки задать адрес серверу тратят время на пустом месте — проверено 2026-09-06.

Если правило брандмауэра удалено (Windows иногда спрашивает заново и по умолчанию
запрещает):

```powershell
New-NetFirewallRule -DisplayName "adb 5037 для гостя VMware" -Direction Inbound `
  -Protocol TCP -LocalPort 5037 -Action Allow
```

**Окно брандмауэра — вторая по частоте причина.** Оно выскакивает при первом запуске
сервера и ждёт ответа; пока на него не ответили «разрешить», гость видит закрытый порт.

### Что делает агент

**Своего сервера не поднимает — работает клиентом в чужом.** Одна переменная окружения, и
все команды (`devices`, `shell`, `pull`, `install`) идут в сервер заказчика:

```powershell
$env:ADB_SERVER_SOCKET = 'tcp:<адрес хоста>:5037'
$adb = "$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe"
& $adb devices -l
```

Так телефон, подключённый к хосту **по проводу**, виден гостю наравне с сетевыми: провод
держит хост, а гость только спрашивает его сервер. Проброс USB в VMware при этом не нужен.

**Работать через PowerShell, а не Git Bash.** MSYS переписывает пути вида `/sdcard/…` в
`C:\Program Files\Git\sdcard\…`, и `adb pull` падает с «failed to stat remote object».
Ловится не сразу: команда выглядит правильной.

Снимок экрана телефона:

```powershell
& $adb -s <устройство> shell screencap -p /sdcard/tima.png
& $adb -s <устройство> pull /sdcard/tima.png "$env:TEMP\tima.png"
```

Экран чёрный — телефон спит: `input keyevent KEYCODE_WAKEUP`, при необходимости свайп
вверх. Нажатия — `input tap <x> <y>`; координаты берутся с самого снимка, размер экрана —
`wm size`.

Адрес хоста — адрес **хост-машины** в сети VMware, он же первый в подсети (`…​.1`).
Записан в `doc_mig/ОКРУЖЕНИЕ.local.md`. **Не путать со шлюзом NAT** (`…​.2`): шлюз — это
виртуальный роутер VMware, на нём не слушает ничего и слушать не будет. На эту путаницу
2026-09-06 ушло время с обеих сторон.

**Своего сервера агент при этом не поднимает и чужой не убивает.**

Проверить сам канал, не трогая adb:

```bash
timeout 5 bash -c 'echo > /dev/tcp/<адрес хоста>/5037' && echo открыт || echo закрыт
```

---

## Что означает увиденное

| Что видит агент | Что это значит | Что делать |
|---|---|---|
| порт 5037 закрыт | сервер не запущен **или** брандмауэр не пропустил | написать заказчику: обе причины на его стороне |
| порт открыт, список пуст | сервер живёт, но устройств в нём нет | написать заказчику; возможно, он смотрит в другой сервер (см. ниже) |
| устройство `offline` | запись есть, а живой сессии с телефоном нет | **не чинить самому**: см. «Телефон offline» |
| устройство `unauthorized` | телефон не подтвердил этот компьютер | заказчику: на телефоне ответить на запрос «Разрешить отладку» |
| `device` | связь есть, можно работать | работать |

## Разбор поломок

### 1. Сервер не запущен

Самая частая. Порт 5037 у хоста закрыт, гость не видит ничего. Лечится запуском сервера
(выше). Признак именно этой причины: `/dev/tcp` не открывается **и** окно брандмауэра не
всплывало.

### 2. Брандмауэр

Вторая по частоте, и выглядит точно так же — закрытый порт. Разница в том, что на машине
заказчика сервер работает и `adb devices` там показывает устройства. Значит правило для
порта 5037 либо не создано, либо удалено, либо в момент запуска висит окно с вопросом.

Проверить у себя:

```powershell
Get-NetFirewallRule -DisplayName "adb 5037*" | Select-Object DisplayName, Enabled, Action
```

### 3. Телефон `offline`

Порт отладки на телефоне открыт, а `adb connect` отвечает `failed to connect`, устройство
числится `offline`. Значит `adbd` жив, но старая сессия мертва — обычно после сна,
перезагрузки телефона или смены сети.

Порядок, от мягкого к жёсткому (делает заказчик у себя):

```powershell
adb disconnect 192.168.1.199:46571     # снять мёртвую запись (адрес свой)
adb connect 192.168.1.199:46571        # попробовать заново
```

Не помогло — на телефоне выключить и снова включить «Отладка по Wi-Fi». **Порт при этом
меняется**, новый адрес виден на том же экране; его надо продиктовать агенту и вписать в
`ТЕЛЕФОНЫ.local.md`.

Не помогло и это — сопряжение (пункт 4).

### 4. Два adb-сервера на одной машине

**Признак обманчивый:** у заказчика `adb devices` показывает устройства, у агента через тот
же порт — пусто. Значит серверов два: Windows разрешает одному процессу занять
`127.0.0.1:5037`, другому — `<адрес VMnet>:5037`, адреса разные, конфликта нет. Клиент
заказчика по умолчанию идёт на петлю, гость — по сети, и они попадают в разные серверы.

Проверить у себя:

```powershell
netstat -ano | findstr :5037        # две строки LISTENING — это оно
Get-Process adb | Select-Object Id, Path
```

Лечится тем, что убиваются **все** серверы, а не один:

```powershell
Get-Process adb | Stop-Process -Force
Start-Process adb -ArgumentList '-a','nodaemon','server','start' -WindowStyle Hidden
adb devices        # пусто — правильно: клиент и сервер теперь одни
```

Агент проверяет, что попал в живой сервер, не поднимая своего:

```bash
exec 3<>/dev/tcp/<адрес хоста>/5037 && printf '000chost:version' >&3 && head -c 32 <&3
# OKAY0004xxxx — сервер отвечает; дальше host:devices-l покажет список
```

### 5. Не сопряжено

Беспроводная отладка Android пускает только сопряжённые компьютеры: поверх TCP идёт TLS с
проверкой ключа сопряжения. Отсюда обманчивая картина — **порт открыт, а `connect`
отказывает**.

На телефоне: «Отладка по Wi-Fi» → «Подключение с помощью кода сопряжения». Там **другой**
порт и шестизначный код; экран держать открытым, код живёт недолго.

```powershell
adb pair 192.168.1.199:<порт сопряжения> <код>
```

Сопряжение разовое на каждую пару «компьютер — телефон». Гостевая машина сопряжена
отдельно от хоста: для неё это чужой компьютер.

### 6. Провод вместо сети

Гость VMware телефон по USB не видит, пока устройство не проброшено:
**Player → Removable Devices → <телефон> → Connect**. После этого гостю видно напрямую, и
сервер хоста не нужен.

## Чего агент не делает никогда

- **Не выполняет `adb kill-server`.** Он убивает сервер вместе с живыми подключениями
  заказчика — на его машине это выглядит как «всё отвалилось само».
- **Не переключает отладку на телефоне** и не меняет порты: телефон в руках у человека.
- **Не ставит APK «чтобы было», когда проверяется обновление.** Если на телефоне версия
  ниже раздаваемой — это и есть состояние, в котором проверяется путь «открыл, нажал,
  обновилось». Установка руками уничтожает проверку, ничего не проверив.
