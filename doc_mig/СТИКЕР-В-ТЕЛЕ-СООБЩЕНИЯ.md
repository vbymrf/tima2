# Стикер в теле сообщения: что вносим в `message_body.proto`

**Решение заказчика 2026-09-04.** Стикер передаётся **меткой внутри зашифрованного
тела**: набор и номер. Файл в сообщении не ходит. Кода этот документ не меняет — здесь
только то, что будет внесено, и обоснования.

Формат самих файлов — [СТИКЕРЫ-И-ЭМОДЗИ.md](СТИКЕРЫ-И-ЭМОДЗИ.md). Здесь протокол.

---

## 1. Модель, от которой отталкиваемся

Слова заказчика: **сообщение — это массив узлов и сведения о нём в JSON. Картинки,
стикеры, разметка — приложения к сообщению, а не отдельные его виды.**

Так оно и устроено в коде уже сегодня:

```
MessageContent(nodes, markup, media)
  → MessageContentCodec.toBody()      → MessageBody (protobuf)
  → zstd
  → Kodium.encryptSymmetric(message_key)  → Envelope.encrypted_payload
  → POST /messages
```

| Что | Где |
|---|---|
| Продуктовая модель и перевод в wire | `messenger-crypto/…/crypto/MessageContent.kt:47` |
| Один кодек на провод и на диск | `client/core/core-encryption/…/TextBodyCodec.kt` |
| Запечатывание конверта | `client/core/core-encryption/…/PersonalMessages.kt:44` |
| Схема тела | `schema/proto/message_body.proto` |
| Схема конверта | `schema/proto/envelope.proto` |

В `message_body.proto` записано прямо:

> **ВАЖНО: у приватного сообщения разметка едет ЗДЕСЬ, внутри зашифрованного тела.**
> Открытой она быть не может: она выведена из содержимого и раскрывает структуру,
> ссылки, наличие медиа и упоминания — то есть социальный граф внутри переписки.

Стикер — ровно такое же выведенное из содержимого сведение. Значит его место там же.

## 2. Что хранит база

`server/migrations/0001_messages.sql`, таблица `personal_messages`. Первая строка файла:
*«Сервер хранит только ciphertext и обёртки; расшифровать не может»*.

| Открыто | Зашифровано |
|---|---|
| `chat_id`, `message_id`, `client_msg_id` | **`encrypted_payload`** |
| `sender_id`, `sender_device` | |
| `kind`, `created_at_unix_ms`, `reply_to` | |
| `format_version`, `signature`, escrow-блобы | |

**JSONB-колонки в этой таблице нет.** Она появляется только в модели публичного контура
([ADR-0011](../doc/adr/0011-message-content-model.md) §5), где содержимое и так открыто.
В личной переписке стикеру негде лежать, кроме зашифрованного тела, — схема решила это
за нас.

## 3. Что вносим в `message_body.proto`

```proto
message StickerRef {
  string pack_id = 1;    // набор
  uint32 index   = 2;    // номер в наборе
}
```

и в `MessageBody` — **новым номером**, старые поля не трогаются:

```proto
  StickerRef sticker = 6;
```

### Правила, которые при этом соблюдаются

- **Номера полей неизменны**, новые добавляются только с новыми номерами — требование
  `envelope.proto` и `proto/README.md`. Поле 6 свободно: заняты 1–5.
- **Схема расширяется, не переписывается.** Старый клиент, не знающий про поле 6,
  пропустит его — так устроен protobuf, и в этом же смысл правила «сервер работает со
  старым клиентом».
- **`schema/test-vectors/` не трогаем.** Добавление поля вектора не ломает; если
  сломает — значит неверен код, а не вектор.

### Плоский текст для старых клиентов — эмодзи

В `MessageContentCodec.toBody()` отправитель уже сегодня кладёт **оба** представления
текста: узлы и плоскую склейку, чтобы клиент старого формата показал сообщение хотя бы
без оформления. Для стикера тот же приём даёт бесплатную деградацию:

| Поле | Что кладём |
|---|---|
| `sticker` (6) | `{pack_id, index}` |
| `text` (1) и `nodes` (4) | **юникод-эмодзи, которому стикер соответствует** — «🎻» |

- новый клиент видит поле 6 и рисует анимацию;
- старый читает `text` и показывает эмодзи;
- пустого пузыря не получает никто.

Отсюда, между прочим, следует и требование к набору: **у каждого стикера должно быть
соответствие юникоду**, иначе подставлять в `text` нечего.

### Почему не через `MediaRef`

В теле уже есть `repeated MediaRef media = 3`, и соблазн положить стикер туда понятен.
Не годится: `MediaRef` несёт `media_key` — ключ шифрования приватного медиа-объекта.
**У стикера ключа нет и быть не может**: файл публичный, одинаковый у всех, лежит в
общем хранилище. Класть его в структуру, у которой обязательное поле — ключ, значит
врать типом.

## 4. Тип сообщения: заводить ли `CK_STICKER`

Вопрос заказчика: **зачем вообще может понадобиться тип сообщения?** Разбор ниже, и он
кончается «не заводить».

### Что такое `kind` сегодня

`ContentKind` в `envelope.proto`: `CK_TEXT`, `CK_VOICE`, `CK_IMAGE`, `CK_VIDEO`,
`CK_FILE`, `CK_SYSTEM`. Колонка `kind INT NOT NULL` в `personal_messages` — **открытая**,
лежит рядом с зашифрованным телом.

**Факт, который стоит знать до всякого обсуждения: поле не используется.**

- `client/core/core-encryption/…/OutgoingSealer.kt:50` — личное сообщение уходит с
  `kind = KIND_TEXT`;
- `client/core/core-encryption/…/GroupMessageSealerOverKodium.kt:31` — групповое тоже;
- на сервере `kind` только пишется и читается обратно (`store/group_messages.go`), ни
  одного решения по нему не принимается.

То есть за всё время живой код положил в это поле ровно одно значение. Заводить
`CK_STICKER` — значит **начать пользоваться полем, которое до сих пор не понадобилось**.

### Шесть случаев, ради которых тип бывает нужен

| Зачем | Работает ли у нас | Вердикт |
|---|---|---|
| **Push «прислал стикер» без расшифровки** | сервер текста не знает; по `kind` мог бы дать содержательное уведомление | **единственный настоящий довод** — и он же утечка: сервер видит поток типов по каждой переписке |
| Превью последнего сообщения в списке чатов | клиент расшифровывает сам, тип берёт из тела | не нужен |
| Фильтр «только медиа в чате» | там же, локально | не нужен |
| Серверные квоты и уборка | считаются медиа-объекты в своей таблице, не сообщения | не нужен |
| Антиспам по типам | противоречит E2E и обходится за секунду: отправитель поставит `CK_TEXT` | не нужен |
| Старый клиент заранее поймёт «не покажу» | тело всё равно расшифровывается; выгоды ноль | не нужен |

### Два довода против, которые сильнее единственного «за»

**Первый: метаданные лежат открыто и вечно.** ADR-0011 §5 требует держать их закрытым
списком именно поэтому. Открытый `kind` со значением «стикер» — это навсегда записанное
«в этом чате в такой-то момент отправили стикер». Взамен мы получаем чуть более
приятный текст push-уведомления.

**Второй, и он технический: появляется два источника правды.** Тип сообщения выводится
из тела — есть поле `sticker`, значит стикер. Открытый `kind` — второе место, где то же
самое записано. Подпись покрывает и метаданные, и полезную нагрузку, так что подменить
их **чужому** нельзя, но отправитель волен положить `kind = CK_TEXT` и стикер в теле.
Получатель обязан верить телу — иначе он показывает не то, что послали. Значит `kind` в
принципе не может быть источником правды, а только подсказкой. Подсказка, которая может
врать, дороже, чем стоит.

### Решение

**`CK_STICKER` не заводим.** Стикер уходит как `CK_TEXT`, тип определяется наличием поля
`sticker` в расшифрованном теле. Это в точности модель заказчика: сообщение одно, а
стикер — приложение к нему.

`ContentKind` из схемы **не убираем** — это контракт, и его номера неизменны. Просто не
расширяем.

Оговорка на будущее: если когда-нибудь понадобится push вида «прислал голосовое», это
будет отдельное решение с отдельным обоснованием и явной ценой в метаданных, а не
«заодно со стикерами».

## 5. Что этот документ не решает

**Откуда получатель берёт картинку.** Метка внутри шифра закрывает передачу: файл не
ходит, сервер слеп. Но по метке нужно показать изображение, и если его нет на
устройстве — клиент пойдёт за ним, а запрос сервер увидит. Это вопрос доставки наборов
([СТИКЕРЫ-И-ЭМОДЗИ.md](СТИКЕРЫ-И-ЭМОДЗИ.md) §5 и §8), и на выбор `{pack_id, index}` он
никак не влияет.

**Кода не касаемся.** Здесь записано, что будет внесено, когда дойдёт очередь:

| Файл | Правка |
|---|---|
| `schema/proto/message_body.proto` | `message StickerRef` + `StickerRef sticker = 6` |
| `messenger-crypto/…/MessageContent.kt` | поле в модели, перевод в `toBody`/`fromBody` |
| `schema/test-vectors/` | **не трогаем** |
| `envelope.proto`, `ContentKind` | **не трогаем** |
