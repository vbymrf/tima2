# Дельта: чего требует интерфейс и что есть на сервере

Выход задачи **С1.1** ([КАРТА-СЕРВЕРА.md](КАРТА-СЕРВЕРА.md)). Требования взяты из
[интерфейс.md §11](../doc/интерфейс.md) построчно; ответ на каждое получен чтением
кода и миграций, а не документации о них.

```
Сверено:     2026-08-21
Коммит:      faea5d2
Источник требований:  doc/интерфейс.md §11 (строки 1005–1062)
Источник ответов:     server/migrations/*.sql (29 файлов), server/internal/api/*.go
```

Вердикты значат:

- **есть** — маршрут или таблица названы, требование закрыто;
- **частично** — опора есть, но не то, что просит §11 (назван недостаток);
- **нет** — на сервере отсутствует вовсе;
- **расходится** — на сервере есть похожее, но с другим смыслом; **это дороже
  «нет»**, потому что придётся решать, что делать с уже существующим;
- **не серверное** — интерфейсное состояние, серверу знать не нужно.

## §2. Счётчики и агрегаты

| Требование | Вердикт | Комментарий |
|---|---|---|
| Непрочитанное **по чату** | **нет, и это не только про счётчик** | `POST /chats/{id}/read` **ничего не сохраняет** — он рассылает `receipt.read` на устройства собеседника. Курсора прочтения на сервере нет ни в `chat_states`, ни где-либо. Значит новое устройство не знает, что прочитано |
| Непрочитанное **по объекту каталога** | нет | Каталога нет |
| Непрочитанное **по разделу** | **не серверное** (решено 2026-08-21) | Разделы клиентские (`doc/01-product/разделы.md`). Сервер отдаёт непрочитанное по объекту, сумму по разделу складывает клиент |
| Непрочитанное **сводно по окну** | **не серверное** | Окно — состояние интерфейса; сумма складывается на клиенте из того же непрочитанного по объекту |
| По разделу: сколько объектов | **не серверное** | Состав раздела знает только клиент — раздел наружу не виден |
| По посту: эмоции по видам с числами | нет | Реакций на сервере нет вовсе |
| По посту: «настроение» −1…+1 | нет | — |
| По посту: число комментариев **и отдельно** веток | нет | — |
| По посту: моя эмоция, мой «+/−» | нет | — |
| По комментарию: эмоции | нет | — |
| По сообщению: эмоции (вся шкала на одном) | нет | — |
| По звонку: **направление** | выводится | `calls.initiator_id` против своего `user_id` |
| По звонку: **тип** | есть | `calls.kind ∈ audio/video` |
| По звонку: **длительность** | выводится | `answered_at` … `ended_at` |

| По голосовой комнате: сколько человек | есть | `voice_rooms` + `memberships(target_type='voice_room')` |
| По голосовой комнате: сколько идёт | выводится | `created_at`, `closed_at` |
| По группе/каналу: участники, подписчики | есть | `memberships`, `channel_subscriptions` |

| По профилю: подписки, подписчики | **частично** | Подписки есть **только на каналы**. Подписки на человека нет (комментарий в миграции: «subscriptions в data-model — полиморфные; для MVP отдельная таблица») |
| По профилю: свои группы | есть | `groups.owner_id` |
| По коллекции: число файлов, тип, тип защиты, непрочитанные | нет | Коллекций нет |
| По автору: число записей и подписчиков | частично | Записи — по `channel_posts.author_id`; подписчиков автора нет |
| По объекту: закреплённые, общие медиа | нет | Закрепления нет ни в одной таблице |

## §4. События окна 4

Окно 4 — «входящие»: ответы, активность, комментарии, эмоции, оценки. **Ни одного
из шести типов на сервере нет.** Существующие 13 событий ws — про доставку и
инфраструктуру, а не про социальную активность:

```
call.incoming      call.state          channel.post
group.rotation_needed                  key.rotated
message.group      message.new         receipt.read
recovery.gk_ready  recovery.gk_request
recovery.msg_ready recovery.msg_request
voice.hand
```

Требования §11 и что им нужно:

| Событие | Нужна сущность, которой нет |
|---|---|
| Ответ в вашей ветке (с числом новых) | ветки постов, курсор прочтения ветки |
| Активность в отслеживаемом обсуждении | отслеживание («подписка на ветку») |
| Комментарий к вашему посту (с цитатой и местом) | комментарии, лента |
| Эмоция на ваше сообщение (со ссылкой) | реакции |
| «Плюс» от канала | реакции + права канала |
| Оценки записи вашего псевдонима (с числом и разбивкой) | псевдонимы, агрегаты |

Плюс общее требование «каждое — с автором, временем и источником»: **нужна таблица
входящих событий**, а не только шина. `device_events` для этого не годится: она
адресована **устройству**, а не человеку, и чистится уборкой.

## §5. Что из этого следует

**1. Вердикт «достроить» подтверждается, но с поправкой.** Личное общение,
группы, каналы, звонки, устройства, escrow — это готовый, покрытый тестами фундамент.
**Социального слоя нет целиком:** реакций, комментариев, лент, разделов, коллекций,
историй, закладок, псевдонимов, статистики, входящих событий — ноль.

**2. Самое дорогое — не «нет», а «расходится».** Три места, где решение уже принято
кем-то раньше и его придётся либо принять, либо отменить:

- **сообщество**: связи заведены (`groups.community_id`, `community_access`,
  `memberships.target_type='community'`), самой таблицы нет;
- **закрытая группа**: `kind` знает два вида, интерфейс требует три;
- **подписки**: на канал — своя таблица, на человека — ничего, хотя в
  `data-model.md` они задуманы полиморфными.

**3. Два требования §11 упираются в шифрование, а не в объём работы.** Реакции на
личные сообщения и счётчик непрочитанного требуют, чтобы сервер знал то, чего он
сейчас не знает: на какое именно сообщение поставили эмоцию и до какого места вы
дочитали. Сегодня `personal_messages` для сервера — непрозрачный `encrypted_payload`
с подписью. Это развилка приватности, а не задача.

**4. Оценку в неделях не даю до ответов.** Не из осторожности: половина объёма
зависит от ответов на вопросы вида «сервер знает или не знает» — а они меняют не
сроки, а схему.

## §7. Хранение и уборка: что такое «правило 90 дней»

Разобрано 2026-08-21, потому что от него зависят решения по социальному слою (см.
[ВОПРОСЫ-К-ЗАКАЗЧИКУ.md](ВОПРОСЫ-К-ЗАКАЗЧИКУ.md) А1). **Правило не про метаданные,
а про ключи и доставку** — это меняет то, как его надо применять к новым таблицам.

Уборку гоняет воркер раз в час. Сроки берутся **из таблицы `retention_policy`**:
`delivery_retention_days` = 90, `appeal_window_days` = 30. Переменные
`TIMA_RETENTION_DAYS` и `TIMA_APPEAL_WINDOW_DAYS` остались **запасом** — работают
только на базе, где миграция 0030 не применена. Восемь задач, ошибка одной не
останавливает остальные (`internal/worker/worker.go`).

### Что удаляется и что от этого перестаёт работать

| Таблица | Что в ней | Срок | Что теряется |
|---|---|---|---|
| `personal_message_keys` | `(chat_id, message_id, recipient, wrapped)` — **ключ сообщения, обёрнутый для устройства**. Сервер прочитать не может | 90 дней от `received_at` сообщения | Сервер больше **не может выдать** сообщение устройству, которое его не забрало. Конверт (`personal_messages`) остаётся навсегда — до escrow-архива |
| `group_wrapped_keys` | то же для групповых ключей: версия ключа, обёрнутая для устройства | 90 дней от ротации версии | Устройства эти версии давно забрали; escrow-копия остаётся в `group_key_history` |
| `group_wrapped_keys` вышедших | обёртки тех, кто вышел или исключён | **30 дней** от `left_at` | Окно апелляции (`crypto-protocol §4.2`): пока открыто — исключённый расшифрует бывшее при нём, закрылось — нет |
| `device_events` | журнал доставки: монотонный `event_id`, `payload` JSONB | 90 дней | GC двигает `events_watermark`; устройство с курсором ниже получает **`sync.gap`** вместо догона. То есть офлайн дольше 90 дней = полный пересбор |
| `sms_codes` | коды подтверждения | 24 ч после истечения | — |
| `device_link_sessions` | сессии привязки устройства (живут 5 минут) | 24 ч после истечения | Сутки запаса оставлены намеренно: «посмотреть в таблицу при разборе жалобы „привязка не сработала"» |

### Чего правило НЕ касается — и это важнее всего

**`personal_message_backup` в уборку не входит.** Это те же ключи сообщений, но
обёрнутые `backup_key` владельца. Значит восстановление своей истории на новом
устройстве (ADR-0010) сроком в 90 дней **не ограничено**: обрезается только путь
«доставить конкретному устройству», а не возможность восстановиться.

Конверты `personal_messages` и `group_messages` тоже не удаляются: в
`0008_gc.sql` сказано прямо — «пока нет escrow-архива; escrow_blob по спеке
хранится до 7 лет».

### Расхождение, найденное и закрытое 2026-08-21

**Было:** таблица `retention_policy` держала 8 политик, правящихся SQL без
пересборки, и в `store/retention.go` записан замысел — «правка требования должна
быть правкой строки, а не пересборкой». А 90 дней в таблице **не было**: они жили в
переменной окружения. Вышло наоборот от замысла — срок жизни аккаунта правился
строкой, а срок, после которого перестаёт выдаваться история, только перевыкаткой.

**Стало:** миграция `0030_delivery_retention.sql` добавила две строки, воркер читает
их через `RetentionDaysOr`, поля структуры остались запасом для базы без миграции.
Одна политика на три таблицы — намеренно: `device_events`,
`personal_message_keys` и `group_wrapped_keys` обязаны чиститься одним сроком, иначе
возникает состояние «событие есть, а ключа к нему уже нет».

Проверка не декларативная: тест `TestWorkerGCAndSyncGap` ставит политику в 0, а поля
структуры — в 999 дней. Если воркер прочитает поля вместо базы, не удалится ничего и
тест упадёт.

Восемь прежних политик:

```
account_inactive_days   30    временный аккаунт: неактивность → архив
account_purge_days      30    архив → физическое стирание
reunion_window_days     30    окно воссоединения истории с новым аккаунтом
no_credentials_days     90    жизнь аккаунта без телефона и почты
legal_retention_days   180    юридическое хранение
chat_archive_days      180    чат в архиве → пометка удалённым
chat_purge_days        180    пометка → физическое стирание
chat_all_archived_days 180    архив у ВСЕХ участников → пометка удалённым
```

**Побочно нашлось: тесты пачкают эту таблицу.** `ResetForTests` её намеренно не
труncate-ит («там строки, засеянные миграцией»), поэтому значение, выставленное
тестом, остаётся в базе после прогона — в базе разработки так и висело
`account_purge_days = 77` от `retention_test.go`. Пока сроки были в переменных
окружения, это было безобидно; теперь от этих строк зависит поведение уборки.
`TestWorkerGCAndSyncGap` возвращает значения через `t.Cleanup`; остальные тесты,
правящие политики, — нет, и это стоит поправить в дорожке Д.

## §6. Как это перепроверить

```bash
grep -rhoE 'mux\.HandleFunc\("[^"]+"' server/internal/api/*.go | sort | wc -l

# таблицы
grep -rhoiE 'create table( if not exists)? +[a-z_]+' server/migrations/*.sql \
  | sed -E 's/.* //' | sort -u

# события ws
grep -rhoE 's\.notify\([^,]+, *[^,]+, *"[a-z_.]+"' server/internal/api/*.go \
  | grep -oE '"[a-z_.]+"' | sort -u
```

Числа в этом документе получены этими командами. Расходятся — верны команды.
