# План постройки клиента заново

> **Статус:** предложение архитектуры, требует утверждения.
> Переписан 2026-08-20 после решений заказчика (§0.0). Код измерен на `stand` (`fcf591f`).
>
> **Это не рефакторинг.** Поддержка прежних клиентов снята, серверные данные
> стираются — значит клиент строится заново. Из старого дерева переносится
> перечисленное в §5, остальное удаляется вместе с ним.
>
> **Область — только клиент.** Сервер не переписывается: он развёрнут и работает
> (106 тестов, 27 миграций, анклав escrow, вебхуки LiveKit). Серверные этапы Р0…Р7 —
> [arhiv/ПЛАН-РЕФАКТОРИНГА.md](arhiv/ПЛАН-РЕФАКТОРИНГА.md), там же оговорка, что его
> галочки — заявки, а не факты.
>
> Канон, которому план подчинён: [ADR-0001](../doc/adr/0001-kmp-compose-client.md)
> (KMP + Compose, SQLDelight, Ktor, Koin, Konsist),
> [module-boundaries.md](../doc/02-architecture/module-boundaries.md) §4 (имена
> модулей), [tech-stack.md](../doc/02-architecture/tech-stack.md),

> [интерфейс.md](../doc/интерфейс.md) (что должен уметь интерфейс).

## §0.0. Принятые решения

Зафиксировано в обсуждении 2026-08-20. Каждое снимает работу, которая иначе попала
бы в план.

| № | Решение | Что снимает |
|---|---|---|
| 1 | **Clean install.** Старая локальная база, `chats.json` и старые ключи не читаются никогда | совместимость хранилища, значения persisted enum, миграции локальной схемы |

| 4 | **Крипто, схема protobuf и тест-векторы переносятся, а не пишутся заново** | — (это ограничение, а не упрощение; обоснование в §0.1) |
| 5 | **Формат конверта и API не меняются, пока v2 не заработает** | три одновременных неизвестных при отладке |
| 6 | **Звонки на ПК — требование** | — |
| 7 | **Сжатие остаётся zstd**; провайдер — `zstd-kmp` вместо `zstd-jni` (§3.6.1) | смену формата тела; сборку `libzstd` под iOS вручную; expect/actual для сжатия |

| 9 | **Плоское поле `text` не заполняется нигде.** Содержимое — только `nodes` + `markup`; **боты переходят на узлы** (§3.4.1) | двойную запись содержимого в каждом сообщении и в каждом посте |
| 10 | **Локальное шифрование — вариант A:** AEAD на поле, метаданные открыто (§3.4.3) | нативную зависимость на трёх платформах; вместе с ней — обещание FTS5 по содержимому |
| 11 | **`module-boundaries.md` §5 признан устаревшим** — там отменённая ADR-0011 модель `text + entities` | проектирование редактора по отменённой модели |

## §0.1. Ограничения — три вместо семи

Всё, что было ограничением из-за старых данных, отменено решениями 1–3. Осталось
то, что от возраста проекта не зависит.

**1. Крипто-ядро, схема и тест-векторы переносятся с доказательством, а не
переписываются.**

Причина не в совместимости — её больше нет. В том, что **доказательство дороже
кода**: `schema/test-vectors` порождены внешними реализациями (`tweetnacl-js`,
`@noble/post-quantum`), канонические байты сходятся Go ↔ Kotlin по KAT-векторам,
BouncyCastle в тестах — второй независимый оракул.

Свидетельство, что это не формальность: именно оракул поймал дефект в реализации
ML-KEM у Kodium — она усекала выход SHAKE и заполняла матрицу 3 % энтропии
([ADR-0005](../doc/adr/0005-kodium-readiness-gate.md)). Код при этом работал:
шифровал, расшифровывал, тесты проходили. **Криптография ломается молча.**
Переписать её заново — значит заново заработать доказательство, а это месяцы.

**2. Формат конверта и API не меняются, пока v2 не заработает.**

Теперь это не запрет, а порядок отладки: когда всё вокруг новое, формат и
серверный контракт — единственное заведомо верное. Изменить их значит получить
падение, о котором нельзя сказать, где оно: в новой сети, новом Outbox, новом
крипто или в формате. После работающей v2 — менять сколько нужно, отдельным ADR.

**3. Инвентарь поведения вычитан прежде, чем старое дерево удалено.**

В `client/` есть знание, которого нет ни в одном документе: признаки блокировки из
журналов мобильной сети, потолок zstd-бомбы, расхождение `livekit_url`/`url`,
повадки `DownloadManager` на Samsung. Список — §5. Удалить дерево, не вычитав его,
значит заново собрать те же грабли в первом же выходе в живую сеть.

## §1. Архитектура

Три слоя. Зависимости направлены **только внутрь**: Presentation → Domain ← Data.
Domain не знает о существовании двух других.

```
┌───────────────────────────────────────────────────────────────┐
│ Presentation      feature-*/commonMain                        │
│   Compose (рендер State) → Intent → Store (MVI) → UseCase     │
│   Знает: core-ui, core-model, domain-*                        │
│   НЕ знает: Ktor, SQL, messenger-crypto, android.*, platform.*│
└───────────────────────┬───────────────────────────────────────┘
                        │ только через UseCase
┌───────────────────────▼───────────────────────────────────────┐
│ Domain            domain-*/commonMain — чистый Kotlin          │
│   UseCase · сущности · интерфейсы репозиториев · политики      │
│   Зависимости: kotlinx-coroutines, kotlinx-datetime. И всё.    │
└───────────────────────▲───────────────────────────────────────┘
                        │ реализует интерфейсы Domain
┌───────────────────────┴───────────────────────────────────────┐
│ Data              core-*/commonMain + */androidMain,iosMain    │
│   Repository (impl) · DataSource · Mapper · DTO · Entity       │
│   core-network · core-database · core-encryption · core-outbox  │
└───────────────────────────────────────────────────────────────┘
```

### §1.1. Связь через UseCase

**UseCase — единственная точка входа Presentation в Domain.** Не «репозиторий,
вызванный из ViewModel», а именованный сценарий.

```kotlin
// domain-chat/commonMain
class SendMessage(
    private val outbox: OutboxRepository,      // интерфейс объявлен здесь же
    private val chats: ChatRepository,
    private val clock: Clock,
) {
    suspend operator fun invoke(chatId: ChatId, draft: MessageDraft): Result<LocalMessageId>
}
```

| Правило | Причина |
|---|---|
| Один UseCase — один сценарий, `operator fun invoke` | список файлов = список того, что приложение умеет |
| Возвращает `Result<T>` или `Flow<T>`, **не бросает** | исключение, дошедшее до Composable, — краш вместо состояния экрана |
| Внутри нет `Dispatchers.*` | диспетчер приходит извне (§2.2), иначе тест обязан ждать реальное время |
| UseCase не вызывает UseCase | иначе через полгода это граф, а не слой. Общее — в доменный сервис |
| UseCase не знает про экраны, навигацию и переводы | это Presentation |

### §1.2. MVI: контракт

Одна `Store` на экран. Логики в Composable нет.

```kotlin
// feature-chat/commonMain
data class ChatState(                      // immutable, только данные для рендера
    val messages: List<MessageUi> = emptyList(),
    val link: LinkState = LinkState.ONLINE,
    val sending: Boolean = false,
    val error: UiText? = null,
)
sealed interface ChatIntent {              // что сделал человек
    data class Send(val text: String) : ChatIntent
    data class Retry(val id: LocalMessageId) : ChatIntent
}
sealed interface ChatEffect {              // однократное: навигация, тост
    data class Navigate(val to: Route) : ChatEffect
}
```

| Правило | Причина |
|---|---|
| `reduce(state, event): State` — **чистая функция** | делает сценарий пользователя воспроизводимым без устройства; на этом стоит весь §3.9 |
| Побочные эффекты отдельно от reducer, вызывают только UseCase | reducer, дергающий сеть, нельзя прогнать 1000 раз за секунду |
| `Effect` — однократное, в канал; `State` — текущее, в `StateFlow` | «показать тост» в State даёт повторный тост на каждой рекомпозиции |
| Composable получает `State` и отдаёт `(Intent) -> Unit`, больше ничего | интерфейс переписывается целиком, не задевая Core |
| В `State` нет платформенных типов (`Bitmap`, `Uri`, `File`) | иначе Presentation прирастает к платформе через данные, а не через импорты |

### §1.3. Как Presentation не узнает про Android и iOS

Четыре механизма, потому что запрет, держащийся на договорённости, не держится.

1. **Модуль физически не видит платформу.** `feature-*` объявляет только
   `commonMain`. Нет source set — нет импорта. Исключение — `app-*`.
2. **Konsist в CI:** `feature-*` не импортирует `android.*`, `platform.*`, `java.*`,
   `io.ktor.*`, `io.tima.crypto.*`, `com.squareup.wire.*` и не зависит от другого
   `feature-*`.
3. **Никаких `java.*` в общем коде:** время — `kotlinx-datetime`, файлы — `okio`.
   `java.time` компилируется на JVM и падает на iOS, то есть ошибка находится
   позже всего.
4. **Ресурсы** — `compose-resources`, не `R.string` и не `NSLocalizedString`.

Платформенное попадает в интерфейс единственным путём: `core-platform` объявляет
`expect`, `app-*` даёт `actual`, Presentation получает **интерфейс** через Koin.

## §2. Паттерны и правила написания кода

### §2.1. Паттерны и где именно они применяются

| Паттерн | Где | Что решает |
|---|---|---|
| **Repository** | `ChatRepository`, `OutboxRepository`, `ContactsRepository`, `UpdateRepository` | в v1 интерфейс `ChatClient` имел ~40 методов, и экран видел через него всё приложение |
| **Mapper** | `MessageDto ↔ Message ↔ MessageEntity` | три модели, три жизни: формат меняет сервер, схему — миграция, домен — продукт. Одна модель на три роли ломается от любой правки |
| **Factory** | `LocalDbFactory`, `CallEngineFactory`, `HttpClientFactory` | объект, чьё создание зависит от платформы, создаётся в `app-*`, а не `expect`-конструктором в глубине |
| **State Machine** | `LinkState` (переносится из v1), `OutboxItemState`, `UpdateState`, `CallState`, `TransportState` | явные состояния и переходы вместо набора `Boolean` |
| **Strategy** | `EndpointStrategy`: прямо / альт-порт / прокси A / прокси B | подмена маршрута конфигом, без сборки |
| **Decorator** | `RetryingTransport`, `LoggingTransport` над `Transport` | ретраи и журнал не размазываются по вызовам API |
| **Outbox** | `core-outbox` | доставка ровно-один-раз при обрывах и убийстве процесса |
| **Result / sealed error** | возврат UseCase | ошибка — значение, а не поток управления |

Отклонено осознанно: ручной Observer (есть `Flow`), `object` с состоянием (не
тестируется, живёт между тестами), Service Locator наружу (Koin только в `app-*`).

### §2.2. Правила

**Слои и интерфейсы**

1. **Интерфейс объявляется в том слое, который его вызывает.** `ChatRepository` — в
   `domain-chat`, реализация — в Data. Обратное не даёт ничего: Domain всё равно
   зависел бы от Data.
2. **Domain не зависит ни от чего, кроме `kotlinx.*`.** Проверяет Konsist. Ktor в
   Domain означает, что туда протёк транспорт.
3. **DTO и Entity не покидают Data.** Наружу ездят доменные типы.
4. **`core-*` не зависит от `feature-*`. `feature-*` не зависит от `feature-*`.**
5. **Модуль появляется, когда у кода есть второй потребитель или другой цикл
   сборки. До этого — пакет.** Команда 2–3 человека; сорок модулей дадут минуты
   ожидания Gradle и ноль изоляции.

**Потоки и ресурсы**

6. **`Dispatchers` не упоминаются в Domain и Presentation.** Инжектится
   `AppDispatchers(main, io, crypto, default)`; `crypto` — отдельный ограниченный
   пул: шифрование и zstd не конкурируют с сетью.
7. **`withContext` — на границе Data**, один раз.
8. **Владеющее нативной памятью или дескриптором реализует `Closeable`** и живёт
   через `use` либо в явном `NativeScope` (§3.7).
9. **Ключи и расшифрованные тела затираются явно.** У Kotlin/Native финализаторы
   не гарантированы.

**Ошибки и состояние**

10. **`try/catch` в Composable запрещён.** Ошибка приходит в `State`.
11. **Строки для человека не собираются в Domain.** `UiText` — ключ и аргументы.
12. **В `@Composable` нет логики, кроме верстки.** «Показать баннер, если офлайн и
    очередь не пуста» — поле `State`, вычисленное reducer'ом.

**Совместимость с сервером** (с прежними клиентами её больше нет, с сервером — есть)

13. **Неизвестное поле игнорируется, неизвестный тип деградирует.** Wire это даёт,
    `kotlinx.serialization` — с `ignoreUnknownKeys = true`. Сервер будет
    расширяться, и клиент не должен падать от нового поля.
14. **Форматы расширяются аддитивно, выкатка — сервер раньше клиента**
    (`server-compatibility.mdc`: «сервер, понимающий и старое и новое, безопасен в
    любой момент; клиент, требующий ручку, которой у сервера ещё нет, сломан с первой
    секунды»). **Но порядок выкатки — не единственная защита:** клиент обязан
    переживать отсутствие поля. Нет значения — значит функции нет, а не «блокировать».
    Иначе откат сервера превращает клиент в кирпич, и порядок выкатки становится
    единственным, что стоит между пользователем и неработающим приложением.
15. **Деривации из [crypto-invariants](../.cursor/rules/crypto-invariants.mdc) не
    меняются при переносе.** Перенос обязан быть побайтово нейтральным, и это
    доказывают тест-векторы, а не глаза.
16. **Смена криптопровайдера = правка одного файла-обёртки.** Если понадобилось
    трогать `EscrowModule`/`PersonalMessageSealer`/`GroupKeyManager` — граница
    обёртки сломана, остановиться.


**`jvmCommon` не создаётся.** В v1 он существовал, и в нём осели `TimaChatService`
(1374 строки) и `MessageStore` (296) — то есть бизнес-логика, отрезанная от iOS не
по необходимости, а потому что так было проще. Набор появляется только под
доказанную нужду (общий JVM-драйвер, JNI-обёртка) и никогда не содержит классов с
суффиксом `Repository`, `UseCase`, `Store`, `Service`. Проверяет Konsist.

### §3.3. `core-network` — гибкость без правки кода

Задача измерена в v1 и записана там же: TCP встаёт за 57 мс, дальше тишина. В v1
это распознавалось разбором текста исключения, маршрут был один и вводился руками.

```
Transport (интерфейс)
   ├── EndpointStrategy   упорядоченные кандидаты: прямой TLS · альт-порт ·
   │                      прокси A · прокси B · фронтинг
   │                      источник: подписанный конфиг + локальное переопределение
   ├── TransportState     PROBE → HEALTHY → DEGRADED → BLOCKED
   ├── RouteMemory        победивший кандидат запоминается на сеть (SSID/оператор)
   └── RetryPolicy        экспонента с дрожанием; сроки — из LinkState
```

| Решение | Причина |
|---|---|
| Кандидаты — **список в конфиге** | смена прокси не требует сборки |
| Проверка параллельно, коротким сроком; побеждает первый ответивший **на уровне приложения** | «пакеты уходят, ответа нет» — успех TCP здесь ничего не значит |
| Победитель запоминается **на сеть** | дома и в мобильной сети блокируется разное |
| Конфиг маршрутов **подписан** | иначе подмена маршрута — способ атаки. Приём уже отработан: `EscrowTrust` проверяет подпись конфига зашитым ключом |
| Пиннинг — на **сервер**, не на прокси | иначе прокси становится доверенным звеном |
| `classifyFailure` переносится из v1 как есть | признаки взяты из журналов настоящих испытаний |
| Ретраится только идемпотентное | повтор отправки идёт **через Outbox** по ключу дедупликации, а не ретраем HTTP |

### §3.4. `core-outbox` — жизненный цикл сообщений

```
Исходящее: DRAFT → QUEUED → SEALED → SENDING → SENT → ACKED
                     ↑                    ↓
                     └── FAILED(retryable) ┘      FAILED(permanent) → DEAD
Входящее:  RECEIVED → DECRYPTED → STORED → READ
                 └→ UNDECRYPTABLE (ключа нет; не теряем, помечаем)
```

| Решение | Причина |
|---|---|
| Ключ идемпотентности генерирует **клиент**, до первой попытки | иначе повтор после обрыва даёт дубль у собеседника |
| **Запечатывание — позднее, на попытке отправки.** Конверт кэшируется с привязкой к идентификатору ключа эпохи escrow и выбрасывается при смене эпохи | так требует [ADR-0016](../doc/adr/0016-local-store-and-link-states.md): в очереди лежит открытый текст (под шифрованием хранилища), конверт собирается перед посылкой, потому что **за время ожидания успевает смениться ключ эпохи escrow**. Заранее запечатанный конверт унёс бы устаревший ключ. Кэш по `key_id` при этом не даёт шифровать заново на каждом ретрае внутри одной эпохи |
| Вложения — своя запись и свой блоб | падение на 90 % загрузки не должно возвращать сообщение в начало |
| `UNDECRYPTABLE` — состояние, а не потеря | ключ может приехать позже |
| Ограничение одновременных отправок | иначе очередь после суток офлайна выстреливает залпом |
| Восстановление при старте | идея из v1 (`requeueStuck`): состояние `SENDING` остаётся висеть после убийства процесса |

**Один источник правды.** В v1 список чатов лежал одновременно в SQLite
(`StoredChat`) и в `chats.json` (`Session.kt`) — те же поля в двух местах. В v2
список чатов живёт только в базе; `Session` хранит сессию и ничего больше.

#### §3.4.1. Модель содержимого сообщения

Действующая модель — [ADR-0011](../doc/adr/0011-message-content-model.md): **массив
узлов плюс разметка**, без якорных символов и без смещений в тексте.

```protobuf
repeated string nodes = 4;   // узлы текста
string markup = 5;           // компактный JSON; пусто = разметки нет
repeated MediaRef media = 3; // вложения, media_key внутри шифрования тела
```

Разметка ссылается на узлы **по идентификаторам, а не по позиции**: вставка узла в
середину иначе сдвигала бы все последующие индексы и ломала ссылки из блоков, хотя
сама разметка не менялась. Смещения в UTF-16 к тому же расходятся между платформами
на эмодзи и составных символах — за это формат 1 и заменили.

**`markup` несёт три разные вещи, а не только стили:**

```
Markup { version, n: [ids узлов], entities, blocks, styles }
  MarkupEntity { type, node, start, length, url, user_id, attribute }  ← инлайн внутри узла
  MarkupBlock  { type, nodes: [ids], children: [...], level, style }   ← структура, рекурсивно
  MarkupStyles { global, by_type }                                     ← каскад
```

**Поле `text` в v2 не заполняется.** Оно существовало для склейки узлов старым
клиентам и как запасной путь при испорченной разметке. Первая причина отменена
(прежние клиенты не поддерживаются), вторая отдельного поля не требует: испорченная
разметка оставляет `nodes`, и их склейка даёт тот же результат. **Боты переходят на
узлы** — значит `text` не заполняется и в публичном контуре.

> **Работа на стороне сервера, вне этого плана.** Отказ от `text` в публичном
> контуре означает, что Bot API обязан отдавать `nodes`/`markup`, а не плоский
> текст, и что колонка `channel_posts.text` перестаёт наполняться. По правилу
> выкатки **сервер идёт раньше клиента**. Задача записана в §7.

**Быстрый путь обязателен.** В схеме прямо сказано: `markup` пуст у обычного
сообщения, а это 99 % сообщений. Обычное сообщение — один узел и пустая разметка;
хранение и рендер обрабатывают этот случай без разбора JSON и без обхода блоков.

**Две зоны видимости, и их нельзя путать:**

| Где | Что | Кто видит |
|---|---|---|
| `Envelope` | chat_id, отправитель, время, `key_id`, подпись, `key_commitment` | **сервер видит** |
| `MessageBody` | `nodes`, `markup`, `media` с `media_key` | только устройства |

Разметка приватного сообщения едет внутри зашифрованного тела намеренно: она
выведена из содержимого и раскрывает структуру, ссылки, наличие медиа и упоминания,
то есть социальный граф внутри переписки. Следствие для хранения: локально она тоже
не может лежать в открытой колонке.

**Готово в коде:** закрытый каталог типов (`MarkupTypes`, незнакомый тип
деградирует в `UNKNOWN`), профили возможностей (`ContentProfile.BUBBLE` /
`PUBLICATION`), каскад стилей (`StyleCascade`: инлайн → тип → чат → сообщество →
приложение, с защитным полом по кеглю и контрасту). **Не готово:** блочный рендерер.
Есть только точечный инлайн-рендер через `AnnotatedString`; таблиц, контейнеров и
списков на экране нет, и каскад с профилями поэтому никем не вызывается. Это хвост
Р5б, он попадает в К5–К6.

> **`doc/02-architecture/module-boundaries.md` §5 устарел** — там модель
> `text + entities` со смещениями в стиле Telegram, отменённая ADR-0011.
> Подтверждено заказчиком 2026-08-20. Правится в дорожке Д первым пунктом: пока
> документ не исправлен, редактор проектируется по отменённой модели.

#### §3.4.2. Формат хранения на устройстве

Тело хранится **теми же байтами, что уходят в конверт** — `zstd(protobuf(MessageBody))`,
только под локальным ключом вместо ключа сообщения. Один кодек на провод и на диск.

```
messages
  local_id        INTEGER PK        свой, монотонный
  dedup_key       TEXT UNIQUE       генерируется до первой попытки отправки
  server_id       INTEGER NULL      приходит с ACK
  chat_id         TEXT
  sender_id       TEXT
  client_ts       INTEGER           часы устройства
  server_ts       INTEGER NULL      порядок в чате — по нему, если есть
  state           INTEGER           машина состояний §3.4
  attempts        INTEGER
  next_attempt_at INTEGER NULL
  reply_to        INTEGER NULL
  body_enc        BLOB              zstd(protobuf(MessageBody)) под локальным AEAD

attachments
  id, local_id → messages, kind, mime, size, path, media_key_enc, state
  ↑ блоб — файлом на диске; в базе только путь и ключ

chats
  chat_id, kind, title_enc, preview_enc, last_at, unread
```

Ключ покоя — `HKDF(deviceSecret, "tima/local-store/v1")`, как в v1; секрет живёт в
`core-secrets` (Keystore / Keychain / DPAPI). **Хранилище ключа — часть формата, а не
деталь реализации:** в v1 на ПК секрет лежал открытым рядом с файлом базы, и
шифрование покоя было декоративным, пока не появился DPAPI.

Пять решений, каждое закрывает дефект v1:

| Решение | Что закрывает |
|---|---|
| Один кодек на провод и на диск | в v1 `packBody` склеивал текст и JSON вложения разделителем `\n\0`; `nodes`/`markup` через него не проходили вовсе |
| Вложения файлами, в базе — путь и ключ | в v1 байты лежали в самой базе (`attachmentBytes`); файл на 100 МБ в SQLite противоречит бюджету памяти §3.7 |
| Outbox — **колонки в `messages`**, не отдельная таблица | иначе снова два источника правды на одно сообщение |
| `dedup_key` уникален | защита от двойной записи, когда догон истории пересёкся с live-каналом. Приём из v1, работает |
| Порядок по `server_ts ?: client_ts`, затем `local_id` | иначе офлайн-сообщения прыгают при получении серверных идентификаторов |
| Превью чата — шифртекст (`preview_enc`) | в v1 открытый текст ушёл из `chats.json`; он не должен вернуться в базу |

**Физическое стирание** (требование [ADR-0015](../doc/adr/0015-retention-and-erasure.md)):
`PRAGMA secure_delete`, иначе `DELETE` оставляет страницы читаемыми, плюс явное
удаление файлов-блобов. Проверяется тестом, а не предположением.

**Локальные миграции — с первого дня**, номер схемы в базе. Деструктивные
разрешены только до первого релиза; после — append-only, как на сервере.

#### §3.4.3. Шифрование покоя и локальный поиск — решено: вариант A

**Принято 2026-08-20: пошаговый AEAD на поле, метаданные открыто, ноль новых
зависимостей.** То же разделение, что в v1 и в ADR-0016.

Отклонён вариант B — шифрование файла базы целиком. Он давал и FTS5 по
зашифрованному индексу, и закрытые метаданные, но ценой нативной зависимости на трёх
платформах, включая iOS-сборку. Для клиента, который ещё не существует, это плата
вперёд за удобство, которое нужно не сразу.

**Из решения следуют три вещи, и все три надо назвать вслух.**

**1. Локальный поиск — только расшифровкой на лету**, по текущему чату или по окну
последних сообщений. Индекса по содержимому нет и не будет: индекс по шифртексту не
ищет, а индекс по открытому тексту — это plaintext-архив рядом с зашифрованной
базой, то есть отмена самого шифрования покоя.

**2. [tech-stack.md](../doc/02-architecture/tech-stack.md) обещает «SQLite FTS5 для
локального поиска» — это обещание больше не действует.** Документ правится в
дорожке Д, иначе получится ровно та болезнь, которую мы лечим: канон говорит одно,
код делает другое, и через месяц никто не помнит, где правда.

**3. Что утекает, если устройство и базу прочитали:** кто с кем, когда, сколько
сообщений, их состояния и размеры вложений. **Содержимое — нет.** Это честная
граница варианта A, и её надо знать заранее, а не обнаружить в отчёте по
безопасности.

Возврат к B остаётся возможен: шифрование файла базы — **аддитивное** изменение, оно
не касается формата на проводе. Если понадобится, это отдельный ADR, перекрывающий
ADR-0016 в части «метаданные открыто», плюс замер драйверов. Сейчас — не нужно.

### §3.5. `core-update` — многоуровневое обновление

| Уровень | Что | Платформа |
|---|---|---|
| 0 | проверка версии: `GET /api/v1/app/version` | все |
| 1 | скачивание и установка пакета | Android: APK · Desktop: свой установщик · iOS: отсылка в App Store |
| 2 | принудительное обновление: ниже `min_client` работа заблокирована | все |

`AppVersionDto` сейчас несёт `version_code`, `version_name`, `url`, `notes` — порога
совместимости нет. Поле аддитивное, и по правилу выкатки **сервер идёт раньше
клиента**.

**При этом клиент не должен зависеть от порядка выкатки для собственной
работоспособности:** отсутствующий `min_client` означает «гейта нет», а не
«блокировать». Иначе откат сервера на предыдущую версию превратит установленные
клиенты в кирпичи — то есть самая опасная кнопка в системе окажется у того, кто
всего лишь откатывает выкатку.

Правила: **подпись проверяется всегда** (иначе канал обновления — канал доставки
чужого кода); сравнение по `versionCode`, не по имени; на iOS уровня 1 нет, и это
часть контракта, а не сюрприз при сборке.

### §3.6. `core-encryption` и `core-secrets`

`messenger-crypto` остаётся единственным местом криптографии и переводится с
`kotlin("jvm")` на KMP. Блокеры по факту:

| Зависимость | Состояние | Действие |
|---|---|---|
| Kodium | KMP, уже используется в общем коде | оставить |
| KyberKotlin (`asia.hombre:kyber`) | KMP | оставить |
| `kotlinx-serialization` | KMP | оставить |
| Wire runtime | KMP-таргеты есть | проверить сборку под iOS |
| **`zstd-jni`** | **JNI, только JVM** | **заменяется на `com.squareup.zstd:zstd-kmp`** — одна библиотека на все таргеты, включая Apple. Проверено прогоном на iOS-симуляторе 2026-08-20; `expect/actual` не нужен вовсе (§3.6.1) |
| **`asia.hombre:kyber`** и `keccak` | **артефактов Apple нет** — единственный оставшийся блокер | таргеты Apple в их сборках **закомментированы**, а код уже собирается под Kotlin/Native. Варианты — §3.6.2 |
| BouncyCastle | `testImplementation` | остаётся в `jvmTest`: это оракул, поймавший дефект Kodium |

`core-secrets` — `SecretVault` (Keystore / Keychain / DPAPI). Хранит только материал
ключей. **Двух слоёв legacy-миграции**, которые несёт `SessionCodec.load()` в v1
(plaintext → vault и разбор сессий, записанных версией, где vault не шифровал), в
v2 нет: clean install.

#### §3.6.1. Сжатие: zstd остаётся, провайдер — `zstd-kmp`

Алгоритм не меняется. В коде уже записано: «Wire-сериализация нормативна для
Go-реализации; zstd-вывод по байтам **не нормативен**… только распаковка
нормативна». Значит iOS не обязан жать теми же байтами — ему нужно читать чужое.

**Провайдер выбран 2026-08-20 и проверен прогоном:** `com.squareup.zstd:zstd-kmp`
0.4.0, Apache 2.0, без зависимостей, публикует `iosArm64`, `iosSimulatorArm64`,
`iosX64`, `android`, `jvm`, `macos*`, `linux*`, `mingwX64`. Спайк прошёл на
iOS-симуляторе в CI.

| Путь | Цена | Вердикт |
|---|---|---|
| **`zstd-kmp`** — одна библиотека на все таргеты | зависимость версии 0.x за одним файлом-обёрткой | **выбран** |
| cinterop к `libzstd` вручную | собирать `libzstd` под каждый таргет Apple: в iOS SDK zstd нет, `libcompression` даёт zlib, LZFSE, LZ4, LZMA | не нужен |
| `zstd-jni` + expect/actual | JVM-only, плюс на Android требовал отдельный `@aar` | отменён |
| Kotlin-порт zstd | своя реализация чужого формата | нет |
| Другой алгоритм | изменение формата тела: ADR, версия, правка Go и Kotlin разом | нет |

**Следствия, каждое — упрощение:**

- **`expect/actual` для сжатия не нужен вовсе.** Канон (`tech-stack.md`) требует
  «expect/actual биндинги» — требование отпадает, документ правится в дорожке Д.
- Костыль v1 исчезает: там исключали jar `zstd-jni` и подключали отдельный `@aar`,
  потому что в jar не было Android-нативов (инвентарь, пункт 15).

**Одна правка не упрощение, а изменение защиты.** У `zstd-kmp` низкоуровневый
потоковый API (`ZSTD_compressStream2`, `ZSTD_decompressStream`) без one-shot и
**без `getFrameContentSize`**. Защита от zstd-бомбы поэтому меняется:

| Было в v1 | Будет в v2 |
|---|---|
| спросить у кадра заявленный размер → сверить с 16 МиБ → распаковать | распаковывать потоково и **падать при превышении потолка на выходе** |

Новый способ **строже**: заголовок кадра может врать или отсутствовать
(`ZSTD_CONTENTSIZE_UNKNOWN`), а фактический выход не обманешь. Потолок обязан быть
**одинаковым на всех платформах** — разный означает, что принятое Android отвергается
iOS, то есть расхождение клиентов.

Компрессор держит нативный контекст и закрывается через `use()` — правило §2.2 п. 8.

##### Взвешенно: почему `zstd-kmp` берём, и на каких условиях

**Альтернатив с таргетами Apple нет.** Проверено: `com.github.luben:zstd-jni` —
один артефакт, JNI, только JVM и Android; `io.airlift:aircompressor` — чистая Java;
у korlibs zstd нет; поиск по Maven Central даёт только JVM-, Scala- и
NDK-варианты. Остаётся `zstd-kmp` либо собирать `libzstd` под каждый таргет Apple
самим.

**Главное, что делает риск приемлемым: выбор провайдера сжатия обратим и не касается
данных.** Сжатый вывод не нормативен, нормативна только распаковка. Поэтому смена
провайдера через год не портит ни сохранённое, ни отправленное — в отличие от
ML-KEM, где другой провайдер ломает согласование ключей. Это разные по цене решения,
и мерить их одной линейкой нельзя.

| Против | Насколько это больно |
|---|---|
| версия **0.4.0**, до 1.0; последний выпуск октябрь 2025 | API может поменяться. Смягчено правилом инвариантов: библиотека живёт за **одним** файлом-обёрткой |

**Условия, при которых это решение остаётся дешёвым** — их надо соблюдать, иначе
преимущество исчезает:

1. библиотека вызывается **только** из одного файла в `messenger-crypto`;
2. версия закреплена в каталоге, обновление — отдельная задача с прогоном векторов;
3. запасной путь записан: cinterop к `libzstd`, собранному под таргеты Apple. Если
   `zstd-kmp` исчезнет, мы теряем удобство, а не данные.

#### §3.6.2. ML-KEM на iOS — единственный оставшийся блокер

`asia.hombre:kyber` (ML-KEM-768 для escrow) и его зависимость `keccak` **не публикуют
ни одного артефакта Apple**. Escrow не опция: каждое исходящее сообщение оборачивает
ключ сообщения на ключ эпохи escrow, поэтому **без ML-KEM iOS не отправит ни одного
сообщения**.

Готовой замены нет — проверено: у `org.kotlincrypto.*` только хеши, MAC и sponges;
у `dev.whyoleg:cryptography-kotlin` 0.6.0 в списке операций KEM отсутствует;
BouncyCastle только JVM.

**Но блокер дешевле, чем выглядел.** В сборках обеих библиотек таргеты Apple
**закомментированы**:

```kotlin
    linuxX64()
    mingwX64()
    //iosArm64()
    //iosX64()
    //iosSimulatorArm64()
    androidNativeArm32()
```
Код уже собирается под Kotlin/Native (linux, mingw, androidNative) — значит дело не в
переносимости кода.

> **Поправка к сказанному раньше.** Сначала я написал, что для публикации klib под
> Apple нужен Mac. **Это неверно.** В Kotlin Gradle Plugin есть свойство
> `kotlin.native.enableKlibsCrossCompilation`, и оно **включено по умолчанию**
> (проверено в исходниках плагина: `booleanProperty(...) ?: true`). Для чистого
> Kotlin-кода klib под Apple собирается и на Linux, и на Windows.
>
> Mac обязателен для другого: **линковка** итоговых бинарей Apple (framework,
> исполняемый файл), **прогон тестов** на симуляторе или устройстве, и cinterop к
> заголовкам Apple SDK.
>
> Похоже, автор отключил не «то, что нельзя собрать», а **то, что нельзя проверить**:
> рядом закомментирован и `linuxArm64()`, а его кросс-компиляция тоже возможна.

Задача превращается из «портировать чужую криптографию» в «раскомментировать три
строки и собрать» — **в двух репозиториях**: `KyberKotlin` и `KeccakKotlin`. Третья
зависимость цепочки, `org.kotlincrypto.random:crypto-rand`, таргеты Apple **уже
публикует**, её трогать не нужно.

| Вариант | Суть | Цена | Инварианты |
|---|---|---|---|
| **A. Вендорить исходники** обеих библиотек в `messenger-crypto` | тот же код → те же байты | два чужих модуля в дереве; апстрим отслеживать вручную, записав хеш коммита | целы |
| **B. Форк + composite build** (как v1 подключал `messenger-crypto`) | тот же код, апстрим догоняется через git | два форка; в сборке — `includeBuild` | целы |
| **C. Второй провайдер для iOS** через cinterop к OpenSSL 3.5+ | не трогаем существующее | тяжёлая зависимость; **две реализации одного примитива** | **нарушает** «один провайдер на примитив» |
| **D. PR автору** + просьба опубликовать | три строки в каждом репозитории | бесплатно; **и теперь понятно, чем помочь**: у него нет Mac для проверки, а у нас есть бесплатные раннеры macOS — можно приложить к PR результат прогона тестов на симуляторе | целы |

Рекомендация: **A или B сейчас, D параллельно.** A и B отличаются только тем, где
лежит код; D снимает долг, если апстрим включит таргеты. Наш CI собирает и **проверяет**
под Apple бесплатно, поэтому и наш вариант, и помощь автору стоят один прогон.
лежит код; D снимает долг, если апстрим включит таргеты. Наш CI умеет собирать под
Apple бесплатно, поэтому проверка любого варианта — один прогон.

**Про оракул на iOS.** Сверять с BouncyCastle там нельзя, он JVM-only. Второй
реализации и не требуется: `schema/test-vectors` порождены **внешними** реализациями
(`tweetnacl-js`, `@noble/post-quantum`) и платформонезависимы. Разделение такое:

| Что проверяем | Чем |
|---|---|
| алгоритм верен | BouncyCastle на JVM + KAT-векторы сторонних реализаций |
| Kotlin/Native ведёт себя как JVM | те же векторы, прогнанные на iOS-симуляторе в CI |

Оговорка ADR-0005 в силе: вектор `mlkem768_escrow` не поймал бы перестановку `d` и
`z`, потому что в нём все 64 байта одинаковы. При переносе нужен вектор с `d != z` —
отдельный пункт К2.

Нативное: `zstd-kmp` (нативные библиотеки на каждый таргет), WebRTC внутри звонков, на iOS — рантайм Kotlin/Native.
Ошибки здесь дают не исключение, а падение процесса.

| Правило | Причина |
|---|---|
| `NativeScope` — арена: выделенное внутри освобождается на выходе, в том числе при исключении | `try/finally` на каждый вызов забывается один раз, и этого достаточно |
| `MemoryBudget`: потолок байтов «в работе» на медиа; превышение — ожидание | в v1 `sendFile(bytes: ByteArray)` брал файл в память целиком |
| Медиа обрабатывается чанками | деривация `chunk:<i>` уже существует — поток предусмотрен форматом |
| Ключи затираются явно | GC не обещает ни времени, ни факта |
| Счётчики нативных аллокаций — в `core-diagnostics` | «падает на старых телефонах» без счётчиков не диагностируется |

### §3.8. `core-call` / `feature-call` — звонки, включая ПК

**Звонки на ПК — требование.** В работу самого LiveKit не вмешиваемся
([ADR-0006](../doc/adr/0006-livekit-media-policy.md)); выбираем только способ, которым
десктоп до него доберётся.

| Платформа | Реализация |
|---|---|
| Android | `livekit-android` (в v1 работает, переносится) |
| iOS | LiveKit Swift SDK через interop |
| Desktop | один из трёх маршрутов ниже |

| Маршрут | Суть | Цена | Риск |
|---|---|---|---|
| **A. LiveKit Rust SDK через FFI** | тот же клиентский стек, что у Flutter- и Unity-SDK; Kotlin зовёт через JNI-обёртку | сборка нативной библиотеки под Windows/macOS/Linux и доставка в дистрибутив | зависимость от чужого FFI; протокол и переподключение — не наши |
| **B. JVM-биндинги WebRTC + свой сигналинг** | готовые Java-обёртки WebRTC, поверх — наша реализация протокола комнаты | **сигналинг пишем сами**: подписка на дорожки, переподключение, качество | высокий: ровно та работа, которую ADR-0006 отдал LiveKit |
| **C. Встроенный webview с `livekit-client`** | окно звонка — веб-страница внутри приложения | лишний рантайм в дистрибутиве, доступ к камере через прослойку | средний по коду, высокий по весу и качеству медиа |

Предпочтение: A, затем C, затем B. **Выбор — замером на К7**, не сейчас: зрелость
FFI и наличие сборок под Windows проверяются руками.

`core-call` описывает звонок контрактом (`CallEngine`, `CallState`); ни один экран не
знает, какой маршрут выбран. Смена маршрута позже — замена одного `actual`.


#### §3.8.1. Насколько мы вмешиваемся в LiveKit — измерено

Правило стоит с ADR-0006: **в работу LiveKit не вмешиваемся, качество медиа — его
зона.** Ниже — что это значит на сегодня, по коду, а не по памяти.

**Вся наша поверхность соприкосновения:**

| Где | Объём | Что делаем |
|---|---|---|
| `server/internal/calls/token.go` | 83 строки | выпускаем `AccessToken` комнаты |
| `server/internal/calls/roomservice.go` | 116 строк | **два вызова** RoomService поверх обычного HTTP (twirp): закрыть комнату |
| `server/internal/api/*calls*.go` | — | обработчик вебхуков: проверка подписи и сверка хэша тела |
| `server/deploy/livekit.yaml`, compose, Caddy | конфигурация | TURN включён, умолчания комнаты |
| клиент | зависимость | официальный `io.livekit:livekit-android` |

Официальный `server-sdk-go` **сознательно не взят**, и причина измерена: только
`livekit/protocol` компилирует 423 пакета против 346 у всего нашего бэкенда, а нужны
два вызова. В файле это записано вместе с условием пересмотра: «понадобится половина
API — SDK станет оправдан, и это будет видно».

**Чего мы не трогаем вовсе:** кодеки, управление перегрузкой, simulcast, маршрутизацию
SFU, переподключение медиа. То есть сегодня мы LiveKit **эксплуатируем через его
публичный API**, а не дорабатываем. Двести строк на всё.

##### Как маршруты Desktop-звонков ложатся на это правило

| Маршрут | Вмешательство | Что появляется у нас |
|---|---|---|
| **A. Rust SDK через FFI** | **нет нового** — их клиентский стек | обёртка JNI и нативная библиотека в дистрибутиве |
| **C. Webview с `livekit-client`** | **нет нового** — их официальный JS-клиент | лишний рантайм; медиа идёт через прослойку |
| **B. JVM-WebRTC + свой сигналинг** | **максимальное** | подписка на дорожки, пересогласование, переподключение, выбор simulcast — **всё то, что ADR-0006 отдал LiveKit** |

Отсюда порядок предпочтения A → C → B не вкусовой. Вариант B означает, что мы
переписываем клиентский протокол LiveKit своими руками, и тогда **каждое обновление
их сервера может нас тихо сломать** — при этом отвечать за качество медиа начинаем мы,
хотя решение ADR-0006 состояло ровно в обратном.

##### Ограничитель, чтобы не сползти

Даже с A или C правило можно нарушить случайно — начав подкручивать битрейты или
писать свои таймеры переподключения. Ограничитель: **контракт `core-call` описывает
намерения и состояния** (войти, выйти, микрофон, камера, кто говорит), и **никогда**
параметры транспорта. Как только в контракте появляется битрейт или таймаут ICE —
мы уже внутри чужой зоны, и это повод остановиться.

### §3.9. `test-*` — тестирование, пригодное для управления ИИ

Главное решение: **утверждения делаются о `State`, а не о пикселях.**

| Слой | Как проверяется | Скорость |
|---|---|---|
| Domain, UseCase | обычные тесты, без платформы | миллисекунды |
| Store (MVI) | сценарий = последовательность `Intent`; сверяются `State` и `Effect` | миллисекунды |
| Data | контрактные тесты против записанных ответов сервера | секунды |
| Экран | рендер из фиксированного `State` (скриншот) | секунды |
| Сквозной | ферма телефонов, живой сервер | минуты |

Отладочный доступ: в debug-сборке приложение поднимает локальный сокет, отдающий
`State` и принимающий `Intent`. Управляющий ИИ шлёт «нажми отправить» и читает
состояние, а не угадывает по скриншоту. **В релизной сборке этого кода нет
физически** — отдельный source set, а не флаг: флаг забывают выключить.

Compose Hot Reload и MCP-сервер — инструмент разработчика; ни одна проверка в CI от
них не зависит.

## §4. Постройка: восемь этапов

Каждый этап заканчивается **проверяемым** признаком. Порядок — от того, что должно
быть заведомо верным, к тому, что на этом стоит.

### К1 — каркас

- `build-logic`, `libs.versions.toml`, модули по §3.1 (пустые)
- **iOS-таргет объявлен и компилируется** с первого коммита. Не «потом»: именно это
  физически не даст JVM-коду просочиться в общий и повторить `jvmCommon`
- Koin в `shared`, Konsist с правилами §2.2, **CI, которого в проекте нет вовсе**
- `core-model`: доменные типы без поведения

**Выход:** `:app-android`, `:app-desktop` собираются пустыми;
`:core-model:compileIosMainKlib` проходит; CI зелёный; правило «feature не зависит
от feature» проверяется машиной.

### К2 — крипто и протокол на KMP

- `messenger-crypto` → `kotlin("multiplatform")`, файлы переносятся без правок
- `zstd`: замена `zstd-jni` на `zstd-kmp` — одна библиотека на все таргеты, `expect/actual` не нужен; обёртка one-shot поверх потокового API с потолком на выходе (§3.6.1)
- **ML-KEM: раскомментировать таргеты Apple** в форке или вендоренных исходниках Kyber и Keccak (§3.6.2) — вариант ждёт решения заказчика
- BouncyCastle только в `jvmTest`
- Wire-кодоген из `schema/proto` проверен под все таргеты

**Выход:** тест-векторы `schema/test-vectors` проходят **байт в байт на JVM**, и
iOS-таргет компилируется (`klib`). Это доказательство, что перенос ничего не сдвинул;
без него дальше не идём.

> **Прогон векторов на iOS-симуляторе — помеченный долг, а не часть гейта.** Он
> требует машины Apple, которой нет (решение 8: iOS держим компилируемым, но не
> запускаем). Пока долг не закрыт, **утверждать «крипто работает на iOS» нельзя ни в
> одном документе** — компиляция доказывает, что код собирается, а не что он считает
> те же байты.

### К3 — сеть, база, Outbox

- `core-network` по §3.3
- `core-database`: SQLDelight, схема проектируется **заново** (clean install), один
  источник правды на список чатов
- `core-outbox` по §3.4, обе машины состояний

**Выход:** смена прокси и эндпоинта — правкой конфига, без сборки (тест на
подменённом конфиге); Outbox не теряет и не дублирует сообщение при убийстве
процесса **в каждом состоянии** — тест на каждый переход.

### К4 — срез: текстовое сообщение

Первый сквозной путь. Auth здесь присутствует **как водопровод, без экранов**:
аккаунт заводится харнессом, ключи устройства создаются, JWT получается.

- `domain-chat`: `SendMessage`, `ObserveChat`, репозитории
- `feature-chat` минимальный: список реплик и поле ввода
- отправка и получение через реальный сервер

**Выход:** сообщение уходит и приходит **на Android и на ПК** (решение 8); сценарий
«отправил, обрыв, повтор, доставлено» прогоняется тестом Store без сервера; iOS
компилируется, но не запускается — Apple-железа нет.

### К5 — auth, интерфейс, дизайн-система

- `core-ui`: токены и компоненты из макета (`Layout-UI-light/README.md`), обе темы
  одним набором токенов
- `feature-auth`: вход, код, секретная фраза, QR-привязка — экраны
- Экраны телефона по [интерфейс.md](../doc/интерфейс.md) §3…§9, порядок по частоте
  использования: чат, список чатов, лента, страница
- Планшет и ПК: три полосы, порог 840 dp — одной разметкой, а не второй вёрсткой

**Выход:** каждый экран — чистый рендер `State`; компонент рисуется в двух темах без
правки кода экрана; форматы различает контейнерный запрос.

### К6 — группы, файлы, медиа

- `domain-chat` расширяется группами, `feature-group`
- `core-media`: чанки, превью, `MemoryBudget` (§3.7)
- Вложения в Outbox отдельной записью

**Выход:** файл 100 МБ отправляется без выхода за бюджет памяти; обрыв на 90 %
продолжает с места, а не с начала.

### К7 — звонки и обновления

- `core-call` + `feature-call`; **замер и выбор маршрута для ПК** (§3.8)
- `core-update` по §3.5, включая новое поле `min_client` (сервер раньше клиента)

**Выход:** звонок Android ↔ ПК состоялся; принудительное обновление проверено в обе
стороны.

### К8 — ферма и приёмка

- `test-harness`: отладочный сокет `State`/`Intent`, сценарный DSL, запуск на ферме
- Прогон инвентаря поведения (§5): на каждый пункт — тест
- Закрытие или явный перенос долга по iOS (К2)

**Выход:** сквозной сценарий идёт на ферме на Android и ПК; каждый пункт §5 закрыт
тестом.

> **Старое дерево удаляется не здесь, а до К1** — этап К0 в

## §5. Инвентарь поведения: что вычитать из v1 до удаления

Знание, которого нет ни в одном документе. Каждый пункт становится тестом или

| Откуда | Что забираем |
|---|---|

| `MessageSerializer.kt` | потолок распакованного тела — защита от zstd-бомбы |
| `UpdateInstaller.kt` | проверка подписи и содержимого APK **до** установки |
| `AppUpdate.android.kt` | повадки `DownloadManager` и системного обработчика APK на Samsung |
| `MessageStore.kt` | `requeueStuck`: состояние «отправляется» висит после убийства процесса |
| `EscrowTrust` | ключ подписи конфига анклава зашит в сборку; TOFU отклонён с обоснованием |
| `build.gradle.kts` | стабильная подпись APK: отладочный ключ на каждой машине свой, смена машины сборки давала «приложение конфликтует с другим пакетом» у всех установленных |
| `DeviceLinkQr` | протокол привязки устройства по QR |
| `Session.kt` | **антипример:** список чатов в двух местах разом. В v2 один источник правды |

**Порядок работ с v1:** вычитать инвентарь в `doc_mig/инвентарь-поведения.md` →
поставить тег `ref/client-v1` (исходники остаются собираемы) → строить новый
`client/`. Двух клиентских деревьев в репозитории одновременно нет: две сборки
Gradle, два пути в CI и постоянный соблазн оставить оба.

Собранные `TIMA-*.apk` уже лежат на машине сборки — v1 можно наблюдать в работе, не
держа её исходники в дереве.
