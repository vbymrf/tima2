# Проверка модели 3: видит ли mobile-mcp наши телефоны

Один вопрос отделяет [модель 3](МОДЕЛИ.md) от готовности, и здесь порядок, которым он
закрывается. Двадцать минут, ничего необратимого.

## В чём был вопрос и почему он уже закрыт

Телефоны живут в **adb-сервере на машине заказчика** (`tcp:192.168.189.1:5037`). Claude
Code живёт в гостевой машине VMware, где своего сервера нет и быть не должно.

Клиент `adb` умеет ходить в чужой сервер: переменная `ADB_SERVER_SOCKET` либо флаг `-L`.
Вопрос был в том, дойдёт ли до mobile-mcp эта переменная.

**Прочитано в исходниках 2026-09-14** — копия лежит в
`third-party/reference/mobilecli`, коммит `f7148582b01a`. Устройствами занимается не сам
mobile-mcp, а отдельная программа `mobilecli`, и делает она вот что:

```go
// devices/android.go
cmd := exec.Command(getAdbPath(), cmdArgs...)
```

Три вещи отсюда следуют, и все три в нашу пользу.

**`adb` запускается как внешняя программа.** Не своя реализация протокола, не жёсткий
`127.0.0.1:5037`, а честный вызов бинаря.

**Окружение наследуется целиком.** У `exec.Command` в Go поле `Env` не задано — значит
дочерний процесс получает окружение родителя как есть, вместе с `ADB_SERVER_SOCKET`. Во
всём `mobilecli` `cmd.Env` присваивается ровно один раз, и то в `simulator.go`, то есть на
пути iOS-симулятора, который нас не касается.

**Путь к `adb` берётся из `ANDROID_HOME`**, с запасными вариантами — и Windows среди них
учтён (`adb.exe`, `%LOCALAPPDATA%\Android\Sdk`):

```go
func getAdbPath() string {
    sdkPath := getAndroidSdkPath()      // ANDROID_HOME, затем стандартные места
    if sdkPath != "" {
        adbPath := filepath.Join(sdkPath, "platform-tools", "adb")
        if runtime.GOOS == "windows" { adbPath += ".exe" }
        return adbPath
    }
    return "adb"                        // best effort, из PATH
}
```

**Значит модель 3 наши телефоны увидит.** Порядок ниже — не расследование, а проверка: одно
дело прочитать код, другое — увидеть три строки в выводе. Шаг 3в на случай, если я всё-таки
ошибся, оставлен.

## Шаг 0 — связь жива

**Перед любой работой с телефонами**, правило из
[ПОДКЛЮЧЕНИЕ.md](../ЖУРНАЛ-И-ОТЛАДКА/ПОДКЛЮЧЕНИЕ.md): агент проверяет и **не чинит молча**.

```bash
timeout 5 bash -c 'echo > /dev/tcp/192.168.189.1/5037' && echo открыт || echo закрыт
```

Закрыт — дальше не идти: это на стороне заказчика (сервер не запущен либо брандмауэр).
Разбор — в `ПОДКЛЮЧЕНИЕ.md`, «Разбор поломок», пункты 1 и 2.

Открыт — проверить, что телефоны в нём есть:

```powershell
$adb = "$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe"
& $adb -L tcp:192.168.189.1:5037 devices -l
```

Нужны три строки со словом `device` (не `offline`, не `unauthorized`). Строки с
`_adb-tls-connect._tcp` — те же телефоны, найденные по mDNS; это известная двойственность,
не поломка.

**Это состояние — эталон.** Всё дальнейшее сравнивается с ним: mobile-mcp обязан увидеть
ровно это, и ни одним телефоном меньше.

## Шаг 2 — проверка без установки чего бы то ни было

`npx` скачивает пакет во временный каталог и запускает. **В настройки Claude Code при этом
ничего не пишется**, MCP-сервер не регистрируется, откатывать нечего.

```powershell
$env:ADB_SERVER_SOCKET = "tcp:192.168.189.1:5037"
$env:MOBILEMCP_DISABLE_TELEMETRY = "1"
$env:ANDROID_HOME = "$env:LOCALAPPDATA\Android\Sdk"
$env:PATH = "$env:ANDROID_HOME\platform-tools;$env:PATH"
npx -y @mobilenext/mobile-mcp@latest --version
```

**`MOBILEMCP_DISABLE_TELEMETRY=1` ставится сразу и навсегда.** У пакета есть сбор
статистики (PostHog, Scarf); выключается он этой переменной, и выключить его надо **до**
первого запуска, а не после.

**`adb` в PATH — не формальность.** `mobilecli` требует его именно там; без этого он не
найдёт ни одного устройства и скажет это невнятно.

## Шаг 3 — главный вопрос

MCP-сервер говорит по stdio и сам по себе ничего не печатает. Спросить у него список
устройств можно двумя путями — начинать с первого, он проще.

### Путь А: через mobilecli напрямую

```powershell
npx -y mobilecli@latest devices
```

Это та самая программа, которой mobile-mcp пользуется внутри, и именно её исходники
прочитаны выше. Видит три телефона — вопрос закрыт: видит их **тем же механизмом**, что и
сервер.

Копия исходников — `third-party/reference/mobilecli`; смотреть там, а не в вебе.

### Путь Б: через сам MCP-сервер

Если путь А не сработал или хочется проверить именно сервер:

```powershell
claude mcp add mobile-mcp --env ADB_SERVER_SOCKET=tcp:192.168.189.1:5037 --env MOBILEMCP_DISABLE_TELEMETRY=1 -- npx -y @mobilenext/mobile-mcp@latest
```

Затем в разговоре с Claude Code вызвать `mobile_list_available_devices`.

**Это уже правка настроек**, и её надо уметь откатить:

```powershell
claude mcp remove mobile-mcp
```

## Что означает увиденное

| Что видно | Что это значит | Что делать |
|---|---|---|
| **Три телефона** | модель 3 живая, `ADB_SERVER_SOCKET` доехал | идти к шагу 4 |
| Список пуст, `adb devices` те же три показывает | переменная не доехала: либо программа ходит в adb своей реализацией на `127.0.0.1:5037`, либо не наследует окружение | шаг 3в |
| `adb not found` | `adb` не в PATH процесса | поправить PATH в той же строке, что запускает npx |
| Ошибка сети или npm | пакет не скачался | это про сеть, а не про модель |
| Один телефон вместо трёх | видит, но выбирает сам | искать в `mobilecli devices` способ назвать устройство |

### Шаг 3в — если переменная не доехала

Три обхода, от дешёвого к дорогому:

1. **Туннель в госте.** Поднять локальное перенаправление `127.0.0.1:5037` →
   `192.168.189.1:5037` внутри гостевой машины. Тогда программе, жёстко идущей на петлю,
   отвечает сервер хоста, и ничего менять не надо:
   ```powershell
   netsh interface portproxy add v4tov4 listenaddress=127.0.0.1 listenport=5037 `
     connectaddress=192.168.189.1 connectport=5037
   ```
   Откат: та же команда с `delete` вместо `add`.
   **Осторожно:** пока перенаправление стоит, обычный `adb` в госте тоже пойдёт на хост.
   Это скорее хорошо, но знать надо.

2. **Пробросить телефон по USB в гостя** — `Player → Removable Devices → <телефон> →
   Connect`. Работает для одного телефона за раз и рвёт его связь с хостом. Годится, чтобы
   доказать, что mobile-mcp вообще умеет наш телефон, но не для прогона на трёх.

3. **Запускать mobile-mcp на хосте** в режиме HTTP (`--listen`) и ходить в него из гостя по
   сети. Самый гибкий путь и самый дорогой: чужая программа переезжает на машину заказчика,
   а это ровно то, чего мы избегаем в [модели 2](УСТАНОВКА-МОДЕЛИ-2.md).

**Первый обход пробовать первым.** Он обратим одной командой и ничего не ставит на машину
заказчика.

## Шаг 4 — умеет ли он то, ради чего затевалось

Список устройств — половина ответа. Вторая половина: **читает ли он дерево элементов**, из-за
которого модель 3 и выбрана. Без него она превращается в модель 1 с лишней прослойкой.

Разбудить телефон и спросить содержимое экрана:

```
mobile_list_elements_on_screen
```

**Должно вернуться текстом:** список элементов с именами и координатами. Если вместо этого
приходит картинка — «accessibility-first» у нас не работает, и весь выигрыш по токенам и
скорости исчезает. Это надо выяснить **до** того, как под модель 3 напишутся сценарии.

Дальше проверить по одному действию каждого вида, на **realme** (самый быстрый на снимках):

| Что | Чем |
|---|---|
| Запуск приложения | `mobile_launch_app` |
| Нажатие | `mobile_click_on_screen_at_coordinates` |
| Ввод текста | `mobile_type_keys` — **проверить кириллицу**, `adb shell input text` её не умеет |
| Свайп | `mobile_swipe_on_screen` |
| Пачка | `mobile_batch_commands` — ради него всё и затевалось |
| Журнал | `mobile_get_device_logs` |

**Кириллица в поле ввода — отдельная проверка, и она не формальность.** `adb shell input
text` кириллицу не набирает вовсе; если mobile-mcp обходит это своим способом — прекрасно,
если нет — половина наших сценариев (имя контакта, название группы, текст сообщения) не
пишется, и это надо знать заранее.

## Чего в этой проверке нет

- **Трёх телефонов одновременно.** Проверяется после того, как заработает один: умеет ли
  mobile-mcp держать три устройства параллельно и как их называть в командах. Если не умеет
  — это меняет оценку времени втрое, потому что сценарии пойдут по очереди.
- **iOS.** Отдельный разговор — [ДОСТУП-К-IOS.md](ДОСТУП-К-IOS.md).
- **Работы в CI.** У mobile-mcp её из коробки нет; появится нужда — писать самим.
