# Проверка модели 3: что выяснилось и что осталось

Прогон 2026-09-14. Порядок ниже пройден, и **половина ответила не так, как обещал код**:
телефоны она видит, а дерева элементов не отдаёт — и оставляет на телефоне след, который
ломает штатный `uiautomator`.

| | Состояние |
|---|---|
| Видит наши телефоны через сервер хоста | **да, проверено** |
| Отдаёт дерево элементов текстом | **нет** — открытый вопрос, шаг 4 |
| Оставляет следы на телефоне | **да**: `/data/local/tmp/mobilecli.dex` и висящий `app_process` |
| Кириллица в поле ввода | не проверено |

> ### ⚠ Прежде чем запускать это снова
>
> `mobilecli` кладёт на телефон свой агент и **не убирает его за собой**. Пока агент висит,
> штатный `adb exec-out uiautomator dump` не работает **ни у кого** — отвечает `Killed`. Это
> выглядит как поломка телефона, а не как след чужой программы, и найти причину без этой
> записи стоит часа.
>
> Убрать после работы, на каждом телефоне, который трогали:
>
> ```powershell
> adb -s <устройство> shell "ps -A | grep app_process"      # найти pid
> adb -s <устройство> shell kill <pid>
> adb -s <устройство> shell rm -f /data/local/tmp/mobilecli.dex
> ```
>
> Проверить, что вылечилось: `adb -s <устройство> exec-out uiautomator dump /dev/tty`
> обязан вернуть XML, а не `Killed`.

## В чём был вопрос и почему он уже закрыт

Телефоны живут в **adb-сервере на машине заказчика** (`tcp:192.168.189.1:5037`). Claude
Code живёт в гостевой машине VMware, где своего сервера нет и быть не должно.

Клиент `adb` умеет ходить в чужой сервер: переменная `ADB_SERVER_SOCKET` либо флаг `-L`.
Вопрос был в том, дойдёт ли до mobile-mcp эта переменная.

**Прочитано в исходниках 2026-09-14** — копия лежит в
`third-party/reference/mobilecli`, коммит `f7148582b01a`. Устройствами занимается не сам
mobile-mcp, а отдельная программа `mobilecli`, и делает она вот что:

```go
// devices/android.go
cmd := exec.Command(getAdbPath(), cmdArgs...)
```

Три вещи отсюда следуют, и все три в нашу пользу.

**`adb` запускается как внешняя программа.** Не своя реализация протокола, не жёсткий
`127.0.0.1:5037`, а честный вызов бинаря.

**Окружение наследуется целиком.** У `exec.Command` в Go поле `Env` не задано — значит
дочерний процесс получает окружение родителя как есть, вместе с `ADB_SERVER_SOCKET`. Во
всём `mobilecli` `cmd.Env` присваивается ровно один раз, и то в `simulator.go`, то есть на
пути iOS-симулятора, который нас не касается.

**Путь к `adb` берётся из `ANDROID_HOME`**, с запасными вариантами — и Windows среди них
учтён (`adb.exe`, `%LOCALAPPDATA%\Android\Sdk`):

```go
func getAdbPath() string {
    sdkPath := getAndroidSdkPath()      // ANDROID_HOME, затем стандартные места
    if sdkPath != "" {
        adbPath := filepath.Join(sdkPath, "platform-tools", "adb")
        if runtime.GOOS == "windows" { adbPath += ".exe" }
        return adbPath
    }
    return "adb"                        // best effort, из PATH
}
```

**Значит модель 3 наши телефоны увидит.** Порядок ниже — не расследование, а проверка: одно
дело прочитать код, другое — увидеть три строки в выводе. Шаг 3в на случай, если я всё-таки
ошибся, оставлен.

## Шаг 0 — связь жива

**Перед любой работой с телефонами**, правило из
[ПОДКЛЮЧЕНИЕ.md](../ЖУРНАЛ-И-ОТЛАДКА/ПОДКЛЮЧЕНИЕ.md): агент проверяет и **не чинит молча**.

```bash
timeout 5 bash -c 'echo > /dev/tcp/192.168.189.1/5037' && echo открыт || echo закрыт
```

Закрыт — дальше не идти: это на стороне заказчика (сервер не запущен либо брандмауэр).
Разбор — в `ПОДКЛЮЧЕНИЕ.md`, «Разбор поломок», пункты 1 и 2.

Открыт — проверить, что телефоны в нём есть:

```powershell
$adb = "$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe"
& $adb -L tcp:192.168.189.1:5037 devices -l
```

Нужны три строки со словом `device` (не `offline`, не `unauthorized`). Строки с
`_adb-tls-connect._tcp` — те же телефоны, найденные по mDNS; это известная двойственность,
не поломка.

**Это состояние — эталон.** Всё дальнейшее сравнивается с ним: mobile-mcp обязан увидеть
ровно это, и ни одним телефоном меньше.

## Шаг 2 — проверка без установки чего бы то ни было

`npx` скачивает пакет во временный каталог и запускает. **В настройки Claude Code при этом
ничего не пишется**, MCP-сервер не регистрируется, откатывать нечего.

```powershell
$env:ADB_SERVER_SOCKET = "tcp:192.168.189.1:5037"
$env:MOBILEMCP_DISABLE_TELEMETRY = "1"
$env:ANDROID_HOME = "$env:LOCALAPPDATA\Android\Sdk"
$env:PATH = "$env:ANDROID_HOME\platform-tools;$env:PATH"
npx -y @mobilenext/mobile-mcp@latest --version
```

**`MOBILEMCP_DISABLE_TELEMETRY=1` ставится сразу и навсегда.** У пакета есть сбор
статистики (PostHog, Scarf); выключается он этой переменной, и выключить его надо **до**
первого запуска, а не после.

**`adb` в PATH — не формальность.** `mobilecli` требует его именно там; без этого он не
найдёт ни одного устройства и скажет это невнятно.

## Шаг 3 — главный вопрос · **пройден, ответ «да»**

MCP-сервер говорит по stdio и сам по себе ничего не печатает. Спросить список устройств
проще у `mobilecli` — той самой программы, которой mobile-mcp пользуется внутри.

### Путь А: через mobilecli напрямую

**В npm пакета с именем `mobilecli` для этого нет** — и это не мелочь: имя занято
[совсем другим проектом](МОДЕЛИ.md#два-тёзки-и-одна-путаница-по-названию), который
транслирует терминал на телефон. Поставить не то легко.

Нужный бинарь лежит в пакетах вида `@mobilenext/mobilecli-<платформа>-<архитектура>`:

```powershell
mkdir mc; cd mc
npm install "@mobilenext/mobilecli-windows-amd64"
$bin = ".\node_modules\@mobilenext\mobilecli-windows-amd64\mobilecli-windows-amd64.exe"

$env:ADB_SERVER_SOCKET = "tcp:192.168.189.1:5037"
$env:ANDROID_HOME = "$env:LOCALAPPDATA\Android\Sdk"
$env:PATH = "$env:ANDROID_HOME\platform-tools;$env:PATH"
& $bin devices
```

Путь к бинарю можно задать и переменной `MOBILECLI_PATH` — тогда сам mobile-mcp возьмёт
указанный.

**Что вышло 2026-09-14** — версия `mobilecli 1.0.10`, все три телефона на месте, и с именами
получше, чем даёт `adb`:

```
realme C25Y     192.168.3.193:46843   Android 11   online
Galaxy A40      192.168.3.226:35273   Android 11   online
Redmi A3        192.168.3.235:43083   Android 16   online
```

**`ADB_SERVER_SOCKET` доехал ровно так, как обещал исходник.** Горлышко пройдено.

Копия исходников — `third-party/reference/mobilecli`; смотреть там, а не в вебе.

### Путь Б: через сам MCP-сервер

Если путь А не сработал или хочется проверить именно сервер:

```powershell
claude mcp add mobile-mcp --env ADB_SERVER_SOCKET=tcp:192.168.189.1:5037 --env MOBILEMCP_DISABLE_TELEMETRY=1 -- npx -y @mobilenext/mobile-mcp@latest
```

Затем в разговоре с Claude Code вызвать `mobile_list_available_devices`.

**Это уже правка настроек**, и её надо уметь откатить:

```powershell
claude mcp remove mobile-mcp
```

## Что означает увиденное

| Что видно | Что это значит | Что делать |
|---|---|---|
| **Три телефона** | модель 3 живая, `ADB_SERVER_SOCKET` доехал | идти к шагу 4 |
| Список пуст, `adb devices` те же три показывает | переменная не доехала: либо программа ходит в adb своей реализацией на `127.0.0.1:5037`, либо не наследует окружение | шаг 3в |
| `adb not found` | `adb` не в PATH процесса | поправить PATH в той же строке, что запускает npx |
| Ошибка сети или npm | пакет не скачался | это про сеть, а не про модель |
| Один телефон вместо трёх | видит, но выбирает сам | искать в `mobilecli devices` способ назвать устройство |

### Шаг 3в — если переменная не доехала

Три обхода, от дешёвого к дорогому:

1. **Туннель в госте.** Поднять локальное перенаправление `127.0.0.1:5037` →
   `192.168.189.1:5037` внутри гостевой машины. Тогда программе, жёстко идущей на петлю,
   отвечает сервер хоста, и ничего менять не надо:
   ```powershell
   netsh interface portproxy add v4tov4 listenaddress=127.0.0.1 listenport=5037 `
     connectaddress=192.168.189.1 connectport=5037
   ```
   Откат: та же команда с `delete` вместо `add`.
   **Осторожно:** пока перенаправление стоит, обычный `adb` в госте тоже пойдёт на хост.
   Это скорее хорошо, но знать надо.

2. **Пробросить телефон по USB в гостя** — `Player → Removable Devices → <телефон> →
   Connect`. Работает для одного телефона за раз и рвёт его связь с хостом. Годится, чтобы
   доказать, что mobile-mcp вообще умеет наш телефон, но не для прогона на трёх.

3. **Запускать mobile-mcp на хосте** в режиме HTTP (`--listen`) и ходить в него из гостя по
   сети. Самый гибкий путь и самый дорогой: чужая программа переезжает на машину заказчика,
   где живут телефоны, adb-сервер и ключи.

**Первый обход пробовать первым.** Он обратим одной командой и ничего не ставит на машину
заказчика.

## Шаг 4 — дерево элементов · **не работает, причина найдена**

Список устройств — половина ответа. Вторая половина: **читает ли он дерево элементов**, из-за
которого модель 3 и выбиралась. Без него она превращается в модель 1 с лишней прослойкой.

**Не читает.** На всех трёх телефонах, четырнадцать с половиной секунд на попытку:

```
mobilecli dump ui --device <устройство>
→ failed to get view tree dump: no XML content found in uiautomator dump
```

### Почему — видно в коде и подтвердилось на устройстве

`DumpSourceRaw` сперва пытается поднять **свой агент** (`getDeviceServerDump`): кладёт
`mobilecli.dex` в `/data/local/tmp/` и запускает `app_process`. У нас этот путь не встаёт, и
он откатывается на штатный `uiautomator`:

```go
output, err := d.runAdbCommand("exec-out", "uiautomator", "dump", "/dev/tty")
```

**Откат падает из-за собственного же агента.** Тот остался висеть и держит мост
доступности; второму клиенту `uiautomator` отвечает `Killed`, XML не находится, и ошибка
получается о `uiautomator`, хотя виноват агент.

Проверено перебором: **до** запуска `mobilecli` штатный `adb exec-out uiautomator dump`
отдавал 23 и 40 тысяч знаков XML на Samsung и Redmi; **после** — `Killed` на всех трёх; после
снятия процесса и удаления файла — снова 11–39 тысяч знаков.

### Причина найдена · `adb forward` при удалённом сервере

Разобрано 2026-09-14 по исходникам и доказано опытом.

`startDeviceServer` делает четыре шага: кладёт `mobilecli.dex` на телефон, запускает
`app_process`, просит `adb forward tcp:0 localabstract:mobilecli-server` — и **опрашивает
получившийся порт**:

```go
// devices/android_rpc.go
http.NewRequestWithContext(..., fmt.Sprintf("http://localhost:%d/", port), body)
```

**`localhost` — вот и вся беда.**

`adb forward` открывает слушающий сокет **в процессе adb-сервера**, то есть на той машине,
где сервер. У нас сервер на хосте, а `mobilecli` работает в гостевой машине. Порт
открывается на хосте; опрашивается `localhost` гостя, где пусто.

Проверено насквозь:

| Что проверяли | Ответ |
|---|---|
| `adb forward tcp:0 …` назначил порт | `50342` |
| `127.0.0.1:50342` из гостя | **закрыт** |
| `192.168.189.1:50342` (хост) из гостя | **открыт** |
| `POST {}` на хостовый порт | **`HTTP 204` — агент ответил** |

**Агент на телефоне поднимается и работает.** Не работает одно: `mobilecli` не может до него
достучаться, потому что стучится не туда. Пять секунд ожидания, откат на `uiautomator` — а
тот уже сломан собственным висящим агентом.

**Это не дефект mobilecli и не свойство наших телефонов.** Это свойство `adb`: при удалённом
сервере клиент и проброшенный порт оказываются на разных машинах. Касается **любого**
инструмента, который поднимает агента на устройстве и ходит к нему через `adb forward`.

Дефект у mobilecli всё же есть, и отдельный: **не подняв сервер, он не убирает за собой
агента** — снимает только проброс. Висящий агент ломает и его собственный запасной путь, и
штатный `uiautomator` для кого угодно.

### Чем это лечится

| Путь | Что даёт | Чего стоит |
|---|---|---|
| **Поднять mobile-mcp на хосте** в режиме `--listen`, ходить из гостя по HTTP | проброс и опрос на одной машине — должно заработать целиком | один сетевой сервис на машине заказчика. **Не переезд Claude Code**: сам агент остаётся в госте |
| Пробросить телефон по USB в гостя | свой adb-сервер в госте, всё локально | один телефон за раз, рвёт связь телефона с хостом |
| Править `localhost` на адрес хоста | однострочная правка | форк чужого инструмента, поддерживать вечно |
| Проброс портов наперёд | — | **не выйдет**: порт назначается `tcp:0`, случайный, заранее неизвестен |

**Первый путь рабочий, и его стоит проверить.** Он превращает открытый вопрос в решённый
либо закрывает модель 3 окончательно.

### Что ещё выяснить

| Что | Как проверить |
|---|---|
| mobile-mcp на хосте с `--listen` | поднять и сходить из гостя по HTTP |
| `uiautomator` без агента вовсе | есть ли у `mobilecli` способ не пытаться поднимать свой сервер |

**Второе тоже стоит проверить.** Штатный `uiautomator` на всех трёх телефонах отдаёт
дерево — значит модель 3 могла бы работать и без своего агента, просто медленнее.

### И то, что надо измерить, даже когда заработает

**Сырое дерево — 11–39 КБ**, то есть **3–12 тысяч токенов**. Снимок экрана — полторы тысячи.
Значит «текст дешевле картинки» **неверно для сырого дерева**, и весь выигрыш сидит в
отборе, который делает `format-elements.ts`.

Мерить надо **отобранный** список: сколько токенов занимает один экран нашего приложения
после отбора. Пока это не измерено, выигрыш модели 3 по токенам — предположение.

Дальше — по одному действию каждого вида, на **realme** (самый быстрый на снимках). Это
делается, **когда дерево заработает**: без него проверять нечего.

| Что | Чем |
|---|---|
| Запуск приложения | `mobile_launch_app` |
| Нажатие | `mobile_click_on_screen_at_coordinates` |
| Ввод текста | `mobile_type_keys` — **проверить кириллицу**, `adb shell input text` её не умеет |
| Свайп | `mobile_swipe_on_screen` |
| Пачка | `mobile_batch_commands` — ради него всё и затевалось |
| Журнал | `mobile_get_device_logs` |

**Кириллица в поле ввода — отдельная проверка, и она не формальность.** `adb shell input
text` кириллицу не набирает вовсе; если mobile-mcp обходит это своим способом — прекрасно,
если нет — половина наших сценариев (имя контакта, название группы, текст сообщения) не
пишется, и это надо знать заранее.

## Чего в этой проверке нет

- **Трёх телефонов одновременно.** Проверяется после того, как заработает один: умеет ли
  mobile-mcp держать три устройства параллельно и как их называть в командах. Если не умеет
  — это меняет оценку времени втрое, потому что сценарии пойдут по очереди.
- **iOS.** Отдельный разговор — [ДОСТУП-К-IOS.md](ДОСТУП-К-IOS.md).
- **Работы в CI.** У mobile-mcp её из коробки нет; появится нужда — писать самим.
