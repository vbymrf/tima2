# План: буфер переходов

Заведён 2026-10-21 по слову заказчика: «Переделываем кнопки перехода… нужно хранить определенные точки… По
сути имеем буффер на клиенте переходов»; после разбора — «один буффер для сообщества / чата… на сервер не
уходит… назад очищает», затем «4. Составляй планы»; дополнен 2026-10-21 — «п4 — делаем общим правилом для всех
переходов, одинаковые точки не дописываются», буфер сохраняется после закрытия приложения («3. да»).
Указатели — [ПЛАН-(УК)](ПЛАН-(УК)-УКАЗАТЕЛЕЙ.md); здесь — только их точка «из Указателей».
Продолжает [РЕДАКТОР-СООБЩЕНИЙ.md](РЕДАКТОР-СООБЩЕНИЙ.md) §11.4 (переходы).

**Статус 2026-10-21: план, работ нет.**

## 0. Что уже есть

- `FeedJumps` (`client/feature/feature-chat/.../FeedJumps.kt`): два списка, «назад» и «вперёд», в памяти
  окна переписки (`remember` в `ChatScreen.kt`) — вышли из переписки, всё забыто; предела нет.
- При переходе запоминается **сообщение у нижнего края экрана** (`anchorOf`), а не само сообщение со
  ссылкой; куда перешли — не запоминается.
- «Назад» появляется сразу после перехода; новый переход стирает «вперёд»; долгое нажатие на «назад» —
  цепочка забыта.
- Переход по ссылке на сообщение **другой переписки не делается** (`ChatScreen.kt`: только своя).
- Сообщения нет на устройстве — переход молча не происходит.

## 1. Решения (заказчик 2026-10-21)

| Что | Решение |
|---|---|
| Сколько буферов | **один на сообщество** (все его переписки) и **один на каждую переписку вне сообщества** — группу, канал, личную |
| Где хранится | **на устройстве**, на сервер не уходит; закрыли приложение — буфер остаётся (подтверждено) |
| Предел | **20 точек**; старые вытесняются |
| Точки перехода | **«откуда»** — само сообщение со ссылкой; **«куда»** — сообщение, на которое перешли. Обе дописываются **в конец** |
| Точка «куда» | записывается сразу, **работать начинает после сдвига ленты** — когда сообщение целиком ушло с экрана |
| «Назад», «вперёд» | ходят по списку точек: «назад» — к точке «куда», ещё раз — к «откуда», и дальше к прежним; «вперёд» — обратно |
| Новый переход | пишется **в конец**; «вперёд» не стирается, место в списке — в конец |
| Одинаковые точки | **подряд одинаковые не дописываются** — общее правило всех переходов: дважды та же ссылка, повторный приход из «Указателей» — одна точка |
| Точка «из Указателей» | переход по указателю пишет первой точкой «из Указателей»; «назад» до неё возвращает во вкладку «Указатели» той же сущности ([ПЛАН-(УК)](ПЛАН-(УК)-УКАЗАТЕЛЕЙ.md)) |
| Долгое нажатие на «назад» | **очищает** буфер |
| «Вниз» | без изменений |

## 2. Этапы

### БП1. Буфер — чистая модель

- `JumpBuffer` в `domain-chat`: точки `(chatId, serverId, kind: FROM | TO | POINTERS, live)`, место в
  списке, предел 20; `jumped(from, to)`, `left(to)` (точка «куда» ожила), `back()`, `forward()`, `clear()`.
  Точка, равная последней, не дописывается.
- Ключ буфера — как у подборки (`MessagePicks.levelOf`), но личная переписка — своя:
  `community:<id>` | `group:<id>` | `channel:<id>` | `personal:<chatId>`.
- Тесты: порядок «назад»/«вперёд», дописывание в конец без стирания, неживая точка «куда»
  пропускается, вытеснение двадцать первой, очистка, одинаковые подряд — одна точка, «назад» до точки
  «из Указателей» — выход во вкладку.

### БП2. Хранение на устройстве

- Таблица `jump_points` в базе устройства (`core-database`, миграция SQLDelight): ключ буфера, порядок,
  переписка, номер, вид, живая ли; место в списке — там же. Около 60 байт на точку, до 1–2 КБ на буфер.
- Смена учётной записи — у каждой свои буферы (как у прочих таблиц).

### БП3. Лента: запись и кнопки

- `FeedJumps` берёт буфер по ключу переписки вместо двух списков в памяти. Переход по ссылке, ответу,
  закреплённому, «Продолжить чтение» дописывает «откуда» = сообщение, на котором нажали, и «куда».
- «Куда» оживает, когда сообщение целиком ушло с экрана (по `visibleItemsInfo`).
- Кнопки «назад» и «вперёд» — как сейчас, видны, когда есть куда; долгое «назад» — очистка.
- Удалённое или недоступное сообщение — точка пропускается и выбрасывается.

### БП4. Переходы между переписками сообщества

- Ссылка на сообщение другой переписки того же сообщества — открыть ту переписку и перейти; «назад» в
  буфере сообщества возвращает в прежнюю переписку.
- Сообщения нет на устройстве — догрузить историю до него; не вышло — подсказка и точка пропускается.
  Есть ли у сервера выдача «вокруг номера» — проверить до начала этапа.
- Ссылка на переписку вне сообщества — переход как сейчас не делается (решить отдельно).

### БП5. Журнал, сценарии, проверка

- Код журнала перехода дополняется ключом буфера и числом точек (без номеров переписок в открытом виде).
- Сценарий `maestro/` перехода (`ref-jump.yaml`) — «назад» к сообщению со ссылкой; строки окна в
  [СЦЕНАРИИ-ПО-ОКНАМ.md](ФУНКЦИОНАЛ/АВТОТЕСТЫ/СЦЕНАРИИ-ПО-ОКНАМ.md).
- Только клиент: сервер не меняется.
