# Сценарии Maestro

Живые сценарии для прогона на телефонах — модель 4. Про сами модели и выбор между
ними — [../doc_mig/ТЕСТЫ-НА-ТЕЛЕФОНАХ/](../doc_mig/ТЕСТЫ-НА-ТЕЛЕФОНАХ/README.md),
про устройство инструмента — [КАК-РАБОТАЮТ-МОДЕЛИ/MAESTRO.md](../doc_mig/ТЕСТЫ-НА-ТЕЛЕФОНАХ/КАК-РАБОТАЮТ-МОДЕЛИ/MAESTRO.md).

## Почему папка здесь, а не в документации

Путь к сценарию передаётся в командную строку Windows. Кириллица в нём ломается о
кодировку консоли — то самое, из-за чего в проекте заведено правило про латиницу в
именах файлов кода. Сценарий — код, и живёт он по этому правилу.

## Как запускать

```bash
MAESTRO_DRIVER_STARTUP_TIMEOUT=180000 \
  maestro --device 192.168.3.193:46843 test maestro/update.yaml
```

**Таймаут обязателен.** По сетевому adb драйвер Maestro не успевает встать за
отведённое по умолчанию время, и прогон виснет молча, без единой строки.

Артефакты каждого прогона — `~/.maestro/tests/<дата_время>/`: `commands.json` со
статусом по каждому шагу, снимки, дерево упавшего шага, журнал телефона.

## Что есть

| Файл | Что проверяет | Состояние |
|---|---|---|
| `update.yaml` | обновление из меню: развилка «есть что обновлять» / «уже последняя» | **3 из 3 телефонов параллельно**, 4 м 39 с на всё, 2026-09-16 |
| `update-install.yaml` | вторая половина: от «Обновить» до «Обновление установлено» | зовётся из `update.yaml` по условию, отдельно не запускается |
| `wake-phone.sh` | не сценарий — подготовка телефона перед прогоном | обязателен, см. ниже |

**Почему сценарий разрезан надвое.** Сервер отвечает одним из двух — «Обновить» или
«Установлена последняя версия», — и заранее неизвестно, чем. Прежде вторая половина шла
безусловно, и телефон, уже стоявший на свежей версии, падал на шаге «Установить»:
обновлять было нечего. Падение при этом выглядело как поломка обновления. Теперь оба
исхода — успех, и в каждом делается снимок: без снимка «нечего обновлять» неотличимо от
«сценарий ушёл не туда».

## Что нужно телефону, чтобы `update.yaml` прошёл целиком

1. **Не спящий телефон** — `sh maestro/wake-phone.sh --all` перед прогоном. Причина
   расписана в самом скрипте и повторена ниже: спящий телефон притворяется чем угодно.
2. **Старая версия приложения**, если проверяется именно установка. Без неё сценарий
   пройдёт по короткой ветке «уже последняя» — это честный успех, но установку он не
   проверит. Телефон для отката — Samsung, порядок отката ниже.
3. **Аккаунт** — экран обновления за входом.
4. **Play Защита выключена**: `adb shell settings put global package_verifier_user_consent -1`
   (решение заказчика 2026-09-15; вернуть — то же с `1`). Иначе сценарий остановится на её
   окне явно, с причиной.

### Вернуть Samsung на старую версию после прогона

**Не `adb install -d`.** Между версиями бывает миграция базы, и после отката пакета
приложение падает на старте: `Can't downgrade database from version 8 to 7` — поймано
2026-09-15. Правильно так:

```bash
adb shell pm clear io.tima.app.v2          # стирает базу и аккаунт на телефоне
adb install -r -d TIMA-<старая>.apk
```

Дальше в приложении: номер → код (стенд отдаёт его на экране) → «Вход по фразе» → двенадцать
слов из `doc_mig/ВЕРСИИ/ТЕЛЕФОНЫ.local.md`. Три минуты, проверено дважды.

## Три телефона сразу

```bash
sh maestro/wake-phone.sh --all
MAESTRO_DRIVER_STARTUP_TIMEOUT=240000   maestro --device адрес1,адрес2,адрес3 test --shard-all=3 maestro/update.yaml
```

Работает. 2026-09-16: 3 из 3, 4 м 39 с на все три (по отдельности вышло бы около
одиннадцати минут). Ветки идут каждая в своём телефоне и друг другу не мешают.

### Вывод, который был неверным, и как он получился

Первый параллельный прогон дал 0 из 3, и я записал причину так: «Maestro не
параллелится из-за adb — сервер один, ветки дерутся за него». **Это неправда**, и
проверять надо было не рассуждением, а снимком.

На снимках упавших шагов был **чёрный экран**. `screen_off_timeout` оказался 30 000 у
Redmi и 60 000 у realme: пока одна ветка ставила приложение, соседние телефоны гасли и
падали на `launchApp` — каждый в свой момент, отчего это и выглядело как драка за общий
ресурс. После `wake-phone.sh` та же команда прошла 2 из 2, а затем 3 из 3.

**Отдельно: `stay_on_while_plugged_in` здесь бесполезен.** Стендовые телефоны стоят НЕ на
зарядке — `dumpsys battery` показывает `ACpowered:false USBpowered:false
Wirelesspowered:false`, уровни 48 / 74 / 78 %. По сетевому adb «подключён» не значит
«питается», и настройка не срабатывает вовсе. Держит экран только
`screen_off_timeout`, и он выставлен в сутки. **Отсюда следствие, о котором надо помнить:
телефоны теперь разряжаются заметно быстрее.** Либо ставить их на зарядку, либо вернуть
таймаут после серии прогонов.

### Драйвер Maestro на телефоне

Драйвер нужен, ставится сам и **остаётся на телефоне после прогона**. Обмерено на Redmi:

```
до прогона    пакетов dev.mobile.maestro*  — 0
во время      dev.mobile.maestro, dev.mobile.maestro.test  — 2
после         те же 2
```

То есть ставится он каждый раз заново (в начале прогона), а убирается — никогда. Сам по
себе он ничего не делает, но это чужие пакеты на устройстве, и знать про них надо. Убрать:
`adb uninstall dev.mobile.maestro` и `dev.mobile.maestro.test`. Пропустить переустановку в
начале — `--no-reinstall-driver`, но тогда при расхождении версий прогон встанет молча.

## Что менялось на стендовых телефонах ради прогонов

Всё это — правки чужих устройств, и здесь они записаны, чтобы было что откатывать.

| Настройка | Стало | Было | Переживает перезагрузку |
|---|---|---|---|
| `global package_verifier_user_consent` | `-1` (Play Защита молчит) | `1` | да |
| `system screen_off_timeout` | `86400000` (сутки) | 30 000 Redmi, 60 000 realme | да |
| `global stay_on_while_plugged_in` | `7` | `0` | да, но **без эффекта**: телефоны не на питании |
| `dumpsys deviceidle disable` | выключен Doze | включён | нет |
| пакеты `dev.mobile.maestro*` | стоят | не было | да |

## Правила для сценариев этой папки

**`clearState` не применять.** Он стирает аккаунт. Проверяем поведение на живом
устройстве, а не на чистом.

**До установки новой версии отбор только по надписям.** Метки (`window:`, `tab:`,
`settings:`) заведены в версии 10 — сценарий обновления начинается на старой версии,
где их нет ни одной.

**Отбор по тексту — полное совпадение по регулярному выражению, а не вхождение.**
`"Установлена"` не найдёт узел «Установлена 2.0.9-dev-v2 (9)». Нужно `.*Установлена.*`.

**К системным окнам привязываться по идентификатору, а не по надписи.** Вендор
переписывает и вопрос, и кнопки: на Redmi «Обновить приложение? / Обновить», на
realme «Установить обновление для этого приложения? / УСТАНОВИТЬ». Положительная
кнопка у обоих — `android:id/button1`.
