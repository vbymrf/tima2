# Звонки: медиа, восстановление связи, групповые звонки

> **Статус:** согласовано 2026-07-30. Не канон — рабочий документ, из которого правки
> уходят в `doc/`. Прежняя редакция была черновиком для согласования и заменена целиком.
> Что уже внесено в канон — §6.

---

## 1. Главное решение: в работу LiveKit не вмешиваемся

Качество медиа — зона ответственности LiveKit. Своей лестницы деградации у продукта
**нет**.

| Механизм | Кто отвечает |
|---|---|
| Simulcast, слои публикации | LiveKit |
| Выбор слоя на подписчика | SFU |
| Adaptive Stream, Dynacast | SDK / SFU |
| Понижение битрейта при заторе | WebRTC |
| ICE restart и full reconnect | LiveKit |
| Тайминги восстановления | конфигурация LiveKit |

Клиент не задаёт пресетов публикации, не подписывается на качество ради собственных
решений, не держит таймеров и не ставит видео на паузу по своему усмотрению. Принцип —
**максимальная совместимость с тем, что LiveKit уже реализовал.**

### Что из-за этого решения не делается

Ранее предполагалось и **отменено**:

- лестница деградации с собственными ступенями;
- автоматическая пауза видео с сохранением звука по порогу качества;
- гистерезис возврата видео и флаг «кто выключил камеру»;
- пресеты захвата и описание слоёв (720/540/360/180);
- собственный таймер обрыва в клиенте;
- grace-период поверх `ParticipantDisconnected` — событию LiveKit доверяем как есть.

## 2. Транспорт

**Все звонки, включая 1:1, идут через LiveKit SFU.** Отдельного P2P-транспорта нет и
не планируется — так работает код, и канон приведён к нему
([ADR-0006](../doc/adr/0006-livekit-media-policy.md) Поправка-1).

## 3. Восстановление связи и обрыв

- Окно автоматического восстановления — **30 секунд**, задаётся **в конфигурации
  LiveKit**, не в коде.
- Восстановление внутри окна — штатное поведение, а не событие продукта.
- Источник правды о составе комнаты — **вебхуки LiveKit**: `participant_joined`,
  `participant_left`, `room_finished`. Бэкенд обновляет состояние звонка по ним и не
  ведёт параллельного учёта.

После терминального обрыва:

| Тип звонка | Поведение |
|---|---|
| **1:1** | Звонок завершён для обоих. Повторного входа нет — только новый звонок |
| **Группа** | Выпавший может войти обратно в тот же активный `call_id`. Право — только у приглашённых и только пока звонок Active |

Не ответивший участник группового звонка может войти в него впервые, пока звонок жив.

## 4. Что предстоит реализовать

Единственный объём работ по звонкам — **групповые звонки**. Это сигналинг и состояние
на нашей стороне; SFU про наши звонки ничего не знает.

| Задача | Почему только мы |
|---|---|
| Групповой звонок как сущность | Сейчас `calls` — это `initiator_id` + `peer_id`. Таблицы участников нет |
| Состав приглашённых и право на вход | LiveKit пускает любого с валидным токеном; кому его выдать, решаем мы |
| Выдача токена на вход и повторный вход | Токен на участника, с правами; при возвращении — новый |
| Обработчик вебхуков LiveKit | **Сейчас отсутствует полностью** — ни одного упоминания в коде сервера |
| Уведомления о звонке | WS-события и пуш — не зона LiveKit |

### Настройки, которые надо привести в порядок

- **TURN выключен** (`turn.enabled: false` в `livekit.yaml`). Участник за строгим NAT
  не подключится. На 1:1 иногда проскакивает, в группе из пяти человек вероятность,
  что кому-то не повезёт, высокая — и выглядеть это будет как «звонки не работают».
- **Умолчания комнаты не заданы** ни одним параметром. Раз тайминги отданы LiveKit,
  задать их надо осознанно. Точные имена ключей — по конфигурации LiveKit 2.x.

## 5. Интерфейс

- Состояния: «плохая связь» → «восстанавливаем связь…» → «связь потеряна» +
  «Перезвонить».
- Видео на паузе — аватар вместо картинки; режим «только аудио» — отдельной пометкой.
  Причина паузы значения не имеет: её ставит LiveKit.
- В группе слот выпавшего исчезает; сетка остальных из-за чужого обрыва не
  схлопывается.
- Экрана «переподключение к тому же звонку» для 1:1 после терминального обрыва нет.
